# Qwen2.5-VL（第三代，2025.01）：Window Attention + 动态 Token 预算 + 绝对时间对齐

> 本笔记覆盖 Qwen2.5-VL 的完整技术剖析（论文 2502.13923，2025 年 1 月发布）。这一代不再做"架构革命"，而是做"工程重构"：把 ViT 的全局注意力换成窗口注意力（**看得快**）、把固定 4× 的 token 压缩升级为可调预算（**看得久**）、把 M-RoPE 的时间轴从"帧序号"升级为"绝对时间"（**看得准时间**）。面试被问"高分辨率图像为什么能跑得动""视频怎么定位到秒""视觉 token 怎么动态压缩"时，本篇是完整答案。

---

## 一、一句话解释

### 1.1 一句话解释

> **Qwen2.5-VL = 在 Qwen2-VL 的"动态分辨率 + M-RoPE"底座上做三项重构的第三代视觉语言模型：Window Attention 让高分辨率输入"跑得动"，动态 token 预算让长内容"装得下"，绝对时间对齐让视频事件"定得住秒"。**

### 1.2 三个"看得"拆解

| 宣传语 | 对应技术 | 解决什么问题 | 一句话原理 |
|--------|----------|--------------|-----------|
| **看得快** | Window Attention | 高分辨率下 ViT 全局注意力 O(N²) 算不动 | 32 层 ViT 中 28 层改为 8×8 窗口注意力，仅 4 层保留全局注意力，复杂度降为线性 |
| **看得久** | Visual Token Merger（动态预算） | 固定 4× 压缩无法在精度与成本间调节 | 2×2 分组 + 2 层 MLP，通过 min_pixels/max_pixels 在 4~16384 token 间任意调节预算 |
| **看得准时间** | 绝对时间对齐 | 帧序号无法表达"两帧隔了多久" | 时间 id 直接对齐真实时间戳 + 动态 FPS 训练，支持秒级（hmsf）时间戳定位 |

### 1.3 在系列中的位置

```text
Qwen2-VL (2024): 动态分辨率 + M-RoPE 帧序号 —— 解决了"看得清"
    ↓
Qwen2.5-VL (2025.01): 窗口注意力 + 动态预算 + 绝对时间 —— 解决"看得快、看得久、看得准时间"
    ↓
Qwen3-VL (2025): Interleaved-MRoPE + DeepStack + 文本时间戳 + MoE —— 解决"看得懂、想得深、记得久"
```

三代的继承关系：**动态分辨率与 M-RoPE 的框架全部保留**（这是 Qwen2.5-VL 的底座），本代只换"执行细节"：注意力机制、压缩器、时间轴编码。

## 二、本代三个关键词总览

### 2.1 关键词速览表

| 关键词 | 所属模块 | 核心设计 | 一句话收益 |
|--------|----------|----------|-----------|
| Window Attention | ViT（视觉编码器） | 窗口 112×112（8×8 patch），全局层 {7, 15, 23, 31} | 高分辨率视觉 token 从算不动到线性可扩展 |
| Visual Token Merger | 视觉-语言连接器 | 2×2 分组 + 2 层 MLP，动态 token 预算 | 精度与成本可调，单图 4~16384 token 任意档位 |
| 绝对时间对齐 | M-RoPE 时间轴 | 时间 id = 真实时间戳，动态 FPS 训练 | 感知运动速度，秒级视频事件定位 |

### 2.2 关键词一：Window Attention（第三节详解）

高分辨率下 patch 数量巨大（如 1344×1344 图有 $96\times96=9216$ 个 patch），全局注意力的 $O(N^2)$ 复杂度直接撑爆显存。Qwen2.5-VL 把 ViT 的大部分层换成局部窗口注意力：**每个 patch 只与周围 8×8 窗口内的 patch 交互**，复杂度降为 $O(N)$；仅第 {7, 15, 23, 31} 四层保留全局注意力负责跨区域信息流通。

### 2.3 关键词二：Visual Token Merger（第四节详解）

Qwen2-VL 的 2×2 卷积合并是**固定 4× 压缩**——无论什么图都是 1/4 token。Qwen2.5-VL 改为 **2×2 分组拼接 + 2 层 MLP**，压缩比本身仍是 4×，但通过 `min_pixels` / `max_pixels` 参数可以**显式控制输入像素预算**，从而把单图 token 数约束在 4~16384 之间的任意档位——小图省算力、大图保细节。

### 2.4 关键词三：绝对时间对齐（第五节详解）

Qwen2-VL 的视频时间 id 是**帧序号**（第 1 帧 id=0，第 2 帧 id=1，…），它不包含"这一帧是视频的第几秒"信息——1 FPS 采样与 30 FPS 采样下，相邻帧的 id 差都是 1。Qwen2.5-VL 把时间 id **直接对齐绝对时间戳**：帧间 id 间隔反映真实时间流速，模型因此能感知运动速度，并能输出"第 X 秒发生了什么事"。

### 2.5 三个关键词的关系

三者不是孤立的，而是一条**工程因果链**：

```text
窗口注意力把算力省下来
    → 高分辨率/高帧率输入才跑得动（看得快）
    → 动态 token 预算把省下来的上下文额度按信息量分配（看得久）
    → 时间轴对齐绝对时间，让多出来的视频帧真正可用（看得准时间）
```

没有窗口注意力，高帧率视频的视觉计算成本会让"绝对时间对齐"失去意义；没有动态预算，长视频的 token 会溢出上下文窗口。

## 三、Window Attention：让高分辨率真正跑得动（重点）

### 3.1 问题：全局注意力的 O(N²) 爆炸

自注意力的计算量为：

$$\text{Attn}(Q, K, V) = \text{softmax}\left(\frac{QK^\top}{\sqrt{d_k}}\right)V$$

其中 $Q, K, V \in \mathbb{R}^{N \times d}$，$N$ 为 patch 数量。每个 query 要与**所有** $N$ 个 key 计算相似度，总计算量为 **$O(N^2)$**。

以 patch 14 为例，不同分辨率下的 patch 数与全局注意力单层开销：

| 输入分辨率 | patch 数 N（patch 14） | 全局注意力单层计算量（约） |
|-----------|------------------------|--------------------------|
| 224×224 | $16\times16=256$ | $256^2 \approx 6.6\times10^4$ |
| 448×448 | $32\times32=1024$ | $1024^2 \approx 1.0\times10^6$ |
| 1344×1344 | $96\times96=9216$ | $9216^2 \approx 8.5\times10^7$ |

分辨率翻倍 → 计算量翻 **4 倍**（$2^2$）。原生分辨率输入 1344×1344 时，单层注意力就是千万级操作，32 层叠加后完全不可行——这就是为什么 Qwen2-VL 需要把大图切 sub-image、Qwen2.5-VL 要直接改注意力机制。

### 3.2 设计总表

| 设计 | 值 |
|------|-----|
| ViT 结构 | hidden **1280**、**32 层**、16 heads、patch 14 |
| 初始化 | **从零训练**（DataComp 等预训练数据初始化） |
| 窗口大小 | **112×112 像素 = 8×8 个 patch** |
| 全局注意力层 | 仅 **4 层**：第 **{7, 15, 23, 31}** 层 |
| 窗口注意力层 | 其余 **28 层** |
| 窗口边界处理 | 区域不足窗口尺寸时**不补零**、保持原分辨率 |
| 归一化 / 激活 | **RMSNorm + SwiGLU**（与 Qwen2.5 LLM 对齐） |

两个容易被面试深挖的点：

1. **为什么 4 层全局层就够？** 第 {7, 15, 23, 31} 层均匀分布在 32 层中（每 8 层 1 次），保证任意深度的窗口局部特征都能周期性"看到"全局——浅层全局层负责早期全局形状感知，深层全局层负责语义级跨区域聚合；
2. **为什么从零训练？** 预训练视觉塔（如 SigLIP/OpenCLIP）基于全局注意力，直接换窗口注意力权重分布不匹配。从零训练 + 1.5T token 视觉预训练，让模型从一开始就适应窗口归纳偏置。

### 3.3 窗口注意力与全局注意力的分工

```text
第 {7, 15, 23, 31} 层：全局注意力（全图 9216 个 patch 两两交互）→ 跨区域信息流通
其余 28 层：窗口注意力（每个 patch 只看自己 8×8 窗口）→ 局部特征提取
```

每个 patch 的注意力范围：

- 全局注意力：$N$ 个 patch（全图）；
- 窗口注意力：$8 \times 8 = 64$ 个 patch（局部）。

**代价**：窗口内 patch 无法直接感知窗外信息，跨区域交互依赖那 4 层全局层接力——这是"局部性"代价，Qwen3-VL 之后用 DeepStack 多级特征注入进一步弥补（见 04 篇）。

### 3.4 复杂度分析：从平方到线性

设窗口边长 $w=8$（单位：patch），窗口注意力单层计算量：

$$C_{\text{window}} = N \times w^2 = 64N$$

全局注意力单层计算量：

$$C_{\text{global}} = N^2$$

32 层 ViT 的总计算量约：

$$C_{\text{total}} \approx 28 \times 64N + 4 \times N^2$$

数值对比（patch 14，不同分辨率）：

| 分辨率 | N | 窗口注意力单层 64N | 全局注意力单层 N² | 单层加速比 | 全局层占比（4/32） |
|--------|-----|------------------|------------------|-----------|------------------|
| 224×224 | 256 | 16,384 | 65,536 | 4× | 12.5% |
| 448×448 | 1024 | 65,536 | 1,048,576 | **16×** | 12.5% |
| 1344×1344 | 9216 | 589,824 | 84,934,656 | **144×** | 12.5% |

**结论**：分辨率越高，窗口注意力的优势越大（加速比随 $N$ 线性增长）。1344×1344 原生输入下，28 层窗口注意力总开销 ≈ $28 \times 590\text{K} \approx 1.65\times10^7$，而 4 层全局层 ≈ $4 \times 8.5\times10^7 = 3.4\times10^8$——即便只有 4 层，全局层仍是计算主体，但总量已经降到"全全局注意力"（$32 \times 8.5\times10^7 \approx 2.7\times10^9$）的 **1/8** 以下。

### 3.5 为什么"局部"没有破坏效果

1. **图像本身高度局部相关**：相邻像素/小 patch 的信息天然冗余，8×8 patch 窗口（112×112 像素）已包含足够上下文；
2. **4 层全局层兜底**：论文消融显示，完全没有全局层会导致跨区域语义丢失，{7,15,23,31} 均匀分布的 4 层足以恢复；
3. **与视觉归纳偏置一致**：CNN 世代就验证了"局部感受野 + 深层逐步扩大"是高效视觉范式，窗口注意力是 Transformer 对同一偏置的复刻。

### 3.6 为什么高分辨率文档才跑得动

文档/OCR 场景的痛点是小字——小字需要高分辨率输入才能清晰，而高分辨率带来巨额 patch 数：

```text
一页 A4 文档截图（约 2000×2800）
    → patch 14 → 约 143×200 = 28,600 个 patch
    → 全局注意力：28600² ≈ 8.2×10⁸（单层，直接爆显存）
    → 窗口注意力：28600 × 64 ≈ 1.8×10⁶（单层，可接受）
```

窗口注意力把单层开销压了 **450 倍**，再配合动态 token 预算控制进入 LLM 的 token 数，原生分辨率文档解析才成为可能。**这是"文档解析（Omni-Document Parsing）"能力的技术前提**。

### 3.7 与 Qwen2-VL 的 ViT 对比

| 维度 | Qwen2-VL ViT | Qwen2.5-VL ViT |
|------|-------------|----------------|
| 参数量 | 675M | 675M（沿用） |
| patch | 14 | 14 |
| 层数 | 全层全局注意力 | 32 层中 28 层窗口 + 4 层全局 {7,15,23,31} |
| 归一化/激活 | 常规 | RMSNorm + SwiGLU |
| 初始化 | DFN 预训练权重 | **从零训练** |
| 位置编码 | 2D-RoPE | 2D-RoPE（沿用） |

## 四、Visual Token Merger：可调预算的 token 压缩（重点）

### 4.1 结构：2×2 分组 + 2 层 MLP

ViT 输出的 patch 特征进入 LLM 前，先经过合并器压缩：

```text
ViT 输出:  H_p × W_p 个 patch 特征（patch 14，hidden 1280）
    ↓ 2×2 邻域分组（空间相邻的 4 个 patch 特征拼接）
    每个 token 对应 4 × 1280 维拼接向量
    ↓ 2 层 MLP 投影到 LLM 隐藏维
    得到 (H_p/2) × (W_p/2) 个视觉 token
```

- 压缩结构仍是 **2×2 → 1**（压缩比 4×）；
- 每个视觉 token 覆盖 $14 \times 2 \times 14 \times 2 = 784$ 像素（28×28 像素块）；
- 视觉 token 数量与动态分辨率公式自洽：

$$N_{\text{tok}} = \frac{H'}{28} \times \frac{W'}{28} = \frac{H' \cdot W'}{784}$$

其中 $H' \times W'$ 为缩放对齐后的输入尺寸（28 的倍数）。

### 4.2 与 Qwen2-VL 固定 4× 卷积的差异

| 维度 | Qwen2-VL（第二代） | Qwen2.5-VL（第三代） |
|------|-------------------|---------------------|
| 合并方式 | 2×2 卷积（stride 2） + MLP | 2×2 分组拼接 + 2 层 MLP |
| 压缩比 | 固定 4× | 结构 4×，但**预算可调** |
| token 预算控制 | 仅 min/max_pixels（分辨率层面） | 像素预算 + **显式指定 resized_height/width** |
| 可调性 | 分辨率决定 token，间接调 | 预算直接决定 token，**精度与成本可显式权衡** |
| 对齐单位 | 28（patch 14 × 合并 2） | 28（沿用） |

本质差异一句话：**Qwen2-VL 是"给一张图，算完再说"；Qwen2.5-VL 是"先说好要多少 token，再决定怎么编码"**。合并器本身仍输出 $(H_p/2)\times(W_p/2)$ 个 token，但上游的缩放策略可以按预算反向调整输入分辨率。

### 4.3 动态预算机制

默认单图 token 范围 **4 ~ 16384**：

| 参数 | 默认值 | 含义 |
|------|--------|------|
| `min_pixels` | $4 \times 28 \times 28$ | 单图最少对应 4 个视觉 token（极小图也至少放大到 4 token） |
| `max_pixels` | $16384 \times 28 \times 28$ | 单图最多对应 16384 个视觉 token（显存安全上限） |
| `resized_height/width` | 可选 | 直接指定目标分辨率（自动对齐 28 网格） |

```text
min_pixels = 4×28×28   → 至少 4 token（极简图，够用即可）
max_pixels = 16384×28×28 → 至多 16384 token（长文档截图、大图全景）
```

**调节方式**：调低 `max_pixels` → 图被等比缩小 → token 变少 → 省显存省算力（细节略损）；调高 → 保细节（代价是 KV cache 变大）。业务上就是"细节优先"还是"成本优先"的旋钮。

### 4.4 精度与成本的权衡

| 场景 | 推荐预算 | 理由 |
|------|----------|------|
| 普通对话配图 | 256~1024 token | 信息量小，足够 |
| 文档/OCR | 4096~16384 | 小字需要高分辨率保细节 |
| 长视频（整体预算） | 总预算分摊到帧 | 帧分辨率按总 token 预算动态调整 |
| 多图对比 | 每图独立预算 | 单图预算下调防溢出 |

动态预算的消融意义（与 Qwen2-VL 的结论一致）：**适当提高 min_pixels（小图放大）能提升 InfoVQA、OCRBench 等感知任务，但 min_pixels 过大反而损害 OCRBench**——大量极小图被过度放大脱离训练分布（OOD）。预算不是越大越好。

### 4.5 视频侧动态预算

视频与图像共用同一套合并器，但多了**时间维压缩**：

- 视频按 **2 FPS** 抽帧；
- 时域卷积（depth=2 的 3D 卷积）把相邻 2 帧合并为 1 个时间步（`temporal_patch_size=2`），**不增加序列长度**就能处理更多帧；
- 单张图片被视为 2 个相同帧（满足时域卷积输入结构）——"图像即 1 帧视频"的统一建模沿用 Qwen2-VL；
- 帧分辨率按总 token 预算动态调整，长视频不至于瞬间吃满 16384。

## 五、绝对时间对齐：从"第几帧"到"第几秒"（重点）

### 5.1 Qwen2-VL 的时间建模局限

Qwen2-VL 的 M-RoPE 时间轴 id 是**帧序号**：

```text
视频（2 FPS 抽帧）:  帧0 → t=0 | 帧1 → t=1 | 帧2 → t=2 | ...
```

问题：**帧序号不包含时间流速信息**。1 FPS 采样的相邻帧间隔 1 秒、30 FPS 采样的相邻帧间隔 1/30 秒，但两边的 id 差都是 1。模型不知道"这两帧之间隔了多久"，因此：

- 无法判断运动快慢（慢动作 vs 快进）；
- 无法回答"第几秒发生"（只能答"第几帧"，且帧号与真实时间无固定换算）。

### 5.2 帧序号 → 真实时间戳

Qwen2.5-VL 的改动：**时间 id 直接按帧的真实时间戳分配**。

```text
2 FPS 采样:  帧0(0.0s) → t=0 | 帧1(0.5s) → t=1 | 帧2(1.0s) → t=2 | 帧3(1.5s) → t=3 ...
帧间 id 间隔 = 真实时间流速 × 采样率
```

- 帧间 id 间隔**反映真实时间间隔**（0.5 秒 = 1 个 id 间隔）；
- 模型从位置编码里"读"出时间：两个 token 相隔的 id 数 × 每 id 对应秒数 = 真实时间差；
- M-RoPE 的时间轴从"帧序号"升级为"绝对时间坐标"。

### 5.3 动态 FPS 训练

固定 2 FPS 训练的问题：模型只见过"0.5 秒/id"一种流速，一旦推理时换采样率就失准。Qwen2.5-VL 的解法是**动态 FPS 训练**——训练时按不同采样率抽样，让时间 id 间隔覆盖多种"秒数/id"比例：

| 训练采样率 | 帧间 id 间隔对应的真实时间 |
|-----------|--------------------------|
| 1 FPS | 1.0 秒 |
| 2 FPS | 0.5 秒 |
| 4 FPS | 0.25 秒 |
| 8 FPS | 0.125 秒 |

模型在不同流速下都见过"真实时间 ↔ id 间隔"的对应关系，学会的是**时间本身的尺度**（1 秒 = 多少个 id 间隔），而不是某一固定采样率下的映射。**这就是"感知运动速度"的来源**：同一段动作，8 FPS 下 4 个 id 间隔，1 FPS 下只有 0.5 个——模型通过 id 间隔密度判断快慢。

### 5.4 秒级时间戳定位（hmsf 格式）

视频定位数据用两种格式标注，模型可输出**秒级时间戳**：

| 格式 | 示例 | 适用 |
|------|------|------|
| 秒 | `13.5 seconds` | 通用时长表达 |
| 时:分:秒:帧（hmsf） | `00:00:13:15` | 精确到帧的视频定位 |

```text
Q: 视频里救援人员什么时候到达？
A: 救援人员在 00:00:13:15（hmsf）到达画面。
```

hmsf 的最后一格是帧号（相对该秒的帧偏移），它与绝对时间 id 的换算关系是封闭的——模型输出定位后，可以精确反推视频中的真实时刻，这是"看得准时间"的直接产品形态。

### 5.5 视频统一建模回顾

| 组件 | 设计 | 作用 |
|------|------|------|
| 抽帧 | 2 FPS（可配） | 采样率与时间 id 对齐 |
| 时域卷积 | depth=2，2 帧合并 1 时间步 | 不增序列长度处理更多帧 |
| M-RoPE 时间轴 | 绝对时间 id（动态 FPS 训练） | 感知速度 + 秒级定位 |
| 位置 id 规则 | 文本 (i,i,i) / 图像 (常数,行,列) / 视频 (时间,行,列) | 三维统一编码 |

### 5.6 带来的新能力（vs Qwen2-VL）

1. **时间定位**：可回答"第几秒发生了什么"，而非"第几帧"；
2. **速度感知**：能区分"慢慢走过去"与"快速跑过去"；
3. **事件密度判断**：能回答"X 和 Y 哪个动作发生得更快/更早"；
4. **跨帧推理**：结合真实时间差，"事件 A 比事件 B 早 3.5 秒"这类问题变得可解。

## 六、Omni-Document Parsing：整页文档解析

### 6.1 从"识别文字"到"解析文档"

Qwen2-VL 已能做 OCR（识别文字），但输出是"散装的文字流"。Qwen2.5-VL 把能力升级为**解析整页文档**：

| 能力 | Qwen2-VL | Qwen2.5-VL |
|------|----------|-----------|
| 文字识别 | 强 | 更强（窗口注意力 + 原生高分辨率） |
| 版面理解 | 弱 | 表格、图表、公式、乐谱、手写体、多栏版面 |
| 结构化输出 | 无 | **HTML 标签 + JSON** |
| 票据/报表抽取 | 手工 | 结构化抽取开箱即用 |

### 6.2 HTML 结构化输出

输出**结构化 HTML 标签**，保留版面布局信息：

```html
<table>
  <tr><td>项目</td><td>金额</td></tr>
  <tr><td>技术服务费</td><td>¥ 12,000</td></tr>
</table>
```

HTML 天然表达层级（`<table>` 内嵌 `<tr>`/`<td>`）与并排关系（多栏 `<div>`），比纯文本更适合文档重建——模型把"看到的一页纸"翻译成"可渲染的网页结构"。

### 6.3 表格/公式/版面

| 元素 | 处理方式 |
|------|----------|
| 表格 | 输出 `<table>` 结构，行列关系无损 |
| 公式 | LaTeX 输出（`\frac{a}{b}` 等） |
| 图表 | 图像描述 + 数据要点提取 |
| 多栏版面 | 按栏顺序结构化重排 |
| 乐谱/手写体 | 专项数据覆盖，原生分辨率支撑 |

### 6.4 典型应用

- 发票/报表结构化抽取（JSON 输出）；
- 学术论文版面重建（HTML/LaTeX）；
- 扫描件数字化（OCR + 版面恢复）；
- 长文档问答（结构保留 → 引用定位）。

**技术依赖链**：窗口注意力（跑得动高分辨率）→ 原生分辨率（小字清晰）→ 动态预算（多分配 token 给文字区）→ 结构化输出（HTML/JSON）。

## 七、Agent 能力：看懂屏幕、操作系统

### 7.1 UI 定位：框/点 + 绝对坐标 JSON

Qwen2.5-VL 面向手机/桌面/Web 截图场景，支持 UI 元素定位：

| 定位形式 | 输出格式 | 用途 |
|----------|----------|------|
| 框（box） | `(x_tl, y_tl), (x_br, y_br)` 绝对坐标 JSON | "点击红色按钮"（按钮在哪） |
| 点（point） | `(x, y)` 绝对坐标 JSON | "点开设置图标"（精确坐标） |

坐标是**绝对坐标 JSON**（相对屏幕分辨率，归一化到 $[0,1000)$ 的文本化坐标），与 Qwen 系"用语言完成定位"的传统一致——无需专门输出头，坐标就是文本 token。

### 7.2 动作空间：function call

UI 操作被统一建模为 **function call 动作空间**：

```text
模型"看屏幕"（截图 → 视觉 token）
    → 理解界面（识别按钮、输入框、弹窗）
    → 决策（该点哪里、输入什么）
    → 输出 function call（如 click(x, y) / type(text) / scroll(direction)）
```

### 7.3 多步轨迹闭环

- 多步 Agent 轨迹数据**合成**（模拟器渲染 + 轨迹标注）；
- 每步附带**推理过程标注**（"先点搜索框 → 输入关键词 → 点击第一个结果"）；
- 支撑"看屏幕 → 决策 → 操作 → 再看屏幕"的完整闭环；
- 训练数据里专门含**长 Agent 轨迹**（对应阶段 3 的 0.6T 长上下文数据）。

## 八、模型家族与训练

### 8.1 模型家族

| 模型 | LLM 底座 | 视觉塔 | 定位 |
|------|----------|--------|------|
| Qwen2.5-VL-3B | Qwen2.5-3B | 675M ViT（共享） | 轻量、端侧 |
| Qwen2.5-VL-7B | Qwen2.5-7B | 675M ViT（共享） | 性价比主力 |
| Qwen2.5-VL-72B | Qwen2.5-72B | 675M ViT（共享） | 旗舰 |

**注意：三个尺寸共用同一个 675M ViT**——视觉计算开销不随 LLM 规模增长（Qwen2-VL 开创的设计，沿用至今）。

### 8.2 三阶段训练（数据规模翻三倍）

| 阶段 | token 量 | 序列长度 | 训练对象 | 数据构成 |
|------|---------|---------|---------|---------|
| 阶段 1 视觉预训练 | **1.5T** | 8192 | **仅 ViT** | 图像字幕、知识、OCR、纯文本 |
| 阶段 2 多模态预训练 | **2T** | 8192 | ViT + LLM | 交错图文、VQA、视频、定位、Agent |
| 阶段 3 长上下文预训练 | **0.6T** | **32768** | ViT + LLM | 长视频、长 Agent 轨迹、长文档 |
| 合计 | **约 4.1T** | — | — | 长视频 >30 分钟专门合成字幕 |

与 Qwen2-VL（1.4T token）对比：**训练数据约 3 倍**。三个设计要点：

1. **阶段 1 只训 ViT**：窗口注意力从零训练，先用 1.5T 数据把视觉塔对齐到窗口归纳偏置；
2. **阶段 3 拉长序列到 32768**：为了容纳长视频与长文档（>30 分钟视频的合成字幕专门为这一阶段准备）；
3. **只对文本 token 计算 loss**：视觉 token 无监督目标，延续 Qwen 系传统。

### 8.3 序列长度演进

```text
Qwen2-VL:  8192（固定）
Qwen2.5-VL: 8192（阶段 1/2）→ 32768（阶段 3）
```

32768 的上下文对应约 30 分钟左右的视频（2 FPS、每帧低分辨率预算）或长文档截图的 token 需求——这也是"看得久"的一部分。

### 8.4 与 Qwen2-VL 训练对比

| 维度 | Qwen2-VL | Qwen2.5-VL |
|------|----------|-----------|
| 总 token | 约 1.4T | **约 4.1T（约 3 倍）** |
| 阶段数 | 3 | 3 |
| 序列长度 | 8192 | 8192 → 32768 |
| 阶段 1 训练对象 | 视觉编码器对齐（DFN 初始化） | 仅 ViT（**从零训练**） |
| 特殊数据 | — | 长视频合成字幕、长 Agent 轨迹 |

## 九、能力提升与局限

### 9.1 与 Qwen2-VL 对比表

| 维度 | Qwen2-VL | Qwen2.5-VL | 提升来源 |
|------|----------|-----------|---------|
| 视觉计算效率 | 全全局注意力，高分辨率受限 | 窗口注意力，原生高分辨率可跑 | 28/32 层窗口化 |
| token 预算 | 像素预算间接控制 | 像素预算 + 显式尺寸，精度成本显式权衡 | 动态合并器 |
| 视频时间感知 | 帧序号，无速度概念 | 绝对时间，感知速度 + 秒级定位 | 绝对时间对齐 + 动态 FPS |
| 文档解析 | OCR + 基础版面 | HTML 结构化整页解析 | 高分辨率 + 专项数据 |
| Agent | 基础截图理解 | 框/点定位 + function call 动作空间 | 合成轨迹数据 |
| 训练数据 | 1.4T | 4.1T | 数据规模翻三倍 |
| 上下文 | 8192 | 32768 | 长上下文阶段 |
| 视频上限 | 可理解较长视频 | **可理解 1 小时以上视频** | 窗口注意力 + 动态预算 |

### 9.2 局限

**局限一：长视频的时间 id 过大、稀疏（最根本的遗留问题）**

绝对时间对齐用**数值大小**表示时间：视频越长，时间 id 越大（30 分钟视频 2 FPS ≈ 3600 个时间 id，更长视频上万）。M-RoPE 是旋转位置编码，过大的位置数值会：

- 超出训练时的 id 分布，长时序外推不稳；
- 时间 id 在高帧率下分布稀疏，模型学不到"密集时间流"。

这个缺陷正是 Qwen3-VL 放弃时间 id、改用**文本时间戳**（`<3.0 seconds>`）的直接动因（见 04 篇第七节）。

**局限二：窗口注意力的局部性**

- 每个 patch 默认只能看到 8×8 窗口，跨区域依赖 4 层全局层接力——窗口间信息交换带宽有限；
- 窗口边界的 patch 视野受限（不补零设计下，边缘区域窗口更小）；
- 对"跨区域比对"类任务（如"左上角物体与右下角物体的关系"）理论支持弱于全全局注意力。

**局限三：动态 FPS 训练的数据成本**

要在各 FPS 下均匀采样训练数据，数据构造昂贵——这是 Qwen3-VL 文本时间戳方案"训练更省"的对比基准。

**局限四：显存峰值压力**

- 单图 token 峰值 16384，KV cache 与注意力计算随 token 数增长，显存上限由"最坏情况"决定；
- 高分辨率 + 高帧率视频下 token 总量仍可能逼近上下文上限；
- 对策：调低预算、flash-attention、按需二次缩放。

## 十、高频面试问答

**Q1：Qwen2.5-VL 的 Window Attention 具体怎么设计？为什么能提速？**
ViT 共 32 层（hidden 1280，patch 14，从零训练）：第 {7, 15, 23, 31} 共 4 层保留全局注意力，其余 28 层使用 8×8 patch（112×112 像素）的窗口注意力，窗口不足时不补零。复杂度从 O(N²) 降为 O(64N)（线性于 patch 数），分辨率越高收益越大（1344² 图单层加速约 144 倍）。RMSNorm + SwiGLU 与 Qwen2.5 LLM 对齐。

**Q2：为什么只保留 4 层全局注意力？**
图像信息高度局部相关，8×8 窗口（112×112 像素）已足够提取局部特征；{7,15,23,31} 均匀分布在 32 层中，每 8 层有一次全局交互，足以承接跨区域信息流通，同时把全局注意力的 O(N²) 开销压到总计算量的约 1/8。

**Q3：Visual Token Merger 与 Qwen2-VL 的 2×2 卷积合并有什么区别？**
结构上：Qwen2 用 2×2 卷积（stride 2）+ MLP，Qwen2.5 用 2×2 邻域拼接 + 2 层 MLP，压缩比同为 4×。本质区别在可控性：Qwen2.5 通过 min_pixels/max_pixels（默认 4~16384 token）或显式 resized_height/width 直接指定 token 预算，精度与成本可显式权衡，而 Qwen2 只能通过分辨率间接控制。

**Q4：单图 token 数怎么算？4~16384 的预算怎么理解？**
缩放对齐后 $N_{\text{tok}} = H'W'/784$（28 = patch 14 × 合并 2）。min_pixels = 4×28×28 保证极小图至少 4 个 token；max_pixels = 16384×28×28 保证单图至多 16384 个 token（显存安全上限）。调低预算省算力损细节，调高反之，min_pixels 过大反而损害 OCRBench（OOD）。

**Q5：绝对时间对齐是怎么工作的？**
M-RoPE 的时间轴从"帧序号"改为"真实时间戳"：时间 id 按帧的真实时间分配，帧间 id 间隔反映真实时间流速；配合动态 FPS 训练（1/2/4/8 FPS 混合采样），模型学会"1 秒 = 多少 id 间隔"，从而感知运动速度；视频定位数据用"秒"与"时:分:秒:帧（hmsf）"两种格式标注，模型可输出秒级时间戳。

**Q6：Qwen2-VL 和 Qwen2.5-VL 在视频能力上的本质区别？**
三点：① 时间建模从"帧序号"变成"绝对时间"（能感知速度、秒级定位事件）；② 采样从固定 2 FPS 变成动态 FPS 训练（任意采样率都稳）；③ 窗口注意力 + 动态预算让更高帧率/更长时间成为可能（可理解 1 小时以上视频）。

**Q7：为什么窗口注意力让高分辨率文档解析成为可能？**
文档小字需要原生高分辨率，而高分辨率产生海量 patch（如 2000×2800 文档约 28,600 个 patch），全局注意力单层 8×10⁸ 次操作直接爆显存；窗口注意力把单层开销压到 1.8×10⁶（约 450 倍），配合动态 token 预算控制进入 LLM 的 token 数，整页文档才跑得动。

**Q8：训练数据 4.1T 是怎么构成的？**
三阶段：阶段 1 视觉预训练 1.5T（仅 ViT，图像字幕/知识/OCR/纯文本，序列 8192）→ 阶段 2 多模态预训练 2T（ViT+LLM，交错图文/VQA/视频/定位/Agent，序列 8192）→ 阶段 3 长上下文预训练 0.6T（ViT+LLM，长视频/长 Agent 轨迹/长文档，序列 32768）。合计约 4.1T，约为 Qwen2-VL（1.4T）的 3 倍。

**Q9：Qwen2.5-VL 的文档解析和 OCR 有什么区别？**
OCR 只输出文字流；Omni-Document Parsing 输出整页结构化表示：表格转 `<table>`、公式转 LaTeX、多栏版面按序重排、票据报表可直接 JSON 抽取。它是"识别文字 + 版面理解 + 结构化输出"三者的组合，依赖窗口注意力（跑得动高分辨率）与原生分辨率（小字清晰）。

**Q10：Qwen2.5-VL 的主要局限有哪些？**
① 长视频时间 id 过大稀疏，损害长时序外推（Qwen3-VL 改文本时间戳的直接动因）；② 窗口注意力局部性，跨区域依赖 4 层全局层；③ 动态 FPS 训练数据构造昂贵；④ 单图 token 峰值 16384 带来显存压力。

## 十一、常见误区

**误区 1：Window Attention 是"每层都做局部 + 全局两种注意力"。**
错。是**分层分工**：28 层只做窗口注意力（8×8 patch），仅 4 层（{7,15,23,31}）做全局注意力，每层只有一种注意力机制。且窗口不足时不补零。

**误区 2：动态 token 预算 = 合并器本身可变压缩比。**
不准确。合并器的结构压缩比**固定 4×**（2×2 → 1）；"动态"指的是**输入像素预算可调**（min/max_pixels、显式尺寸），通过改变上游分辨率反向决定 token 数 4~16384。

**误区 3：绝对时间对齐只是把帧序号换了个单位。**
不止。它还配套了**动态 FPS 训练**（多种采样率混合）让模型学会时间流速、**hmsf 秒级格式**做视频定位标注。仅换单位不训练，模型无法从 id 间隔感知速度。

**误区 4：Qwen2.5-VL 的 ViT 是复用 Qwen2-VL 预训练权重微调的。**
错。窗口注意力与全局注意力权重分布不匹配，ViT 是**从零训练**（hidden 1280、32 层、patch 14），由阶段 1 的 1.5T 视觉数据完成初始化对齐。
