# Qwen-VL 系列：部署与推理优化

> 本笔记是 Qwen-VL 系列技术专题的第二篇，聚焦多模态模型的**服务化部署与推理优化**。全篇纯理论：指标定义、推理链路拆解、框架选型、token 裁剪、量化、显存核算、服务化与压测方法。所有数字沿用《09_QwenVL.md》的基准事实：单图 token 上限 16384、1080p 图约 2584 token、视觉塔 675M（Qwen2 系）/ SigLIP-2 级（Qwen3-VL）、2 FPS 视频建模、Qwen3-VL 256K 原生上下文与 Thinking 双模式。面试被问"多模态为什么显存大""token 怎么裁剪""vLLM 为什么快"时，本笔记是完整答案。

## 一、部署目标与指标

### 1.1 核心指标定义表

| 指标 | 定义 | 受什么影响 | 多模态下的典型表现 |
|------|------|-----------|------------------|
| TTFT（Time To First Token） | 请求进入 → 返回首个输出 token 的耗时 | prefill 长度、视觉塔前向、首步 decode | 一张图几千视觉 token 全量参与 prefill，TTFT 天然远高于纯文本 |
| TPOT（Time Per Output Token） | decode 阶段生成每个 token 的平均耗时 | KV cache 读取带宽、batch 大小、模型规模 | 与文本接近，但受同 batch 内最长序列拖累 |
| P50 / P95 | 延迟的分位数（50% / 95% 请求不超时） | 负载、排队、序列长度分布 | 输入长度方差极大（4~16384 token），P95 远高于 P50 |
| QPS（Queries Per Second） | 吞吐：每秒完成的请求数 | batch 效率、量化、并发 | 受长 prefill 的 GPU 占用拖累，多模态 QPS 低于同规模纯文本 |
| 显存峰值 | 推理全程显存的最大占用 | 权重 + KV cache + 激活 + 视觉特征 | 由"最坏情况"（16384 token 长文档/视频）决定，打包困难 |

### 1.2 多模态特有的三个特征

1. **prefill 长**：一张 1080p 图约 2584 个视觉 token，加上文本轻松三千起步；而纯文本请求往往只有几百 token。prefill 阶段 attention 是 O(n²)，TTFT 被视觉 token 数直接决定；
2. **视觉部分算力密集**：图像要走一遍 ViT 前向（Qwen2 系 675M，patch 14），FLOPs 与像素数成正比，是纯文本没有的固定开销；
3. **输入长度波动极大**：同一个模型既要处理 4 token 的极简图，也要处理 16384 token 的长文档。batch 内打包困难、padding 浪费多、延迟方差大——这就是 P95 比平均延迟更重要的原因。

### 1.3 指标之间的权衡

```text
token 预算 ↓ → TTFT ↓、KV 显存 ↓、QPS ↑，但精度/召回 ↓（小字、细粒度）
量化加深   → 显存 ↓、QPS ↑，但精度风险 ↑（视觉塔敏感）
batch 增大 → QPS ↑、P95 ↑（排队与相互拖累）
并发升高   → 利用率 ↑，但超过拐点后 P95 急剧恶化
```

### 1.4 显存峰值核算公式（定容第一性原理）

$$M_{\text{peak}} = M_{\text{weights}} + M_{\text{KV}}(n_{\max}) + M_{\text{activation}}$$

- $M_{\text{weights}}$：常驻权重。BF16 每参数 2 字节，INT8 每参数 1 字节；
- $M_{\text{KV}}(n_{\max})$：按**最坏情况 token 数**（16384）核算的 KV cache，而非平均输入；
- $M_{\text{activation}}$：视觉塔激活 + prefill 激活，随 batch 与分辨率波动。

以 Qwen2-VL-7B 为例（LLM 约 7.6B 参数，INT8；视觉塔 675M，BF16；预算 512 token）：

$$M_{\text{peak}} \approx \underbrace{7.6 \times 1}_{\text{INT8 权重}} + \underbrace{0.675 \times 2}_{\text{视觉塔 BF16}} + \underbrace{2\times28\times512\times3584\times1}_{\text{KV, INT8}} + 2\sim3_{\text{激活}} \approx 12\ \text{GB}$$

**关键纪律**：定容用峰值（16384 token 档）而不是均值；batch 打包时"最坏情况"决定显存上限，这正是多模态"batch 内打包困难"的根源（论文 §10.1）。

## 二、推理链路拆解

### 2.1 五个阶段

```text
① 预处理与切分（服务端，CPU/前端）
    缩放 → 28 对齐 → 超 448² 切 sub-image（行优先）
  ↓
② 视觉塔前向（GPU，仅一次）
    每个 sub-image 过 ViT（Qwen2 系 675M，patch 14 / Qwen3-VL SigLIP-2 级，patch 16）
    → patch 特征（1280 维）
  ↓
③ 压缩与投影（GPU，一次）
    2×2 合并（或 32× 像素压缩）+ MLP 投影到 LLM 隐藏维（3584）
    → 视觉 token，替换 <|image_pad|> 占位符
  ↓
④ LLM prefill（GPU，一次）
    视觉 token + 文本 token 全量参与：attention O(n²)，写入 KV cache
  ↓
⑤ decode（GPU，T 次迭代）
    逐 token 生成：每步只与全部 n 个 KV 交互（O(n)），KV cache 持续累积
```

### 2.2 各阶段算力/显存特征表

| 阶段 | 算力特征 | 显存特征 | 执行次数 | 主要优化手段 |
|------|---------|---------|---------|-------------|
| 预处理/切分 | 几乎为零 | 零 | 1 | 服务端缓存切分结果 |
| 视觉塔前向 | FLOPs ∝ 像素数；675M ViT | 激活随 batch×像素增长 | 1 次/请求 | 分辨率预算（max_pixels）、窗口注意力 |
| 压缩/投影 | 线性，可忽略 | 小 | 1 | — |
| LLM prefill | attention O(n²)；16384 token 时朴素分数矩阵约 15 GB（BF16） | 首次写入全部 KV | 1 次/请求 | flash-attention、chunked prefill、token 预算 |
| decode | 每步 O(n)（读全部 KV）；注意力带宽密集而非算力密集 | KV cache 累积为主 | T 次（输出长度） | 批处理、KV cache 量化、GQA 复用 |

### 2.3 一个请求的显存时间线（示意）

```text
显存
 ↑
 │  ┌── 视觉塔激活（峰值段）──────────────────────────┐
 │  │    ┌── prefill 激活（峰值段）────┐                │
 │  │    │ ┌───────────────────────── KV cache（持续累积）┤
 │  └────┴──────────────────────────────┘
 │  权重（常驻，最大的一块）
 └────────────────────────────────────────────→ 时间
  ②视觉塔  ③投影  ④prefill     ⑤decode（T 步）
```

**关键点**：显存峰值出现在"视觉塔激活 + prefill 激活 + 全部 KV"叠加的窗口期；decode 阶段只有 KV 在增长，显存随时间缓升、不回落。因此**峰值显存 ≈ 权重 + 最大 KV + 激活峰值**，三块都要核算。

### 2.4 prefill 与 decode 的算力/带宽模型（为什么优化手段不同）

| 阶段 | 计算量 | 数据量 | 算术强度（FLOP/byte） | 瓶颈 |
|------|--------|--------|----------------------|------|
| LLM prefill | $\approx 2 n^2 d$ 每层（attention）+ $2 n d^2$（FFN） | n 个 token 的激活 | 高（可并行，算力密集） | **算力**：O(n²) 注意力 |
| LLM decode | $\approx 2 n d$ 每层（读全部 KV） | n 个 token 的 KV | 低（每 token 读 n×d 个权重/KV） | **显存带宽**：KV 读取 |
| 视觉塔前向 | $\approx 2N_p^2 d_v$（patch 自注意力，$N_p$ 为 patch 数） | 像素激活 | 高 | 算力（可用窗口注意力降至 O(N_p)） |

- **prefill 是算力密集**：长视觉 token 序列下 attention O(n²)，所以 token 预算对 TTFT 是"平方级"杠杆；
- **decode 是带宽密集**：TPOT 主要由"每步读取全部 KV 的带宽"决定，所以 KV cache 量化与 batch 分摊对 TPOT 最有效；
- **视觉塔前向是固定税**：与 LLM 解码不同，它只在请求开头跑一次，但 675M ViT 在低分辨率下也可能占 TTFT 的相当比例，预算降到底时它会成为 TTFT 的主要成分。

### 2.5 chunked prefill：拆解长 prefill 的延迟尖峰

单请求 prefill 16384 token 时，TTFT 可达秒级甚至数十秒级（O(n²) 注意力 + 显存峰值）。**Chunked Prefill** 把长 prefill 切成多个小 chunk（如 2048 token/块），与 decode 请求混排在同一个 batch 里：

```text
无 chunked：  [======= prefill 16384 =======]  → 其他请求全部被堵住（TTFT 尖峰）
有 chunked：  [c1][d1][d2][c2][d3][d4][c3]...  → 长 prefill 与短 decode 穿插
```

收益：① 消除"一个长请求饿死整个 batch"的延迟尖峰；② 拉平显存峰值（不需要一次性写入全部 KV）。代价：长请求自身的 TTFT 略有上升——这是"公平性"与"单请求极致延迟"的取舍。多模态下长文档/长视频请求尤其依赖此机制。

## 三、推理框架选型

### 3.1 HF Transformers vs vLLM vs SGLang 对比表

| 维度 | HF Transformers | vLLM | SGLang |
|------|-----------------|------|--------|
| 定位 | 研究/原型验证 | 高并发服务 | 高并发 + 复杂采样/结构化输出 |
| 批处理 | 无自动批处理（手动） | **continuous batching**（迭代级调度） | continuous batching |
| KV cache 管理 | 连续内存预分配，浪费严重 | **PagedAttention**（页表映射） | **RadixAttention**（前缀树复用） |
| 前缀复用 | 无 | prefix cache（需命中） | RadixAttention 自动复用 |
| 注意力 | eager / SDPA | flash-attention 系列 | flash-attention 系列 |
| 多模态支持 | 最广（Transformers 原生） | Qwen2-VL / 2.5-VL / 3-VL 原生支持 | Qwen2-VL 等原生支持 |
| 典型延迟 | 高（无优化） | 低 | 低（多轮图文对话复用更强） |
| 适用 | 调试、评测、小规模 | 生产服务主力 | 需要 RadixAttention 复用或 structured output 的场景 |

### 3.2 vLLM 为什么快：两个核心机制

**PagedAttention**：把 KV cache 按固定块（默认 16 token/块）切分，通过**页表**把逻辑块映射到非连续的物理块。

```text
逻辑视图（每个序列的连续 KV）           物理显存（按 16 token 块分页）
┌────┬────┬────┬────┬────┐          ┌────┬────┬────┬────┬────┬────┐
│seq1│seq2│seq3│    │    │  页表映射 │ 块1│ 块3│ 块2│ 块4│    │    │
└────┴────┴────┴────┴────┘          └────┴────┴────┴────┴────┴────┘
```

- 消除**内部碎片**（传统预分配按最大长度预留，短序列浪费大半）；
- 消除**外部碎片**（物理块可以分散存放，不要求连续显存）；
- 效果：相同显存下容纳更多并发序列，显存利用率接近 100% 的"按需分配"。

**Continuous batching（连续批处理）**：传统静态 batch 等整个 batch 都生成完才整体换入新请求，GPU 空转严重。vLLM 是**迭代级调度**：每轮 decode 结束，完成的请求立即退出、新请求立即插入，batch 动态伸缩。对多模态尤其重要——长 prefill 请求与短文本请求可以在同一轮调度中穿插，避免"一个长请求卡住整个 batch"。

### 3.3 多模态框架注意点

- 视觉塔前向与预处理（缩放/切分/占位符替换）必须由引擎或配套 processor 完成——vLLM/SGLang 已内置 Qwen 系的多模态入口，但不同版本对 Qwen3-VL 的 DeepStack / 文本时间戳 / 双模式支持程度不同，选型时要核对版本；
- 多图/视频请求的占位符计数（Qwen3-VL 用 `<|image_pad|>` 计数占位）要由预处理正确生成；
- SGLang 的 RadixAttention 对**多轮图文对话**收益最大：同一张图的视觉 token 是固定的，前缀树可以跨轮直接复用其 KV，省掉每轮重复的视觉 prefill。

### 3.4 引擎选型决策树

```text
是否生产服务？
 ├─ 否 → HF Transformers（调试/评测/原型最快）
 └─ 是 → 是否需要多轮图文 KV 复用 / 结构化输出（JSON Schema）？
          ├─ 是 → SGLang（RadixAttention + structured output 原生）
          └─ 否 → vLLM（生态最成熟、多模态支持最全：Qwen2-VL/2.5-VL/3-VL 原生）
```

| 场景 | 推荐 | 理由 |
|------|------|------|
| 单轮高并发图片理解 | vLLM | continuous batching + PagedAttention 最成熟 |
| 多轮图文对话（同图反复追问） | SGLang | RadixAttention 复用视觉 KV，省每轮 prefill |
| Agent/function call 场景 | SGLang | 结构化输出与约束解码 |
| 评测脚本、离线批跑 | HF Transformers | 最灵活、无额外依赖 |
| Qwen3-VL 最新特性（DeepStack/时间戳/Thinking） | 核对各引擎版本 | 新架构特性滞后集成，需验证

## 四、视觉 Token 裁剪（重点）

### 4.1 为什么 token 是 KV cache 大头：数值账本

以 Qwen2-VL-7B 的 LLM（28 层、3584 维、BF16）为例，KV cache 成本：2×28×n×3584×2 字节 ≈ **0.40 MB/token**。

| 请求类型 | token 构成 | KV cache 估算 |
|---------|-----------|--------------|
| 纯文本问题 | 约 512 文本 token | 约 0.21 GB |
| 单张 1080p 图 + 文本 | **约 2584 视觉 token** + 几百文本 | 约 1.04 GB（视觉是文本的 5 倍+） |
| 长文档截图 | 上限 16384 | 约 6.58 GB（单序列即超大半卡） |
| 多图对比 | 每图独立预算，线性叠加 | 随图数线性增长 |

**结论一句话**：多模态请求的 KV cache 大头是视觉 token，不是文本。token 预算直接决定显存与 TTFT，是部署优化第一杠杆。

### 4.2 裁剪方法分类

| 方法 | 原理 | 优点 | 代价/风险 |
|------|------|------|----------|
| 分辨率上限（max_pixels） | 缩放使 $H'\cdot W' \le \text{max\_pixels}$，28 对齐 | 最简单可靠；从源头控制 token | 小字/细节被缩没 |
| 均匀采样 | 对 token 序列隔 N 取 1 / 网格降采样 | 实现成本低 | 无差别丢信息，可能破坏密集文字 |
| 注意力分数裁剪 | 按 ViT/VLM 注意力分数保留 top-k token | 信息驱动，动态保留重要区域 | 需额外前向统计，硬件稀疏计算支持不成熟 |
| 语义合并 | 相似 token 合并（patch merging 类） | 保语义密度 | 实现复杂，位置坐标需同步处理 |
| 帧降采样（视频） | 2 FPS → 1 FPS，或限制总帧数 | 视频 token 直接减半 | 高运动/快速翻页场景漏事件 |

**工程上的主流组合**：以 `max_pixels` 为总闸（把预算从 16384×28×28 下调），视频侧用 fps/num_frames 限帧，必要时再用帧分辨率（total_pixels）二次压缩。裁剪应在**预处理阶段**完成，而不是在视觉塔前向后丢弃 token——前向算力同样被省掉。

### 4.3 裁剪的代价（精度账本）

1. **小字/细粒度**：文档、票据、OCRBench 类任务随预算下降快速掉点——小字在低分辨率下不可读；
2. **定位精度**：grounding 框的坐标精度依赖 token 网格粒度，预算过低时框的位置偏移、置信下降；
3. **幻觉**：信息不足时模型倾向"脑补"——物体存在性、计数、属性判断都变差；
4. **OOD 风险**：`min_pixels` 过大把极小图过度放大，脱离训练分布，反而损害 OCRBench（论文消融结论）；
5. **时间信息**：视频降帧会漏掉瞬时事件（翻页、动作切换）。

| 预算档位 | 建议场景 |
|---------|---------|
| 4~256 | 图标、简单示意图、图标分类 |
| 256~1280（Qwen3-VL 默认） | 通用对话、网页截图、通用图片理解 |
| 2048~4096 | 文档、票据、含小字的截图 |
| 8192~16384 | 长文档、高密度 OCR、长视频单帧 |

### 4.4 预算与像素的定量换算（裁剪的数学）

token 预算与像素预算互为反解。给定目标 token 数 $N$，像素预算为：

$$\text{max\_pixels} = N \times 784 \quad \text{（Qwen2 系，28 对齐）}$$

| 目标 token N | 对应 max_pixels | 等价分辨率（方形示例） |
|-------------|----------------|----------------------|
| 64 | $64 \times 784 = 50{,}176$ | 224×224 |
| 256 | $256 \times 784 = 200{,}704$ | 448×448 |
| 512 | $512 \times 784 = 401{,}408$ | 约 634×634 |
| 4096 | $4096 \times 784 = 3{,}211{,}264$ | 约 1792×1792 |
| 16384 | $16384 \times 784 = 12{,}845{,}056$ | 上限（默认值） |

视频侧同理：总预算固定时，**帧数与每帧 token 是反比关系**。设总预算 $B$、时域合并后时间步数 $S$（2 FPS 下 1 分钟视频 60 步），则每步预算 $b = B/S$：

$$B = 16384,\ S=60 \Rightarrow b \approx 273\ \text{token/帧（约 224² 档）};\quad B = 4096 \Rightarrow b \approx 68\ \text{token/帧（约 196² 档）}$$

这就是"总 token 预算 → 动态调帧分辨率"（Qwen2.5-VL/Qwen3-VL 视频侧）的数学：**先定总预算，再反推帧分辨率**，保证任何时长视频都落在显存上限内。

## 五、量化

### 5.1 量化什么

| 量化对象 | 机制 | 内存收益 | 多模态注意点 |
|---------|------|---------|-------------|
| LLM 权重 | BF16(2B/参数) → INT8(1B) → INT4(0.5B) | 2× / 4× | Qwen2-VL-7B 的 LLM 约 7.6B：BF16 ≈ 15.2 GB → INT8 ≈ 7.6 GB → INT4 ≈ 3.8 GB |
| KV cache | FP8 / INT8 量化 | 减半 | 长上下文场景收益最大（KV 是大头） |
| 视觉塔 | 保持 BF16/FP16 为主 | — | 675M BF16 ≈ 1.35 GB；量化敏感（见 5.2） |

### 5.2 视觉塔量化敏感性：为什么它比 LLM 更娇气

- **传导放大**：视觉特征失真会**传导**进 LLM 的整个推理链——LLM 权重量化损失的是"语言能力"，视觉塔量化损失的是"看到的画面"，而画面错误无法被语言能力弥补；
- **实测经验（理论层面）**：LLM 部分 INT8（AWQ/GPTQ 类）几乎无损；INT4 在一般任务可接受，但数学、长链推理、Thinking 模式有可见下降；KV cache INT8 在短上下文几乎无感，长上下文（>8K）下降略明显；**视觉塔 INT8 时 OCR、细粒度定位、文档解析最先掉点**——多模态精度组合拳是"LLM 可量化，视觉塔保持高精度"。

### 5.3 精度×成本的组合经验矩阵

| LLM 权重 | KV cache | 视觉塔 | 精度风险 | 建议场景 |
|---------|---------|--------|---------|---------|
| BF16 | BF16 | BF16 | 无 | 旗舰、评测基准 |
| INT8 | BF16 | BF16 | 很低 | 生产默认（性价比最高） |
| INT8 | FP8/INT8 | BF16 | 低 | 长上下文/高并发 |
| INT4 | INT8 | BF16 | 中（长链推理略降） | 显存紧张、端侧 |
| INT4 | INT8 | INT8 | 高（OCR/定位先掉） | 不推荐，除非场景不敏感 |

### 5.4 量化方案的数学与选择

**对称量化**：权重 $w$ 以缩放因子 $s$ 映射到整数：

$$w \approx s \cdot w_{\text{int}}, \qquad s = \frac{\max|w|}{2^{b-1}-1}$$

按 $s$ 的粒度分为三档：

| 粒度 | 每个 $s$ 覆盖范围 | 精度 | 实现成本 |
|------|-----------------|------|---------|
| per-tensor | 整层一个 $s$ | 最差（层内权重动态范围大） | 最低 |
| per-channel | 每输出通道一个 $s$ | 好（激活侧常用） | 低 |
| group（如 g128） | 每 128 个参数一组 | 最好 | 中 |

**GPTQ vs AWQ（校准型 vs 激活感知型）**：GPTQ 基于 Hessian 做逐层误差补偿（误差最小化）；AWQ 用激活统计识别"重要通道"并提高其精度保护。两者在多模态模型上的经验差异不大，但 **AWQ 对小模型、长尾激活（视觉 token 分布）更稳健**——视觉 token 的激活分布与文本差异大，校准数据里必须混入图像样本。

**KV cache 量化数学**：KV 量化把每 token 的 KV 内存从 $2 \times 2$ 字节（BF16）降到 $2 \times 1$ 字节（INT8），KV 总内存直接减半：

$$M_{\text{KV}}^{\text{INT8}} = \frac{1}{2} M_{\text{KV}}^{\text{BF16}}$$

16384 token 档：约 6.58 GB → 约 3.3 GB，对长文档/长视频请求是决定性收益。

## 六、显存优化组合拳

### 6.1 四条杠杆

1. **token 预算**：max_pixels / fps / 帧分辨率——同时压 KV、prefill 算力、视觉塔前向（效果最猛，但精度代价见 4.3）；
2. **量化**：LLM 权重 INT8 + KV FP8 + 视觉塔 BF16（显存减半级）；
3. **KV cache 优化**：GQA（多 query 共享 KV，Qwen 系已内置）、KV 量化、vLLM PagedAttention、多轮前缀复用（SGLang RadixAttention / vLLM prefix cache）；
4. **批量策略**：动态 batch（continuous batching）+ 按 token 数分桶，避免"长短混装"的 padding 浪费。

### 6.2 7B / 30B 部署配置示例表（纯理论示例，需按实测调整）

| 配置项 | Qwen2-VL-7B / Qwen2.5-VL-7B | Qwen3-VL-30B-A3B（MoE） |
|--------|------------------------------|-------------------------|
| LLM 权重精度 | INT8（约 8 GB） | INT8（约 30 GB；BF16 约 60 GB） |
| 视觉塔 | 675M，BF16（约 1.35 GB） | SigLIP-2 级，BF16（约 0.8 GB） |
| max_pixels | 512×28×28（约 512 token/图） | 512×28×28 |
| KV cache | FP8 量化 | FP8 量化 |
| 显存核算（单请求） | 权重 8 + 视觉塔 1.4 + KV(512 token) 0.2 + 激活 2~3 ≈ **12 GB** | 权重 30 + 视觉塔 0.8 + KV 0.2 + 激活 ≈ **33 GB+** |
| 建议显存 | 1× A100/H100 80 GB | 2× 80 GB（或 INT4 后 1× 卡） |
| 并发 batch | 4~16 | 4~8（MoE 激活仅 3B，每 token 算力省，但权重常驻多） |
| 备注 | 单卡可支撑多实例/高并发 | MoE 需注意 expert 权重装载与显存带宽 |

> 核算口径：7B 模型"权重 + 峰值 KV + 激活"约 12 GB，80 GB 卡理论可跑约 5 个独立实例或 1 个高并发服务；显存上限由**最坏情况**（16384 token 请求）决定，batch 内打包困难是多模态服务吞吐的天花板。

### 6.3 多轮图文对话的 KV 复用（前缀缓存数学）

多轮对话的典型特征：**同一张图的视觉 token 序列逐轮重复出现**（图像通常不变，只换问题文本）。若不缓存，每一轮都要重新 prefill 视觉 token，浪费：

$$M_{\text{waste}} = n_{\text{vis}} \times d \times 2 \times L \times 2 \ \text{(字节/轮)}$$

以 1080p 图（2584 视觉 token）、28 层、3584 维、BF16 为例，每轮重复 prefill 约 1 GB 的 KV 计算与 1.04 GB 显存写放——10 轮对话重复 10 次。

**解法**：前缀缓存（vLLM prefix cache / SGLang RadixAttention）按 token 序列的公共前缀复用 KV：第 1 轮算过的视觉 KV 直接命中，后续轮次只 prefill 新文本。

```text
轮 1： [img tokens (2584)][问题 1] → 全量 prefill，KV 全部写入缓存
轮 2： [img tokens (2584)] ← 命中缓存，不再 prefill；只算 [问题 2] 的 KV
```

**前提条件**：图像必须**逐 bit 相同**（预处理确定性强：同分辨率、同缩放、同切分），任何预处理随机性都会破坏前缀命中；这也是"预处理结果服务端缓存"（§7.4）的价值所在。

## 七、服务化

### 7.1 接口形态

- **OpenAI 兼容接口**（`/v1/chat/completions`）：content 中 `image_url` 支持单图/多图，视频可传帧序列；预处理（缩放/切分/占位符替换）在服务端完成；
- Qwen3-VL 双模式（Instruct / Thinking）：可通过模型标识或系统提示路由，服务端需区分两条推理配置（Thinking 的长输出见 7.5）。

### 7.2 并发与排队

- 引擎层（vLLM/SGLang）自带调度队列，但**网关层需要排队策略**：TTFT 敏感的短请求优先；长文档/视频请求进入低优先级队列，避免一个 16384 token 的 prefill 饿死其他请求；
- 队列深度 + 引擎并发 = 服务吞吐模型的完整参数；超载时优先拒绝新请求（返回 503）而不是无限排队。

### 7.3 批处理

- **按 token 数分桶**：把视觉 token 接近的请求打包（256 档、1024 档、4096 档…），避免"4 token 与 16384 token 混装"的极端 padding 浪费；
- 多模态的 batch 打包比纯文本难：视觉 token 数差异大、预处理时长差异大——因此"动态 batch + 分桶"是标配，静态 batch 基本不可用。

### 7.4 多图 / 视频请求处理

| 请求类型 | 处理要点 |
|---------|---------|
| 多图对比 | 每图独立预算；服务端限制总预算（如 4×256=1024），防止线性爆炸 |
| 视频 | 服务端抽帧（2 FPS 基准，可配 fps/num_frames），限制帧数与 total_pixels；Qwen3-VL 需插入文本时间戳 |
| 长文档截图 | 单页 ≤ 上限（16384）；超长文档按页切图分发，或多页分次请求 |

### 7.5 超时设置（Thinking 模式长推理链）

- Qwen3-VL **Thinking 版**在推理时输出长思维链（CoT），一次请求可能生成数万 token——传统 30~60s 的超时必然超时；
- 对策：① 客户端/网关超时放宽到 300s+ 或按"token 速率×预算"动态计算；② **优先流式输出**（SSE），逐 token 到达，客户端不感知超时；③ 路由层区分 Thinking 与非 Thinking 请求，Thinking 走长超时池；
- 配套：Thinking 请求的并发预算要单独核算（长输出占住 KV 与解码带宽）。

### 7.6 高可用与容错

| 组件 | 风险 | 对策 |
|------|------|------|
| 引擎实例 | 单点故障、OOM 崩溃 | 多副本 + 无状态化（KV 缓存放引擎内，可重建）；健康检查探活（/health） |
| 显存 | 长请求 OOM 拖垮整实例 | 按最坏情况定容 + 并发上限；超限请求降级（降预算重试或返回 429） |
| 预处理 | 切分/占位符替换出错 | 预处理结果确定性 + 结果缓存（同时利于 KV 前缀命中） |
| 模型更新 | 灰度风险 | 新模型版本与旧版本并行，按流量比例灰度，用评测集回归 P95/QPS/精度 |
| 客户端 | 重试风暴 | 指数退避 + 幂等；对 429/503 不无限重试 |

## 八、性能基准测试方法

### 8.1 对比实验设计表

| 变量 | 取值 |
|------|------|
| 推理引擎 | HF Transformers / vLLM / SGLang |
| 精度 | BF16 / INT8 / INT4 / KV-INT8 组合 |
| 分辨率/token 预算 | 256 / 1024 / 4096 / 16384 |
| 输入类型 | 纯文本 / 单图 / 多图 / 视频 |
| 并发 | 1 / 4 / 16 / 64 |
| 输出长度 | 固定 max_tokens（如 256），保证可比 |

**方法**：控制变量，每组 ≥100 请求取 P50/P95（长尾数据用 P95，不要用均值）；指标 = {TTFT, TPOT, P95, QPS, 显存峰值}；同组请求的输入 token 数必须一致（多模态下尤其要固定图像与文本长度）。

### 8.2 视觉部分单独测

- **单图 prefill 时间**：固定 prompt、固定图，仅 prefill（max_tokens=1 或流式首 token），测 TTFT——它包含"视觉塔前向 + 压缩投影 + LLM prefill"三段，是纯文本没有的开销；
- 扫描分辨率：256 / 1024 / 4096 预算下 TTFT 的增量曲线，用来标定"token 预算 ↔ 延迟"的换算；
- 视频：固定总 token，扫描帧数（帧数 ↑ → 每帧 token ↓），观察 TTFT 与召回率的折线；
- 拆分观测：分别计时视觉塔前向与 LLM prefill（可用 profiler 打点），定位瓶颈在 ViT 还是 LLM。

### 8.3 负载测试与端到端

- 并发扫描：1 → 4 → 16 → 64，画 **QPS-P95 曲线**（吞吐上升、延迟恶化存在拐点，拐点即服务容量）；
- 长尾检查：混合负载（10% 长文档 + 90% 短图）下 P95 是否被长请求拉爆——这正是多模态服务要分桶的原因；
- 显存观测：峰值显存随并发的变化曲线，用于定容（避免 OOM 级联）。

### 8.4 数据口径与报告模板

| 口径项 | 约定 |
|--------|------|
| 延迟定义 | TTFT = 请求入队 → 首 token；TPOT = 输出间隔；两者分开报，不混为"总延迟" |
| 分位数 | P50/P95 必报，P99 选报；**不用均值** |
| 输入固定 | 同组对比必须固定图像尺寸/预算/文本长度/输出长度（max_tokens 一致） |
| 预热 | 引擎 warmup 后再测（显存分配、算子 JIT 在首请求触发） |
| 样本量 | 每组合格请求 ≥100（并发 64 时取 1000+） |
| 冷热分离 | 前缀缓存命中率作为独立指标上报（多轮对话场景） |

**报告模板（示意）**：

```text
场景: Qwen2.5-VL-7B / vLLM / INT8+KV-FP8 / 1080p 图 / 预算 1024 / 并发 16
TTFT: P50 420ms / P95 780ms     TPOT: P50 28ms / P95 41ms
QPS: 38.2                       显存峰值: 23.4 GB / 80 GB
前缀命中率: 0%（首轮）/ 92%（多轮）     结论: 容量拐点位于并发 32
```

## 九、高频面试问答

**Q1：多模态推理为什么显存比纯文本大？**
三块叠加：① 视觉塔权重与激活（675M ViT 前向）；② 视觉 token 数量大（1080p 约 2584 token vs 文本几百），KV cache = 2×L×n×d×2B 线性放大；③ 单图上限 16384 token 的"最坏情况"决定了显存规格，batch 打包困难。

**Q2：视觉 token 裁剪有哪些手段？**
分辨率上限（max_pixels，从源头控制）、均匀采样、注意力分数裁剪（保留 top-k）、语义合并、视频帧降采样（2 FPS→1 FPS 或限制帧数）。工程主力是 max_pixels + fps/num_frames，裁剪要在预处理阶段做，才能同时省前向算力。

**Q3：vLLM 为什么快？**
两个机制：PagedAttention（KV 按 16 token 块分页、页表映射，消除内部/外部碎片，同显存容纳更多序列）和 continuous batching（迭代级调度，完成即退、新请求即入，避免静态 batch 的 GPU 空转）。多模态场景下长 prefill 请求可与短请求穿插调度。

**Q4：量化对多模态模型影响如何？**
LLM 权重 INT8 几乎无损、INT4 在长链推理/Thinking 有可见下降；KV cache INT8 长上下文略降；**视觉塔最敏感**——特征失真传导进 LLM 整条链，OCR、定位、细粒度先掉点，因此视觉塔保持 BF16/FP16。推荐组合：LLM INT8 + KV FP8 + 视觉塔 BF16。

**Q5：为什么 P95 比平均延迟重要？**
多模态输入长度方差极大（4~16384 token），长尾请求的延迟可能是中位数的数倍；均值被多数短请求稀释，掩盖长文档/视频请求的体验灾难。SLA 以 P95（甚至 P99）为准。

**Q6：多模态的 TTFT 为什么高？怎么优化？**
视觉 token 全量参与 prefill（attention O(n²)）+ 视觉塔前向。优化：降 token 预算（最有效）、flash-attention、chunked prefill、多轮对话复用视觉 KV（RadixAttention/prefix cache）。

**Q7：16384 token 的长文档请求部署要注意什么？**
单序列 KV ≈ 6.58 GB（28 层 3584 维 BF16），朴素 prefill 分数矩阵约 15 GB——必须 flash-attention；建议 KV 量化、降预算或按页切图；并放入低优先级队列避免拖垮并发。

**Q8：Qwen3-VL Thinking 模式部署要注意什么？**
长思维链输出可达数万 token：超时放宽到 300s+ 或按 token 速率动态计算，优先流式输出（SSE），Thinking 与非 Thinking 分路由、分开核算并发预算。

**Q9：怎么测视觉部分的性能？**
固定输入测 TTFT（含视觉塔前向+压缩+LLM prefill），扫描 token 预算画 TTFT 增量曲线，视频扫描帧数；用 profiler 拆分视觉塔与 LLM 前向耗时定位瓶颈。

**Q10：一张 80 GB 卡能撑多大并发？**
按"权重 + 峰值 KV + 激活"核算：7B INT8 ≈ 12 GB/请求基准，理论可并发多个，但 16384 token 的最坏情况与动态 batch 决定实际容量——必须用 QPS-P95 曲线实测拐点，不能拍脑袋。

## 十、常见误区

**误区 1：视觉 token 越多模型越准。**
不成立。超过训练分布后边际收益为零甚至为负（OOD）；成本却是 KV 线性、prefill 平方增长。精度要用 benchmark 测，token 预算要用显存算。

**误区 2：量化直接无脑上 INT4。**
多模态的视觉塔量化风险远高于 LLM 权重量化——OCR/定位先掉点，且 INT4 对长链推理（Thinking）有可见下降。正确姿势是分模块量化：LLM 可量化、视觉塔保持高精度。

**误区 3：显存只算权重。**
多模态峰值 = 权重 + KV（视觉 token 大头）+ 激活 + 视觉塔特征；16384 token 单序列 KV ≈ 6.58 GB，远超直觉。

**误区 4：平均延迟够用，不用管 P95。**
多模态输入长度方差极大，均值掩盖长尾；SLA 必须按 P95/P99 设计，混合负载下长请求会拉爆整批。

**误区 5：vLLM 开箱即满分。**
引擎解决的是 KV 管理与批处理，token 预算、分桶策略、视觉塔精度、超时设置仍需按多模态特性调优；不同版本对 Qwen3-VL 新特性（DeepStack、时间戳、双模式）的支持程度不同，选型要核对版本。
