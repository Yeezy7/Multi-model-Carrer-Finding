# Qwen3.5-Omni：Hybrid Attention MoE、256K 上下文与原生 Omni Agent

> 本系列索引见 [00_Omni系列演进总览](00_Omni系列演进总览.md)

> 本笔记覆盖 Qwen3.5-Omni 的完整技术剖析（论文 arXiv:2604.15804，2026 年发布，目前以 API 形式提供 Plus / Flash 两个变体）。这一代把 Omni 系列推向规模化：Thinker 与 Talker 双双换装 Hybrid Attention MoE、上下文拉到 256K（10 小时以上音频、400 秒 720P 视频）、训练数据超 1 亿小时音视频，并引入 ARIA 文本-语音对齐、MTP 逐帧残差码本预测、脚本级结构化字幕、零样本音色定制与原生 omni agent。面试被问"ARIA 是什么""Hybrid Attention MoE 是什么""10 小时音频怎么存""Vibe Coding 是什么"时，本篇是完整答案。

## 二、相对 Qwen3-Omni 的五大升级点

### 2.1 升级总览表

| # | 升级点 | Qwen3-Omni | Qwen3.5-Omni |
|---|--------|-----------|--------------|
| ① | 主干架构 | Thinker 用标准 MoE；Talker 为轻量分支 | **Thinker 与 Talker 均用 Hybrid Attention MoE** |
| ② | 上下文 | 流式长音频（单实例 40 分钟） | **256K 原生**（10h+ 音频、400s 720P@1FPS） |
| ③ | 文本-语音对齐 | 隐式对齐（Talker 直接吃 Thinker 表示） | **ARIA 显式动态对齐** |
| ④ | 语音合成 | RVQ codec + 因果 ConvNet | **MTP 逐帧残差码本 + Code2Wav 逐帧合成** |
| ⑤ | 语言与音色 | 19 理解 / 10 生成 | **113 识别 / 36 合成 + 零样本音色定制** |

### 2.2 升级一：Thinker/Talker 均采用 Hybrid Attention MoE

**为什么长序列下标准注意力不够用**：注意力是 $O(n^2)$ 复杂度；256K 上下文 + 音频/视频长序列下，KV cache 与计算双双爆炸。MoE 解决了 FFN 的稀疏化，但注意力仍然是瓶颈。

**Hybrid Attention MoE = 两件事的混合**：

| 层面 | 设计 | 收益 |
|------|------|------|
| 注意力混合 | 关键 token（如系统指令、问题、说话人标识）走全局密集注意力保语义，长序列的其余部分走稀疏/局部注意力 | 计算从 $O(n^2)$ 压向近线性，KV cache 更小 |
| 专家混合 | FFN 层用 MoE 稀疏激活（延续 A3B 思路） | 算力按激活参数花 |

**为什么 Talker 也要换**：语音生成面对的是逐帧的 codec 序列，长对话下 Talker 的序列可能长达数万帧——Talker 同样需要高效长序列推理，所以这次是"双 MoE"。

**注意力机制的三种形态对比**：

| 形态 | 复杂度 | 长程语义 | 适用 |
|------|--------|----------|------|
| 全密集注意力 | $O(n^2)$ | 最强 | 短序列、关键 token |
| 纯稀疏/局部注意力 | 近线性 | 弱（远距离依赖丢失） | 超长但语义均匀的序列 |
| **混合注意力（Hybrid）** | 关键 token 密集 + 其余稀疏 | 在关键位置保全局 | **长序列多模态推理** |

Hybrid 的设计哲学：**"钱"（注意力预算）花在少数真正重要的 token 上**——问题、指令、说话人、话题词全量关注，流水般的音频/视频帧做局部关注，两全其美。

### 2.3 升级二：256K 原生上下文

| 能力 | 数值 |
|------|------|
| 上下文窗口 | **256K** |
| 音频 | **10 小时以上**（整段输入） |
| 视频 | **400 秒 720P，1 FPS 采样**（400 帧） |

**10 小时音频怎么"放得下"**（token 账本）：

- AuT 每帧约 80ms → 12.5 帧/秒 → 10 小时 ≈ 45 万帧；
- 45 万帧 × 每帧 1 token 远超 256K，因此必须有**帧级压缩**：相邻帧池化合并（一个 token 覆盖更长的音频段）+ 长序列流式管理（早期帧摘要化），最终把 10 小时音频压进上下文（详见面试 Q3）。

**视频侧账本**：400 秒 @ 1 FPS = 400 帧；每帧再经视觉 token 压缩（patch 合并）与关键帧筛选，整段视频以数百~数千 token 级别进入上下文，与音频轨道联合建模。

**256K 能力的来源**：上下文不是"事后拉长"，而是在训练阶段就按 256K 序列长度做长上下文训练（延续 Qwen3-VL 的长序列路线），再叠加 Hybrid Attention 减小 KV cache，才能让"超长输入"既是能力、又付得起推理成本。

### 2.4 升级三：ARIA（重点）

#### 2.4.1 问题背景：文本与语音 tokenizer 的编码率不匹配

| tokenizer | 编码率特征 |
|-----------|-----------|
| 文本（Qwen 分词） | 一个 token ≈ 1 个中文字或一个英文词片，**长度不固定** |
| 语音（AuT 帧 / codec） | **固定帧率**（每帧 ≈ 80ms，12.5 帧/秒），帧长恒定 |

生成语音时，模型要把"文本单元"映射成"语音单元"。如果按固定比例（如 1 个文本 token = 固定数量的语音帧）强行对齐：

| 后果 | 表现 |
|------|------|
| 漏词 | 文本被"挤掉"——快语速下某些字没生成出来 |
| 错音 | 文本与语音单元错位，音素张冠李戴 |
| 数字读错 | "12345" 的分词与口语读数（"一万两千三百四十五"）长度不匹配 |
| 韵律生硬 | 停顿、重音无法落在正确的语义位置 |

根因：**一个文本 token 对应几个语音帧是动态的（取决于读音、语速、连读），固定映射必然错位**。

**为什么 Qwen3-Omni 时代不明显、现在必须解决**：Qwen3-Omni 的 Talker 直接吃 Thinker 的语义表示，对齐是"隐式"的——短句、低速场景够用；但当 256K 上下文让句子变长、语速变快、多语言（113 语种）引入大量发音长度差异时，隐式对齐的错位率被放大，必须把对齐"显式化"。

#### 2.4.2 ARIA 机制：Adaptive Rate Interleave Alignment

```text
文本单元:   T1 ──► 生成 3 帧    T2 ──► 生成 2 帧    T3 ──► 生成 4 帧 ...
语音单元:   [S1 S2 S3]         [S4 S5]             [S6 S7 S8 S9] ...
            （动态决定每个文本单元对应多少语音帧，交错成联合序列生成）
```

1. **自适应率（Adaptive Rate）**：解码过程中动态决定"当前文本单元该生成几个语音帧"，依据是已生成的语音与剩余文本的语义匹配度；
2. **交错（Interleave）**：把文本单元与语音单元交错成一个联合序列一起建模，而不是"先生成全部文本、再按比例摊派语音"。

#### 2.4.3 效果

| 维度 | 改善 |
|------|------|
| 准确率 | 漏词、错音、数字读错显著减少 |
| 自然度 | 停顿/重音落在语义正确的位置，韵律更自然 |
| 长句 | 长句、快语速场景下稳定性明显提升 |

### 2.5 升级四：MTP + Code2Wav 逐帧流式合成

| 模块 | 职责 |
|------|------|
| **MTP** | 每一帧一次前向，并行预测该帧的**全部残差码本**（帧内并行、帧间自回归） |
| **Code2Wav** | 拿到当前帧全部 code 后**逐帧合成波形**（single-frame immediate synthesis） |

```text
帧 t:  MTP 一次前向 ──► 预测 [c₁ c₂ … c_K]（本帧全部残差码本）
                          │
                          ▼
              Code2Wav 逐帧合成 ──► 本帧波形（≈80ms）──► 立即播放
```

对比 Qwen3-Omni：

| 维度 | Qwen3-Omni | Qwen3.5-Omni |
|------|-----------|--------------|
| 码本预测 | 逐码本顺序预测 | **MTP 帧内一次前向出全部残差码本** |
| 波形合成 | 因果 ConvNet 逐帧 | Code2Wav 逐帧（流水线化） |
| 流式粒度 | 帧级 | **帧级（即时合成、无需整句/整块缓冲）** |

### 2.6 升级五：多语言扩展与零样本音色定制

| 能力 | Qwen3-Omni | Qwen3.5-Omni |
|------|-----------|--------------|
| 语音识别语种 | 19 | **113（语言与方言）** |
| 语音合成语种 | 10 | **36** |
| 音色定制 | 无 | **零样本：用户样本 → 克隆音色** |

**零样本音色定制**：用户给几秒~几十秒的样本，模型提取说话人表征并注入 Talker，即可用"用户的声音"说任意内容——不需要微调，不改变文本内容控制，内容与韵律仍由模型生成。

流程（三步）：

```text
1. 用户提供参考样本（几秒~几十秒语音）
   ↓
2. 模型提取说话人表征（音色/口音/语速风格向量）
   ↓
3. 注入 Talker：任意新内容以该音色流式合成
```

应用：个人语音助理、有声书/播客定制、游戏角色配音、多语言"用我的声音说话"（跨语种音色迁移）。

## 三、能力（重点）

### 3.1 脚本级结构化音视频字幕

| 维度 | 普通字幕 | 脚本级结构化字幕 |
|------|----------|------------------|
| 时间同步 | 句级粗时间 | **精确时间同步**（逐句/逐词时间戳） |
| 场景 | 无 | **自动场景分割**（scene segmentation） |
| 输出 | 纯文本行 | **结构化脚本**（时间戳 + 说话人 + 场景段） |

典型输出形态：

```text
[场景 1 · 0:00:00 - 0:00:12 · 办公室]
[说话人 A] 这个版本我们周五必须上线（0:00:01.2）
[说话人 B] 测试用例还没跑完（0:00:05.8）
[场景切换 · 0:00:12 · 会议室]
```

用途：会议纪要、播客脚本化、影视逐字稿、内容检索（按说话人/场景/时间点定位）。

### 3.2 Audio-Visual Vibe Coding

**Vibe Coding**：用自然语言描述"想要什么"，让模型直接产出代码/应用。**Audio-Visual Vibe Coding** 把输入从纯文本扩展到音视频：

| 输入形态 | 例子 |
|----------|------|
| 口述需求（音频） | "帮我写一个记录每日饮水的网页应用" |
| 语音 + 屏幕录制（音视频） | 边演示原型边说需求 → 生成对应代码 |
| 语音 + 示意图 | 指着图描述布局 → 生成页面 |

意义：编程入口从"键盘打字"扩展到"开口说话 + 视觉演示"，降低工具使用门槛。

### 3.3 原生 omni agent

| 能力 | 说明 |
|------|------|
| WebSearch | 实时联网检索（边搜边答） |
| FunctionCall | 调用外部函数/API（查天气、订票、操作工具） |
| 语音输出 | 结果直接以语音回报，无需转文字再读 |
| 实时流式交互 | 边说边想、边说边调工具，打断可恢复 |

一句话：**Qwen3.5-Omni 不再是"问答模型"，而是"带耳朵、带嘴、会查资料、会调工具的 agent"**。

### 3.4 超长输入的实际场景

| 输入 | 典型场景 | 技术支撑 |
|------|----------|----------|
| 10 小时音频 | 全天会议纪要、播客/有声书整本理解、长录音转脚本 | 256K + 帧级压缩 |
| 400 秒视频（1 FPS） | 长视频内容审核、课程讲解理解、影视片段分析 | 256K + 视觉 token 压缩 |
| 音视频同步 | 字幕生成、说话人区分、场景切换检测 | 音视频联合建模 |

### 3.5 数据：规模化从哪里来

| 数据 | 用途 |
|------|------|
| 异构图文对 | 视觉与图文对齐能力（继承 VLM 路线） |
| **超 1 亿小时音视频内容** | 语音识别/合成、跨模态对齐、音视频联合理解 |

规模化数据的价值：语音语种 19 → 113、36 语种合成、零样本音色定制、超长音频稳定性，本质都是"数据堆出来的能力"。

## 四、评测

### 4.1 评测规模

| 指标 | 数值 |
|------|------|
| 评测子任务与 benchmark | **215 个**（音视频理解 / 推理 / 交互） |
| Plus 版本 | 全部主要榜单 SOTA |
| 与闭源对比 | 部分音频任务**超越 Gemini-3.1 Pro** |

### 4.2 能力分组

| 组 | 代表任务 | 表现 |
|----|----------|------|
| 音视频理解 | 长视频问答、音视频联合推理 | SOTA |
| 语音识别/合成 | 113 语种 ASR、36 语种 TTS | SOTA（部分超越 Gemini-3.1 Pro） |
| 交互 | 实时语音对话、打断、角色扮演 | SOTA |
| 结构化输出 | 脚本级字幕、场景分割 | SOTA |
| Agent | 工具调用、联网检索 | 原生能力，端到端评测 |

### 4.3 为什么是"215 个子任务"

评测采用"benchmark → 子任务"的拆解粒度：一个 benchmark（如某音视频问答集）按数据集、语种、难度、输入类型拆成多个子任务分别计分，避免"平均分掩盖短板"。

| 评测层次 | 含义 |
|----------|------|
| Benchmark | 公开数据集/榜单（约数十个） |
| **子任务** | 按维度拆解后共 **215 个** |
| 结论 | Plus 在 215 个子任务上整体 SOTA；部分音频任务超越 Gemini-3.1 Pro |

## 五、产品形态

### 5.1 Plus 与 Flash

| 变体 | 定位 | 适合场景 |
|------|------|----------|
| **Plus** | 旗舰：数百亿参数、能力最强 | 复杂推理、长文档/长音视频、Agent、脚本字幕 |
| **Flash** | 快速：低延迟、低成本 | 高频语音交互、实时对话、成本敏感场景 |

### 5.2 部署方式

| 方式 | 说明 |
|------|------|
| API（DashScope） | Plus / Flash 按需调用，含流式语音交互 |
| 场景选型 | 按"延迟敏感度 × 能力需求 × 成本预算"三轴选择 |

### 5.3 变体差异要点

| 维度 | Plus | Flash |
|------|------|-------|
| 能力 | 旗舰（复杂推理/长音视频/Agent） | 够用（对话/转写/短任务） |
| 延迟 | 相对较高（推理更深） | 低（适合实时语音交互） |
| 成本 | 较高 | 低（高频调用友好） |
| 典型场景 | 脚本字幕、Vibe Coding、长内容理解 | 客服机器人、口语陪练 |

### 5.4 场景选型建议

| 场景 | 建议 |
|------|------|
| 客服语音机器人（高并发） | Flash |
| 会议纪要 + 长音频脚本化 | Plus |
| 口述编程 / Vibe Coding | Plus |
| 实时口语陪练 | Flash（低延迟优先） |
| 音视频内容理解与检索 | Plus |

### 6.1 关键维度逐条详解

| **架构** | 标准 MoE → Hybrid Attention MoE（双份） | 长序列下注意力不再是瓶颈，256K 才"付得起" |
| **上下文** | 流式 40 分钟 → 256K 整段 | 从"边放边记"到"整段理解+全局检索" |
| **数据** | 2000 万小时音频 → 1 亿小时音视频 | 语种、音色、长音频稳定性的来源 |
| **语言** | 19/10 → 113/36 | 低资源语言能力来自数据规模化 |
| **延迟** | 帧级流式 → MTP 逐帧即时合成 | 冷启动与逐帧延迟继续下探 |
| **能力** | 问答为主 → 结构化输出 + Agent | 从"模型"走向"生产力工具" |

---

## 七、趋势总结

1. **全模态 agent 化**：模型从"问答"走向"带耳朵、带嘴、会调工具的 agent"（WebSearch、FunctionCall、语音输出一体化）。下一代竞争的主战场不再是"能听能说"，而是"听完说完之后能做什么"；
2. **Vibe Coding 落地**：音视频指令直接生成代码，"编程入口"从键盘扩展到语音与视觉。口述需求 + 屏幕演示就能产出应用，软件生产方式本身在被改写；
3. **流式低延迟**：MTP + Code2Wav 逐帧即时合成，冷启动与逐帧延迟持续压向人耳无感（300ms 以内是体验分水岭），实时语音交互成为默认形态而非附加功能；
4. **长上下文与长音频**：256K 原生 + 帧级压缩，10 小时音频整段理解成为标配；"听得完整"是会议纪要、长内容理解、影视分析等生产力场景的前提；
5. **规模化数据**：1 亿小时音视频 + 异构图文对，"数据即能力"——语音语种从 19 → 113、音色零样本克隆、长音频稳定性，全部是数据规模换来的；Omni 模型的军备竞赛正在从"架构创新"转向"数据 + 工程"。

## 八、高频面试问答

**Q1：ARIA 是什么？解决了什么问题？**
Adaptive Rate Interleave Alignment（自适应率交错对齐）。问题：文本 tokenizer（变长编码）与语音 tokenizer（固定帧率，≈80ms/帧）编码率不匹配，固定映射导致漏词、错音、数字读错。ARIA 在解码时动态决定每个文本单元生成几个语音帧，并把文本/语音单元交错成联合序列建模，显著减少上述错误、韵律更自然。

**Q2：Hybrid Attention MoE 是什么？**
混合注意力 + 稀疏专家：注意力层面把关键 token 的全局密集注意力与长序列的稀疏/局部注意力混合，把 $O(n^2)$ 压向近线性并减小 KV cache；FFN 层面延续 MoE 稀疏激活。这次 Thinker 与 Talker 都换装——因为 Talker 也要处理数万帧的 codec 长序列。

**Q3：10 小时音频怎么存进 256K 上下文？**
账本：80ms/帧 → 12.5 帧/秒 → 10 小时 ≈ 45 万帧，直接逐帧转 token 必然超 256K。做法：帧级压缩（相邻帧池化合并，一个 token 覆盖更长音频）+ 长序列流式管理（早期帧摘要化/滑窗），把 10 小时音频压进 256K；视频同理（400 秒 @1FPS = 400 帧 + 视觉 token 压缩）。

**Q4：Vibe Coding 是什么？**
用自然语言描述需求、让模型直接生成代码的编程方式。Audio-Visual Vibe Coding 把输入扩展到音视频：口述需求、语音 + 屏幕录制、语音 + 示意图都能直接产出代码，降低编程门槛。

**Q5：MTP 和 Code2Wav 是什么关系？**
MTP 负责"预测"：每一帧一次前向并行输出该帧全部残差码本（帧内并行、帧间自回归）；Code2Wav 负责"合成"：拿到当前帧全部 code 后逐帧合成波形（single-frame immediate synthesis）。两者流水线化实现帧级流式输出。

**Q6：零样本音色定制怎么做？**
用户提供几秒~几十秒的样本，模型提取说话人表征注入 Talker 合成过程，即可克隆音色说任意内容；无需微调，内容与韵律仍由模型控制。

**Q7：113 种语音识别语种怎么做到的？**
核心是数据：超 1 亿小时音视频训练数据（含大量低资源语言/方言成对数据）+ 异构图文对；语音语种从 19 → 113 是数据规模化带来的能力扩展，也依赖 AuT 编码器的多任务预训练。

**Q8：脚本级字幕和普通字幕有什么区别？**
普通字幕是句级粗时间文本行；脚本级字幕带精确时间同步（逐句/逐词时间戳）+ 自动场景分割 + 说话人标签，输出结构化脚本，可用于检索、纪要、影视逐字稿。

**Q9：Plus 和 Flash 怎么选？**
Plus 旗舰（数百亿参数、能力最强）适合复杂推理、长音视频、Agent、脚本字幕；Flash 快速低成本适合高频语音交互与成本敏感场景。按"延迟 × 能力 × 成本"三轴选型。

**Q10：原生 omni agent 意味着什么？**
模型原生支持 WebSearch、FunctionCall、语音输出与实时流式交互——能边听边想、边说边调工具，无需外部编排系统拼装；这是"全模态 agent 化"趋势的核心体现。

## 九、常见误区

**误区 1：ARIA 是一个新的语音合成模型。**
错。ARIA 是**对齐机制**（自适应率交错对齐），解决文本/语音 tokenizer 编码率不匹配导致的漏词、错音、数字读错；语音合成仍由 MTP + Code2Wav 完成。

**误区 2：Hybrid Attention MoE = 稀疏注意力。**
错。是"混合"：关键 token 仍走全局密集注意力（保语义与长程依赖），长序列其余部分走稀疏/局部注意力，再叠加 MoE 稀疏 FFN。

**误区 3：256K 上下文 = 把 10 小时音频逐帧塞进模型。**
错。80ms/帧原始序列远超 256K，必须经过帧级压缩与流式管理；256K 是"压缩后的表示"能容纳的窗口。

**误区 4：零样本音色定制 = 完全复刻用户声音。**
部分对。克隆的是**音色与风格**，内容、韵律、情绪由模型生成控制；"零样本"指无需微调，只需几秒样本。

**误区 5：MTP 是并行生成整段语音。**
错。MTP 只在**帧内**并行预测全部残差码本，**帧间仍是自回归**——否则无法流式；"逐帧流式"正是靠帧间自回归 + 帧内并行实现的。
