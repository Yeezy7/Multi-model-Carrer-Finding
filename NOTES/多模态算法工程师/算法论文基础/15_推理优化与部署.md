# 多模态模型推理优化与部署：量化、引擎、显存与服务化的完整工程地图

> 本笔记面向"多模态算法工程师"的部署落地面试。模型训练好只是第一步，面试官真正关心的是：**你怎么把它跑起来、跑得快、跑得稳、扛得住并发**。覆盖：性能指标体系、精度压缩（量化）、推理引擎（ONNX/TensorRT/vLLM）、显存优化、服务化部署、多模态特有优化、验收报告与常见误区，全部为纯理论讲解。

---

## 一、部署目标与指标体系（重点）

### 1.1 一句话总览

> **部署优化的本质 = 在显存上限内，用尽量少的延迟、尽量高的吞吐，把模型稳定地跑在 GPU 上，并满足并发场景下的服务质量（SLO）。**

多模态模型（视觉塔 + 投影层 + LLM）部署难度高于纯文本 LLM：输入侧是**上万 token 的图像序列**，视觉塔与 LLM 的异构计算特征叠加，显存与延迟压力都更大。

### 1.2 核心指标定义表

| 指标 | 英文 | 定义 | 单位 | 关注者 |
|------|------|------|------|--------|
| 平均延迟 | Latency (mean) | 单请求端到端耗时均值 | ms/s | 开发 |
| 分位延迟 | P50 / P95 / P99 | N 次请求延迟升序后 50%/95%/99% 分位值 | ms | 运维、SLO |
| 首 token 延迟 | TTFT | 请求到达服务端到收到第一个输出 token | ms | 用户体验 |
| 单 token 延迟 | TPOT | 相邻两个输出 token 的间隔（decode 每步耗时） | ms/token | 流式体验 |
| 端到端延迟 | E2E Latency | 完整生成一个回答的总时间 | s | 业务 |
| 吞吐（token） | TPS | 单位时间生成的 token 总数 | tokens/s | 成本、容量 |
| 吞吐（请求） | QPS | 单位时间完成的请求数 | req/s | 容量规划 |
| 并发 | Concurrency | 同时"在途"（inflight）的请求数 | 个 | 资源规划 |
| 显存峰值 | Peak Memory | 推理过程显存占用最大值 | GB | 容量规划 |
| 利用率 | GPU Utilization | GPU 计算/带宽资源被利用的比例 | % | 成本 |
| Goodput | 有效吞吐 | 剔除超时、错误后的有效请求吞吐 | req/s | SLO 评审 |

### 1.3 指标之间的关系（数学上必须讲清）

端到端延迟与 TTFT / TPOT 的关系：$L_{e2e} = \text{TTFT} + \text{TPOT} \times (n_{out} - 1)$，$n_{out}$ 为输出 token 数。**TTFT 由 prefill 阶段决定，TPOT 由 decode 阶段决定**，两者对应不同优化目标（见第二十章）。

吞吐与延迟通过**并发**联系起来（Little's Law）：$N = \lambda \times W$，$N$ 为在途请求数（并发）、$\lambda$ 为请求到达率（≈ QPS）、$W$ 为平均驻留时间（≈ 平均端到端延迟）。**考点**：并发、QPS、延迟三者不能独立设计——给定 QPS 与延迟目标，并发需求 $N = \lambda W$ 即确定；而 GPU 能撑起的并发受显存（KV cache）约束，这是 PagedAttention 存在的意义。

TPS 与 QPS 换算：$QPS \approx \dfrac{TPS}{\bar{n}_{out}}$。**只看 QPS 不看输出长度是常见指标陷阱**：输出长度翻倍，QPS 可能腰斩但 TPS 没变。

### 1.4 为什么 P95 / P99 比平均延迟重要

- 平均延迟被少数极快请求拉低，**掩盖尾部劣化**，而用户体验由最慢的那批请求决定；
- 分布式链路中尾延迟叠加放大（k 个独立环节每环节 P99 为 p，整体 P99 ≈ 1 - (1-p)^k），且生产 SLO 通常直接以分位定义（如"P95 < 3s"）。**只报平均延迟不报分位是外行行为**。

## 二、性能指标的测量与基准测试设计（重点）

### 2.1 测量六条纪律

1. **预热（Warmup）**：先跑 50~100 次再计时（GPU 频率爬升、CUDA context、缓存未命中会污染数据）；
2. **固定输入与序列长度**：延迟测试用固定输入（同一批图 + 同 prompt）；输入/输出长度对 KV cache 与计算量影响巨大，必须固定并注明；
3. **控制批大小**：延迟用 batch=1；吞吐扫 batch {1,4,8,16,32,64}；
4. **足量样本 + 锁定环境**：每项 ≥ 200 次（生产 ≥ 1000）取分位数；GPU、驱动、CUDA、cuDNN、引擎版本全部记录，否则对比无效。

### 2.2 基准测试设计表（直接可复用）

| 设计维度 | 延迟测试 | 吞吐测试 | 说明 |
|----------|----------|----------|------|
| 批大小 | 固定 1 | 扫描 {1,4,8,16,32,64} | batch=1 代表单用户感知 |
| 并发 | 1（串行） | 负载工具按 λ 注入 | 并发 ≠ 批大小 |
| 输入/输出长度 | 固定（如 256/1024/4096；64/128/512） | 同左 | 视觉 token 数也要固定 |
| 预热/样本/指标 | 100 次 / ≥500 / TTFT·TPOT·E2E | 100 次 / ≥500 / TPS·QPS·显存 | 取 P50/P95/P99，控制变量法 |

**TTFT/TPOT 测法**：记录请求发起时刻 $t_0$ 与首 token 到达时刻 $t_1$，$\text{TTFT} = t_1 - t_0$；相邻 token 到达时间差的中位数即 TPOT。注意区分**服务端指标**（引擎日志，反映引擎能力）与**客户端指标**（含网络往返，反映用户体验）——引擎对比用前者，验收用后者。

### 2.3 吞吐-延迟曲线（必画的一张图）

对每个 batch 大小测一点，横轴吞吐（TPS）、纵轴 P95 延迟，曲线呈"近线性段 → 拐点（knee）→ 陡升段"：

- **近线性段**：batch 变大，权重读取被摊薄，吞吐上涨但延迟缓慢上升——红利区；
- **拐点之后**：batch 太大，排队/计算时间暴涨，P95 指数式恶化；
- **部署目标**：工作点选在拐点左侧，留 20~30% 余量应对突发流量。

## 三、精度压缩总览：为什么量化可行（重点、非常详细）

### 3.1 量化的定义

**量化（Quantization）**：用低精度数值（INT8/INT4/FP8/BF16）近似表示 FP32，换取显存减半/减 1/4 与计算加速：

$$q = \text{round}\left(\frac{r - z}{S}\right), \qquad r \approx S \cdot (q - z)$$

- $r$：原始浮点值；$q$：量化整数；$S$：缩放因子（scale）；$z$：零点（zero point）。
- **对称量化**：$z=0$，$S = \dfrac{\max|x|}{2^{b-1}-1}$（INT8 分母 127）；**非对称量化**：$S = \dfrac{x_{max}-x_{min}}{2^b-1}$（INT8 分母 255）。
- **量化误差**：每元素舍入误差不超过半步长 $\|\hat{x}-x\|_\infty \le \dfrac{S}{2}$；相对满量程信号约 $\dfrac{1}{2(2^b-1)}$，INT8 约 0.2%~0.4%，INT4 约 3%。

### 3.2 数值格式全景表（必背）

| 格式 | 符号/指数/尾数 | 相对精度 | 动态范围 | 显存（7B 模型） |
|------|----------------|----------|----------|-----------------|
| FP32 | 1/8/23 | ~2⁻²³ ≈ 1.2e-7 | 10⁻³⁸ ~ 10³⁸ | 28 GB |
| FP16 | 1/5/10 | ~2⁻¹¹ ≈ 4.9e-4 | ±65504 | 14 GB |
| BF16 | 1/8/7 | ~2⁻⁸ ≈ 3.9e-3 | 同 FP32 | 14 GB |
| INT8 | — | 256 级 | [-127,127] | 7 GB |
| INT4 | — | 16 级 | [-7,7] | 3.5 GB |

**要点**：FP16 尾数多但动态范围小（易溢出）；BF16 指数位与 FP32 相同（不溢出）、尾数少，是现代大模型推理标准格式；FP8 分 E4M3（精度高，前向）与 E5M2（范围宽，反向）两种。

### 3.3 为什么量化可行（三大理论基础）

1. **权重分布集中**：训练好的权重近似对称、集中在 0 附近的长尾分布，对称均匀量化即可覆盖主体；极端 outlier 用 per-channel 缩放或校准阈值处理；
2. **信息冗余**：参数总量远超任务所需信息（有效秩低、参数高度相关），权重的小幅扰动（量化即加有界噪声 $\|\delta\| \le S/2$）不显著改变输出分布；
3. **网络鲁棒性**：深层损失面平滑，量化误差逐层传播时被非线性部分吸收，端到端误差远小于单层误差的简单叠加。

**面试一句话**：量化 = 把"连续高精度"换成"离散低精度"，利用分布集中 + 模型冗余 + 误差有界三个性质，用极小精度代价换 2~4 倍显存与计算收益。

### 3.4 量化加速的三个来源（为什么量化能加速）

1. **显存减半**：INT8 字节数减半 → 权重/KV 读取带宽压力减半（decode 是带宽瓶颈，直接受益）；
2. **计算翻倍**：GPU 张量核心 INT8 峰值吞吐约为 FP16 的 2 倍（A100：FP16 312 TFLOPS vs INT8 624 TOPS）；
3. **缓存友好**：L2/寄存器容纳双倍参数，kernel 命中率提升。

**代价**：HBM 带宽数值不变，只是搬运字节变少；小模型本身带宽受限时 INT8 实际加速比低于 2×——**加速比受瓶颈环节约束（Roofline）**。

## 四、PTQ 与 QAT（重点）

### 4.1 两条路线对比

| 维度 | PTQ（训练后量化） | QAT（量化感知训练） |
|------|-------------------|---------------------|
| 流程 | 训练完 → 校准集统计分布 → 直接量化 | 训练时插入伪量化算子，让模型适应量化噪声 |
| 数据/成本 | 校准集（几百~几千样本），无需反向传播 | 完整训练数据，需反向传播（成本高） |
| 精度/适用 | INT8 大模型近无损，INT4 可能明显下降；适合快速部署 | INT8 更好、INT4 可接受；适合精度敏感、端侧小模型 |

### 4.2 PTQ 流程

```text
1. 加载 FP16 权重 → 2. 准备校准集（几百张代表业务分布的样本）
3. 前向收集每层权重/激活统计量（min/max、直方图）→ 计算 scale/zp（MinMax / Percentile / KL）
4. 替换为量化算子（权重离线量化；激活选静态/动态）
5. 验证集评估，定位敏感层 → 敏感层保高精度或改 QAT
```

### 4.3 QAT 流程与 STE 技巧

```text
1. 计算图中插入伪量化节点（forward 模拟 round + 截断）
2. 反向传播用 STE（Straight-Through Estimator）：∂q/∂r ≈ 1
3. 用正常数据微调（lr 约为正常训练的 1/10）
4. 移除伪量化节点，导出真实 INT8 权重 → 验证 + 部署
```

**STE 是 QAT 的核心数学技巧**：$\text{round}$ 的导数几乎处处为 0，直接回传会梯度消失；STE 令 $\frac{\partial \hat{q}}{\partial r} \approx 1$，等价于"前向体验量化噪声、反向无视量化"，模型从而在量化噪声下收敛。

### 4.4 误差来源分析（PTQ 为什么有时掉点）

| 误差类型 | 来源 | 缓解手段 |
|----------|------|----------|
| 截断/舍入 | outlier 超范围 / round 半步 | Percentile 校准、per-channel、更细步长、GPTQ 误差补偿 |
| 激活范围 | logits/LN 输出宽分布 | 动态量化、per-token 缩放、SmoothQuant |
| 层间放大 | 误差逐层累积 | 逐层敏感性分析，敏感层保 FP16 |
| 耦合 | 激活+权重同时量化 | QAT、混合精度 |

## 五、INT8 量化工程细节（重点）

### 5.1 per-tensor vs per-channel（必答）

| 维度 | per-tensor | per-channel（权重） |
|------|------------|---------------------|
| 粒度/存储 | 整个张量一个 scale | 每输出通道一个 scale（C_out 个，可忽略） |
| outlier 影响 | 一个 outlier 拉大全局步长，全体精度浪费 | 只在所在通道损失 |
| 精度/推荐 | 较差；适合小模型、激活 | 显著更好；大模型权重首选 |

激活侧对应 **per-token**（每个 token 一个 scale）：激活 outlier 往往以 token 为单位出现，per-token 动态缩放是当前激活量化主流（W8A8）。

### 5.2 校准（Calibration）方法对比

校准集作用：**不反向传播**，只统计激活分布确定 scale/zp。典型规模 512~2048 个代表性样本（图像任务覆盖各种分辨率/内容）。

| 方法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| MinMax | 用实际 min/max 定范围 | 零截断误差 | 被 outlier 绑架 |
| Percentile | 截断到 99.99% 分位 | 抗 outlier | 阈值需调 |
| Entropy (KL) | 最小化量化前后 KL 散度（TensorRT 默认） | 感知友好 | 需直方图 |

（另有 MSE 法：最小化 $\|x-\hat{x}\|^2$，数值最优但计算量大。）校准集**不能太脏也不能太纯**：太纯 → 激活范围估计过窄，上线后 outlier 大量截断；太脏 → 范围虚大整体浪费。经验：按业务分布抽样 + 混入少量困难样本。

### 5.3 静态量化 vs 动态量化

- **静态量化**：校准阶段确定激活 scale，推理零额外开销——主流；
- **动态量化**：推理时逐 token 实时算 min/max——精度好但开销大，用于小模型或敏感层。

### 5.4 SmoothQuant：激活量化的经典解法（面试加分）

激活难量化的根因：**outlier 集中在少数通道且幅值大**。SmoothQuant 把激活的量化难度"迁移"到权重上，对输入 $X$ 与权重 $W$ 做通道级缩放：

$$Y = (X \cdot \text{diag}(s)^{-1}) \cdot (\text{diag}(s) \cdot W)$$

激活除以 $s$ 再量化（范围收窄），权重乘 $s$ 再量化（per-channel 量化容忍变宽），$s$ 由激活通道幅值统计得到（$s_j \propto \max|X_{:,j}|^\alpha$）。这使得 **W8A8 全 INT8 推理**成为可能，而不是"权重 INT8、激活 FP16"的 W8A16 半吊子方案。

## 六、4-bit 量化：NF4、GPTQ、AWQ（重点）

### 6.1 三种流派概览

| 方法 | 流派 | 需要校准数据 | 需要重训 | 代表场景 |
|------|------|--------------|----------|----------|
| NF4 (QLoRA) | 数据类型设计 | 否 | 是（LoRA 微调） | 单卡微调 65B+ |
| GPTQ | 误差补偿（二阶信息） | 是（几百样本） | 否 | 推理部署 |
| AWQ | 激活感知通道保护 | 是（几十~几百样本） | 否 | 推理部署 |

### 6.2 NF4（Normal Float 4，QLoRA 核心）

核心洞察：**权重分布近似标准正态，均匀量化浪费中间段分辨率**。NF4 把 16 个可表示值放在标准正态分布的**等概率分位点**上，分布密的地方步长小：

$$q_i = \frac{1}{2}\left(Q\left(\frac{i}{2^k}\right) + Q\left(\frac{i+1}{2^k}\right)\right), \quad i = 0, 1, \ldots, 2^k - 1$$

其中 $Q(\cdot)$ 是标准正态 CDF 分位数，$k=4$。期望量化误差远小于均匀量化。

QLoRA 配套技术（面试常问）：**Double Quantization（双重量化）**——把 NF4 的 scale（FP32）再用 8-bit 量化，每参数省约 0.37 bit；**Paged Optimizers**——优化器状态页式管理，避免大模型微调 OOM。

### 6.3 GPTQ（误差补偿式量化，OBS 家族的 GPU 版）

思想：**量化一个权重后，更新其余权重补偿它对输出的影响**。对单层 $WX$ 最小化 $\min_{\hat{W}} \| WX - \hat{W}X \|_F^2$：逐列贪心量化，每量化一列用**二阶信息**（Hessian $H = 2XX^\top$）决定补偿：

$$w' = w - \frac{w_j^q - w_j}{[H^{-1}]_{jj}} \cdot (H^{-1})_{:,j}$$

$j$ 位置的量化误差按 $H^{-1}$ 加权扩散到其余未量化权重上，误差被"摊销"。lazy batch update（每 128 列统一更新）+ Cholesky 分解求 $H^{-1}$，使 175B 参数能源码头 4-bit 装下（论文在 A100 上量化 OPT-175B 约 4 小时）。**记忆点**：GPTQ 与剪枝中的 OBS（Optimal Brain Surgeon）同源。

### 6.4 AWQ（Activation-aware Weight Quantization）

核心洞察：**权重重要性不均匀——少数通道承载大部分激活幅度**。量化前把重要通道的权重乘保护缩放因子 $s$（提升分辨率），同时激活除以 $s$ 保持输出不变：$\hat{W} = s^{-1} \cdot \text{quant}(W \cdot s)$，$s_j = \max|X_{:,j}|^\alpha$。只保护 1% 左右的重要通道，网格搜索最优 $\alpha$（0~1）。**不需要反向传播、不需要二阶矩阵**，校准数据需求少、速度快、鲁棒，适合多模态全模型量化。

### 6.5 小结

要**微调**（领域适配）→ NF4 + LoRA（QLoRA）；要**纯推理压缩、精度优先** → GPTQ；要**快速鲁棒、资源有限** → AWQ；实际部署通常对比 AWQ/GPTQ 的 PPL 与下游任务指标后决定。

## 七、激活量化、KV Cache 量化与混合方案

### 7.1 "谁被量化"坐标系

| 方案 | 权重 | 激活 | KV Cache | 显存收益 | 典型做法 |
|------|------|------|----------|----------|----------|
| W8A16 | INT8 | FP16 | FP16 | 权重减半 | 老牌 PTQ |
| W8A8 | INT8 | INT8 | FP16/FP8 | 权重+激活减半 | SmoothQuant 类 |
| W4A16 | INT4 | FP16 | FP16 | 权重减至 1/4 | GPTQ / AWQ |
| KV-INT8/FP8 | — | — | INT8/FP8 | KV 减半 | 长上下文/高并发刚需 |

（FP8 全家桶：权重/激活/KV 全 FP8，H100 原生支持，各减半。）

### 7.2 KV Cache 量化的原理与收益

**KV cache**：decode 阶段每生成一个 token 就把该 token 的 K、V 向量追加进缓存，供后续 token 注意力使用（省去重复 prefill）。显存公式：

$$M_{KV} = 2 \times L \times H \times d_h \times S \times B \times b$$

$L$ 层数、$H$ 头数、$d_h$ 头维度、$S$ 序列长度、$B$ batch、$b$ 每元素字节（FP16=2，FP8/INT8=1）；系数 2 来自 K 和 V。

**数值例**（LLaMA-2-7B：$L=32, H=32, d_h=128$）：每 token KV 占用 $2 \times 32 \times 32 \times 128 \times 2\text{B} = 512\text{KB}$；单请求 4K 上下文 **2GB**，batch=32 时 **64GB**——KV cache 是高并发与长上下文的显存大头，也是量化收益最大的地方。KV 量化要点：KV 值分布稳定，INT8/FP8 量化损失极小（业界已大量使用 FP8 KV cache）；按 **per-token/per-channel 分组缩放**，attention score 在量化域计算后反量化；与权重量化正交可叠加（W4A16 + KV-FP8 是显存极致部署常见组合）。

### 7.3 为什么激活量化比权重量化难

权重**离线**量化，可慢慢统计、逐通道精调；激活**在线**出现，静态量化只能靠校准集外推，分布一变就截断；且激活含 outlier（注意力 logits、视觉 patch embedding 高分辨率时动态范围大），参与每步前向，误差直接逐层放大。

## 八、量化对多模态模型的影响（重点）

### 8.1 三个子模块的量化敏感性

| 子模块 | 规模 | 量化敏感性 | 常见部署策略 |
|--------|------|------------|--------------|
| 视觉塔（ViT）+ 投影层 | 0.3B~6B + <1% | **高**（细粒度特征、桥接瓶颈） | 保 FP16/BF16，或仅 INT8 |
| LLM | 1B~70B | 中（冗余大、鲁棒） | INT8 / INT4（GPTQ/AWQ） |

### 8.2 视觉塔为什么量化敏感（面试高频）

1. **规模小、冗余少**：LLM 几十亿参数冗余空间大；视觉塔 0.3~0.7B，去冗余后编码能力直接受损；
2. **任务精细**：OCR 字符级、计数、空间位置依赖视觉特征高保真，INT4 后 patch 级细节丢失明显；
3. **输入动态范围大**：高分辨率 patch 数千，patch embedding 与 attention logits 幅值跨度大，激活量化截断概率高；
4. **误差前置放大**：视觉塔在计算图最前端，误差被投影层和 LLM 逐层放大，等效"把错图喂给 LLM"。

> **工程结论**：视觉塔只占总参数约 10%，量化收益小、风险高——**默认方案是"LLM 量化 + 视觉塔 FP16"**。全模型 INT8/FP8 优先 QAT 而非 PTQ；OCR/图表等细粒度任务务必端到端 benchmark。

### 8.3 多模态特有的量化收益

高分辨率/多图产生**上万视觉 token**，KV cache 巨大 → KV 量化（INT8/FP8）收益显著；视觉塔推理是长序列前向（计算密集），INT8 张量核心加速直接；检索类（embedding）场景激活峰值内存大，W8A8 收益明显。

## 九、推理引擎总览（重点）

### 9.1 引擎坐标系

| 引擎 | 定位 | 是否编译 | 内核来源 | 调度优化 |
|------|------|----------|----------|----------|
| PyTorch Eager | 研究/基线 | 否（逐算子调度） | ATen + cuDNN | 无 |
| ONNX Runtime | 跨框架中间层 | 是 | 内置 EP + TensorRT EP | 图优化 |
| TensorRT | NVIDIA 深度优化 | 是（engine） | 自研 CUDA kernel | 层融合 + 精度选择 |
| vLLM | LLM/VLM 服务化 | 是 | 生态复用 + 自研 kernel | PagedAttention + 连续批处理 |

### 9.2 引擎选择决策树

自回归生成（LLM/VLM 对话）→ **vLLM 首选**（极致低延迟/边缘 → TensorRT-LLM）；编码器类（检索/embedding）→ 跨框架用 ONNX Runtime、极致低延迟用 TensorRT；实验/demo → PyTorch Eager + torch.compile。

## 十、ONNX 与 ONNX Runtime

### 10.1 是什么

ONNX 是**模型交换的中间格式**：一套与框架无关的算子集合（opset）和计算图描述。PyTorch 模型导出为 ONNX 图，被任意后端（ONNX Runtime、TensorRT、OpenVINO、TFLite）消费。

### 10.2 为什么要导出 ONNX（三大理由）

1. **跨框架互通**：PyTorch 训练 → ONNX → 任意平台部署，避免框架锁定；
2. **图级优化 + TensorRT 前端**：ONNX 图是静态确定的，可做动态图做不到的优化（常量折叠、死节点消除、算子融合）；TensorRT 最标准、最稳定的入口就是 ONNX 图，比手写 C++ 网络定义可靠。

### 10.3 ONNX Runtime 的关键机制

- **Execution Provider（EP）**：同一张 ONNX 图可选 CPU EP、CUDA EP、TensorRT EP，换硬件不换模型；
- **图优化**：常量折叠、算子融合（LayerNorm 融合、Softmax+Scale 融合）、内存规划（arena 复用）；
- **局限**：动态形状（视觉 token 数随分辨率变）支持有限，导出要声明动态维度上界；自回归生成场景 KV cache 管理需手工做（vLLM 原生解决）。

> **面试一句话**：ONNX = 格式（模型描述），ONNX Runtime = 执行引擎（图优化 + 多后端调度）。导出 ONNX 解决"模型怎么描述、怎么换后端"，加速靠后端 EP 与融合——它是"中间层"，不是加速器本身。

## 十一、TensorRT（重点）

### 11.1 一句话

> **TensorRT 是 NVIDIA 的推理优化框架：把计算图编译成专为特定 GPU 定制、算子深度融合、内核自动选择的二进制 engine 文件。**

### 11.2 TensorRT 为什么快（面试必答，4 层）

1. **层融合**：多个算子合并为单一 kernel，减少 kernel 启动与中间张量读写。典型：Conv+BN+ReLU 融合、矩阵乘+残差+激活融合、LayerNorm/Softmax 全融合；
2. **内核自动选择（Tactic Selection）**：对每个算子，在**目标 GPU 上实际跑多套候选 kernel**（不同 tile、向量化宽度、是否用 Tensor Core）选最快的——PyTorch 做不到的自动调优；
3. **精度选择**：FP32/FP16/INT8 混合精度调度，敏感算子保 FP32，配合 INT8 校准近无损；
4. **底层 CUDA 深度优化**：手写/半手写 Tensor Core kernel、内存复用（arena 池）、序列化 engine 消除 Python 解释与逐算子分发开销。

### 11.3 Engine 构建流程

engine 文件**绑定 GPU 型号、驱动、CUDA 版本**（A100 的 engine 不能跑在 V100 上）：PyTorch → 导出 ONNX → TensorRT 解析 → 图优化（融合、消除）→ 精度配置（FP16/INT8 + 校准）→ 每算子目标卡上 autotune kernel → 序列化 engine 文件 → 运行时加载部署。### 11.4 适用与局限

| 优点 | 局限 |
|------|------|
| 低延迟（batch=1 最优，融合收益大）、显存占用低 | 构建时间长（autotune）、engine 与硬件绑定 |
| INT8/FP8 生态成熟、可与 Triton/自定义插件集成 | 动态形状支持复杂；生成场景需 TensorRT-LLM 或自行管理 KV |

> **定位**：TensorRT 是"延迟优先 + 形状相对固定"场景的最优解（检索、embedding、端侧）；自回归生成场景需要 TensorRT-LLM 或 vLLM 这类 LLM 专用方案。

## 十二、vLLM：PagedAttention 与显存管理（重点）

### 12.1 要解决的问题

传统 LLM 服务中，KV cache 按"请求最大可能长度"预分配连续显存：实际序列短 → **内部碎片**；请求间显存不共享 → **外部碎片**；碎片导致显存利用率只有 20~40%，并发上不去。

### 12.2 PagedAttention：KV Cache 的分页管理（必背）

**思想：把 KV cache 切成固定大小的块（block，如每块 16 token），用页表（page table）映射"逻辑 token 位置 → 物理显存位置"——与操作系统虚拟内存分页完全同构**：请求 A 的逻辑块 0/1/2 经页表指向物理块 #7/#3/#12，空闲块可任意拼接复用。

收益（论文报告吞吐提升 2~4 倍）：① **碎片趋零**——块粒度分配，块内浪费 ≤ 1 块，块间任意拼接，显存利用率 90%+；② **高并发**——显存利用率提升 → 同卡承载并发请求翻倍；③ **零拷贝共享**——并行采样/投机解码共享前缀块，配合 **Copy-on-Write**；④ **换出（swap）**——显存不足时块换到 CPU，恢复换回，避免 OOM。

### 12.3 为什么性能高

注意力按块遍历（block-wise attention），块内连续、块间页表索引，配合专用 kernel，**解决碎片问题而不引入明显访存开销**——这是它区别于朴素"KV cache 换出"方案的关键。面试一句话：PagedAttention 把 KV cache 从"连续大数组"变成"分页小数组"，像虚拟内存管理物理内存一样管理显存，碎片消失、并发翻倍，这是 vLLM 吞吐高的第一来源。

## 十三、Continuous Batching 与调度（重点）

### 13.1 传统静态批处理的问题

静态 batching：凑满一个 batch 才推理 → 早完成的请求**空等**；batch 内只要有一个长请求，全批陪跑，P99 崩坏。

### 13.2 Continuous Batching（连续批处理 / 迭代级调度）

**思想：调度粒度从"请求级"降到"decode 迭代级"——每轮 decode 结束，完成的请求立刻退出，队列里的新请求立即做 prefill 补位。**（静态 batching 是 `[A B C] → [A B C] → [A B C]` 全批陪跑；连续 batching 是 `[A B C] → [B C D] → [B D E]`，A 完成即走、D 立即加入。）

收益：GPU 每轮都在干"密度最高"的活，吞吐提升 2~10×；短请求不被长请求拖累，P95 显著改善；**prefill 与 decode 混批**——新请求的 prefill 与老请求的 decode 并行，进一步填满计算资源。

### 13.3 调度与抢占

- 显存不足时**抢占（preemption）**：把低优先级/最老请求的 KV 块 swap 到 CPU（配合 PagedAttention 的块粒度）；
- 常用 **FCFS + 优先级队列**；新请求 prefill 不抢正在 decode 的请求（保证 TTFT 稳定）；
- **Chunked Prefill**：把大 prefill 切块穿插到 decode 中间，防止单请求 prefill 卡住整批 decode。

## 十四、推理引擎对比总表（重点）

| 维度 | PyTorch Eager | ONNX Runtime | TensorRT | vLLM |
|------|---------------|--------------|----------|------|
| 延迟（batch=1） | 高（Python + 无融合） | 中 | **低** | 中低（TTFT 受调度影响） |
| 吞吐（高并发） | 低 | 中 | 中高（需自行批处理） | **高**（连续批处理） |
| 显存效率 | 低（KV 预分配） | 中 | 中 | **高**（PagedAttention） |
| 动态形状（视觉 token） | 最灵活 | 中（需声明） | 低 | 中（需配置） |
| 开发成本 | 最低 | 低 | 高（构建/插件） | 低（部署即用） |
| 模型类型 | 任意 | 任意（非生成优先） | 编码器/固定形状 | **自回归生成** |
| 多模态支持 | 原生 | 中等 | 需自拼图 | 主流 VLM 原生 |
| 典型场景 | 原型、基线 | 跨平台、嵌入式 | 检索、端侧 | 高并发对话、RAG |

**选型结论**：高并发文本/VLM 生成 → vLLM；低延迟、固定输入形状（embedding）→ TensorRT；跨框架/多端复用 → ONNX。三者不互斥：ONNX 图可作 TensorRT 前端，vLLM 内部也可挂 TensorRT-LLM 引擎。

## 十五、显存优化（重点）

### 15.1 推理显存构成（必背公式）

$$\text{Mem} = M_{weights} + M_{KV} + M_{activations} + M_{framework}$$

| 组成部分 | 规模公式 | 7B 模型示例 | 占比趋势 |
|----------|----------|-------------|----------|
| 权重 | $P \times b$（参数量×字节） | 7B×2B = 14GB（FP16） | 短上下文时最大 |
| KV cache | $2 L H d_h S B b$ | 4K 上下文单请求 2GB；batch32 达 64GB | **长上下文/高并发时爆炸** |
| 激活 + 框架 | 取决于 batch/序列/图结构；CUDA context | 数 GB + 数百 MB~1GB | 大 batch、多图时激增 |

> **显存矛盾的本质**：权重是固定成本（一次加载），KV cache 随**并发 × 上下文**线性增长。高并发下 KV cache 反超权重成为最大头——这正是"量化权重 + 量化 KV + 分页管理"三件套的动机。

### 15.2 视觉模型（VLM）的显存特殊性（重点）

1. **视觉 token 爆炸 + KV cache 被撑爆**：ViT patch14 时，336² 图 → 576 token，1152² 高分辨率图 → $82 \times 82 \approx 6724$ token；Qwen2-VL-7B（$L=28, H=28, d_h=128$）每 token KV ≈ 392KB，单张 1152² 图 ≈ 2.6GB——一张图相当于几千字文本；
2. **激活激增**：prefill 阶段视觉序列的中间激活（含注意力的 $S^2$ 项）随分辨率平方增长；视觉塔权重也要加载（675M FP16 ≈ 1.35GB）。

### 15.3 优化手段清单（按收益排序）

| 手段 | 原理 | 收益 | 代价 |
|------|------|------|------|
| 权重量化（INT8/INT4） | 字节减半/减 1/4 | 权重 + KV 直接缩小 | 精度风险 |
| KV cache 量化（FP8/INT8） | KV 字节减半 | 长上下文/高并发收益大 | 极小精度损失 |
| GQA / MQA | 多 query 头共享 KV 头 | KV 减至 1/G ~ 1/H | 训练时决定 |
| FlashAttention | 不物化 N×N 注意力矩阵 | 激活显存 O(N²)→O(N) | 无（且更快） |
| 批处理 / 显存池 / token 压缩 | 复用与压缩 | 并发提升、峰值下降、KV+激活双降 | 排队延迟 / 实现复杂度 / 精度风险 |

**注意**：梯度检查点（gradient checkpointing）是**训练**技术（重算换显存），推理不需要——面试被问到要指出这是训练侧手段。

### 15.4 GQA/MQA 数学

标准 MHA：$H$ 个 query 头、$H$ 个 KV 头。GQA 把 KV 头合并成 $G$ 组：

$$M_{KV}^{GQA} = \frac{G}{H} \times M_{KV}^{MHA}$$

LLaMA-2-70B（G=8）KV cache 仅为同规模 MHA 的 1/8；MQA（G=1）减到 1/H。

### 15.5 FlashAttention 为什么省显存又快

标准注意力要物化 $S \times S$ 注意力矩阵（HBM 反复读写）；FlashAttention 用 **tiling + 在线 softmax（两 pass rescaling：$m \leftarrow \max(m, m_{new})$，$l \leftarrow l \cdot e^{m_{old}-m} + l_{new}$）** 把注意力计算融合成分块流式，全程不落地大矩阵。显存 O(S²) → O(S)；HBM 访问减少 5~20 倍，attention 阶段提速 2~4×；decode 阶段每步对全部 KV 做注意力同样受益。

## 十六、服务化部署（重点）

### 16.1 整体架构

请求链路：**客户端请求（HTTP/gRPC）→ [FastAPI 层]（鉴权、限流、校验）→ [队列]（吸收突发流量）→ [批处理器]（动态批：攒到 max_batch 或 max_wait 发车）→ [推理引擎（vLLM / TensorRT / ONNX）] → 流式返回（SSE / WebSocket）**。队列的作用是解耦"请求到达率"与"推理速率"。

### 16.2 FastAPI 服务的关键点

| 问题 | 解法 | 原因 |
|------|------|------|
| 推理阻塞/GIL | async 接口 + 推理放后台线程/进程，多 worker 并发 | 防阻塞拖垮事件循环、绕开 GIL |
| 请求积压 | 有界队列 + 背压（503 快速失败） | 无限队列 = 延迟雪崩 |
| 长输出 | SSE/流式返回 | 用户体验 + 提前释放连接 |
| 批处理 | **Dynamic Batching**：攒到 `max_batch_size` 或最长等待 `max_wait_ms`（如 32 个 / 20ms）即推理 | 单请求走推理浪费 GPU |

**Dynamic Batching 语义**：延迟 = 攒批等待 + 推理时间。`max_wait_ms` 是"吞吐-延迟旋钮"：调大 → 吞吐升、延迟升；调小反之。

### 16.3 模型加载策略对比

| 策略 | 做法 | 优点 | 缺点 | 适用 |
|------|------|------|------|------|
| 单模型常驻 | 启动即加载，常驻显存 | 首延迟最低、稳定 | 显存独占 | 单一高频模型 |
| 多模型按需 / 模型池 | 懒加载 + LRU 淘汰；或预加载 K 副本、多卡分片 | 显存复用 / 高可用 | 冷启动 1~10s+ / 显存×K | 模型多流量低 / 高可用 |

多模态场景：多个 VLM 常共用/近似共享视觉塔，模型池可共享视觉塔副本，避免重复占用。

### 16.4 吞吐与延迟的权衡（面试必答）

**为什么 batching 增大延迟却能提升吞吐**：GPU 是"吞吐型"设备——一批处理 32 个请求的时间远小于单请求的 32 倍（权重读取被摊薄：单请求每步 decode 读一遍全部权重，batch=32 时 32 个请求共享这一次读取）；代价是每个请求多等"攒批 + 整批跑完"。

**本质是排队论问题**：利用率高 → 单请求等待长。M/M/1 队列响应时间 $W = \dfrac{1}{\mu(1-\rho)}$——利用率 $\rho \to 1$ 时响应时间 $\to \infty$。所以生产目标不是 GPU 满载，而是**在吞吐-延迟曲线拐点左侧工作**，留 20~30% 余量。

> **面试结论**：延迟和吞吐是同一资源（GPU）的两个侧面，不能同时最大化；部署调优 = 找到业务可接受 P95 约束下的最大吞吐点（即拐点左侧工作点）。

## 十七、并发、排队与延迟分析（重点）

### 17.1 为什么高并发下必须排队

并发直接冲进 GPU 的后果：① **显存爆炸**（并发 × KV cache 超限 → OOM，全部请求陪葬）；② **性能雪崩**（超过承载能力后每请求更慢，P99 指数恶化、吞吐反而下降）；③ **不可控**（无缓冲、无公平性）。

排队的作用：**削峰填谷**（把到达率 $\lambda$ 变成 GPU 能消化的速率）、**可控调度**（FCFS/优先级 + 批处理，P95 可预测）、**优雅降级**（队列满返回 503 快速失败，而不是拖死服务）。

### 17.2 为什么 P95 比平均延迟重要（服务化视角）

- 平均延迟被多数正常请求主导，**掩盖 5% 慢请求**——而这 5% 正是投诉来源；SLO 定义决定团队行为：目标"平均 < 2s"无人管尾部，目标"P95 < 3s、P99 < 5s"倒逼处理长尾（超时、重试、排队策略）；
- 分布式调用下尾延迟叠加放大——**尾延迟是系统设计问题而非运气**。

### 17.3 监控与容量规划

- 监控三件套：延迟分位（P50/P95/P99）、吞吐（TPS/QPS）、显存（峰值 + 当前）＋ 队列深度、利用率；
- 容量规划：按"峰值 QPS × P95 目标"用 Little's Law 反推并发，再按"并发 × 单请求 KV + 权重"推算 GPU 数：$\text{GPU 数} \approx \dfrac{\text{并发} \times M_{KV}^{req} + M_{weights}}{M_{gpu}}$

## 十八、Docker 部署

### 18.1 镜像构建要点

多阶段构建：构建阶段装 CUDA toolkit，运行阶段只用 runtime（`FROM nvidia/cuda:12.1-runtime-ubuntu22.04` + `COPY --from=build /app /app`）。

| 事项 | 做法 | 原因 |
|------|------|------|
| 基础镜像 | `nvidia/cuda:*-runtime`（不用 full） | 运行时不需要 toolkit，镜像小几 GB |
| GPU 运行时 | 安装 nvidia-container-toolkit，`docker run --gpus all` | 容器内可见 GPU |
| 健康检查 | `/healthz` 端点 + docker healthcheck，多副本多端口 | 摘除不健康实例；单实例 OOM 不拖垮全部 |
| 模型/版本 | 镜像内或共享卷挂载；锁 CUDA/driver/引擎版本 | 模型几十 GB 控制镜像体积；engine 与版本绑定 |

### 18.2 部署注意

容器对 GPU 直通、无虚拟化损耗，但**确认容器内 `nvidia-smi` 可见**；engine/模型加载放启动阶段（非首个请求），配合健康检查 ready 后再注册到负载均衡；水平扩展按 GPU 数做副本，队列在副本间做轮询/一致性哈希。

## 十九、多模态推理特有的优化（重点）

### 19.1 视觉 token 裁剪与压缩

**问题**：高分辨率/多图输入产生数千~上万视觉 token，KV cache 与 prefill 计算量随 token 数增长（KV 线性、注意力平方）。

| 方法 | 思想 | 说明 |
|------|------|------|
| Token Merger（Qwen2-VL） | **空间合并**：相邻 token（如 2×2 窗口）合并为 1 个，token 数降为 1/4 | 高分辨率窗口下合并局部冗余，保留全局语义 |
| 注意力得分裁剪（T-Monkey 等） | **显著性选择**：用注意力得分选出信息量最高的 K 个 token，丢弃背景/冗余 | 高分辨率 OCR/文档图收益大 |
| AnyRes 瓦片化（LLaVA-NeXT） | 分辨率缩放为多瓦片，每瓦片独立编码 | 控制单图 token 上限 |

**工程权衡**：合并率越高，OCR/细粒度精度越差；通常对"高分辨率大图"启用压缩、普通图不启用，用分辨率/任务类型路由控制。

### 19.2 视觉编码器复用与 Embedding 缓存

- **多图/多轮任务**：同一张图多次提问 → 视觉塔 + 投影输出只**编码一次**，后续轮次复用缓存特征（重复 prefill 是最大浪费）；
- **检索场景**：离线把整个图库编码成 embedding 入库（向量库如 FAISS/HNSW），在线 query 只编码文本/小图——视觉塔计算从在线路径移到离线路径；增量入库异步编码，缓存命中走内存检索（毫秒级）；
- **前提**：视觉塔部署中冻结（权重不变），特征才是确定、可缓存的。

### 19.3 视觉塔与 LLM 的异构部署

视觉塔是计算密集（ViT 前向）、对 INT4 敏感，LLM 是 prefill 计算密集 + decode 带宽密集、量化友好，两者并行方式不同。工程上可以把视觉塔和 LLM 部署到**不同进程/GPU**：视觉塔用 TensorRT 低延迟编码，LLM 用 vLLM 高吞吐生成，中间特征接口连接——多模态服务化的高级形态。

## 二十、Prefill 与 Decode 阶段优化差异（重点）

### 20.1 两个阶段的计算本质（Roofline 视角）

**算术强度**（每字节搬运对应的浮点运算数）：$I = \dfrac{FLOPs}{Bytes}$。A100 平衡点：312 TFLOPS ÷ 2 TB/s ≈ **156 FLOPs/B**。

- **Prefill**：处理 $S$ 个输入 token，FLOPs ∝ $S^2$（注意力）但权重只读一遍 → 算术强度高，**计算瓶颈（compute-bound）**，吃满 Tensor Core 就有收益；
- **Decode**：每生成一个 token 要**重读全部权重 + 全部 KV cache**，FLOPs 只有点积量级。7B FP16 单流每 token 至少读 14GB 权重 → 理论上限 = 2TB/s ÷ 14GB ≈ **143 token/s**（与实测单流同量级），是**显存带宽瓶颈（memory-bound）**。

### 20.2 对应优化手段

| 优化 | Prefill | Decode |
|------|---------|--------|
| FlashAttention | 减少 S² 矩阵 HBM 往返 | 加速每步 KV 注意力扫描 |
| 量化 | INT8/FP8 张量核心翻倍 | 字节减半 → 带宽瓶颈直接缓解 |
| batching | 填满计算 | **权重读取摊薄，吞吐近线性上升** |
| KV 管理 + 投机解码 | — | PagedAttention + KV 量化；小模型草稿 + 大模型并行验证 |

### 20.3 投机解码一句话原理（面试加分）

小模型（draft）快速采样 $k$ 个 token，大模型（target）**一次前向并行验证**——带宽瓶颈下"验证 k 个 token 的成本接近 1 个 token"，被拒处回退重采样，典型 1.5~3×。

### 20.4 多模态视角的 prefill 特化

视觉 token 是**一次性预填充**：图像 prefill 完即固定，可单独缓存（§19.2）；大图 prefill 的 $S^2$ 注意力计算量爆炸 → 视觉 token 压缩本质是**砍 prefill 计算量 + KV 显存**；TTFT = 视觉 prefill + 文本 prefill + 调度等待，接口层要按业务给 TTFT 预算（如"P95 TTFT < 2s"）。

## 二十二、常见误区

**误区 1：量化成 INT4，速度就快 4 倍。**
错。加速受瓶颈约束：compute-bound 的 prefill 接近理论 2×（INT8），decode 是带宽瓶颈，收益来自字节减半；INT4 还要付反量化与拆包开销。**显存收益（减 1/4）才是 INT4 的核心价值。**

**误区 2：模型变小延迟必然变低 / P95 = 平均延迟 + 固定余量。**
不一定。带宽受限的 decode 阶段延迟取决于"每 token 读多少字节"，压缩只减计算量不减字节则延迟几乎不变；尾延迟是请求分布的真实属性，与均值无固定关系，并发升高、排队出现时 P95 非线性恶化（$\rho \to 1$ 发散），必须实测。

**误区 3：PTQ 掉点就上 QAT，一定能救回来。**
不一定。掉点根因（激活 outlier、校准集不代表性）不解决，QAT 也白费且成本高。正确顺序：查校准集 → per-channel/per-token → SmoothQuant → 敏感层保 FP16 → 最后才 QAT。

**误区 4：vLLM 快是因为它的 kernel 写得快。**
部分正确但主因是架构：**PagedAttention（碎片 → 并发翻倍）+ Continuous Batching（GPU 利用率）**贡献大部分吞吐提升，kernel 是锦上添花。

**误区 5：多模态模型 = LLM + 视觉塔，按 LLM 的方式量化就行。**
错。视觉塔量化敏感、视觉 token 导致 KV 爆炸、prefill 计算量平方增长——需要视觉侧专门优化（token 压缩、特征缓存、塔单独部署）。

## 二十三、高频面试问答

**Q1：TensorRT 为什么快？**
四点：① 层融合减少 kernel 启动与中间读写；② 每算子在目标卡上实跑候选 kernel 择优（tactic）；③ FP16/INT8 精度选择 + 校准；④ 深度优化 CUDA/Tensor Core kernel + 序列化 engine 消除运行时开销。

**Q2：PTQ 和 QAT 的区别？**
PTQ：训练后用校准集统计分布直接量化，无反向传播，快但精度上限低；QAT：训练中插入伪量化算子（STE 直通梯度），模型适应量化噪声，精度高但需重训。INT8 大模型 PTQ 常够用；INT4 或小模型（如视觉塔）倾向 QAT。

**Q3：vLLM 的 PagedAttention 原理？**
把 KV cache 切成固定大小块，用页表把"请求的逻辑 KV 序列"映射到"物理显存块"，类似操作系统分页。消除预分配造成的内部/外部碎片，显存利用率从 20~40% 提到 90%+，支持块级换出与 Copy-on-Write 共享，并发能力翻倍。

**Q4：Continuous Batching 是什么？**
调度粒度从请求级降到 decode 迭代级：每轮 decode 结束，完成请求立刻退出、新请求立即补位，prefill 与 decode 混批。避免"全批等最慢请求"，GPU 每轮满负荷，吞吐提升 2~10 倍，P95 改善。

**Q5：为什么 P95/P99 比平均延迟重要？**
平均被多数快请求掩盖，不能反映用户体验；SLO 按分位定义才能倒逼尾部优化；分布式链路中尾延迟叠加放大。指标报告必须给分布。

**Q6：量化为什么能加速？**
三重来源：字节减半（权重/KV 带宽压力减半，decode 直接受益）、INT8 张量核心峰值约 2× FP16（prefill 受益）、缓存友好。同时显存减小 → 可增大 batch/并发。

**Q7：为什么 prefill 是计算瓶颈而 decode 是带宽瓶颈？**
算术强度 = FLOPs/字节。prefill 一次读权重、算 S² 注意力，强度高 → 吃算力；decode 每 token 重读全部权重 + KV cache，强度可低至 ~1 FLOP/B，远低于 A100 平衡点 156 FLOPs/B → 带宽决定速度。故 decode 优化核心是"减少每 token 读取字节"（量化、KV 压缩、GQA）与"摊薄权重读取"（batching）。

**Q8：多模态模型推理与纯文本 LLM 的部署差异？**
① 视觉 token 数千~上万 → KV cache 与 prefill 计算量爆炸；② 视觉塔量化敏感，通常保 FP16、LLM 量化；③ 高分辨率激活动态范围大，激活量化难；④ 可做视觉特征缓存（多轮/多图复用）、token 压缩、视觉塔独立部署等特有优化。

**Q9：KV cache 是什么？为什么值得量化？**
自回归生成时每步产出的 K/V 向量缓存在显存中供后续 token 注意力使用，避免重复 prefill。其大小 $2LH d_h S B b$ 随序列 × 并发线性增长，高并发/长上下文时是显存最大头。量化为 FP8/INT8 字节减半、损失极小，是性价比最高的显存优化。

**Q10：部署时怎么选引擎？**
自回归生成（VLM 对话）→ vLLM；固定形状低延迟（embedding/检索）→ TensorRT；跨框架移植 → ONNX。用基准测试决策：同模型同输入对比 P50/P95、吞吐、显存，满足 SLO 前提下选成本最低者。
