# 图文检索与向量库：多模态检索系统全栈笔记

> 本笔记覆盖多模态检索（text-to-image、image-to-image、图文匹配、视频片段检索）从任务定义、双塔召回模型、ANN 近似最近邻算法、向量数据库选型，到多模态特有问题和效果评测的完整体系。面试被问"你们检索系统怎么做的""为什么用双塔不用 VLM 打分""HNSW 和 IVF 怎么选"时，本文是完整弹药库。与 05_SigLIP 的关系：SigLIP/CLIP 是检索系统的"编码器"，本文讲的是编码器之外的一整套工程系统。

## 一、检索任务定义与问题分类

### 1.1 四大检索任务

| 任务 | 输入（Query） | 输出 | 典型场景 |
|------|--------------|------|---------|
| 文本搜图（T2I Retrieval） | 一句话/一句描述 | 按相关度排序的图像 Top-K | 电商"红色连衣裙"、相册搜索、素材库 |
| 图搜图（I2I Retrieval） | 一张图 | 语义相似的图像 Top-K | 以图找款、去重、版权检索 |
| 图文匹配（ITM） | 一张图 + 一句文本 | 是否匹配（分数/二分类） | 图文一致性审核、数据清洗、CLIP 过滤 |
| 视频片段检索（Video Retrieval） | 文本/图 | 命中片段 + 起止时间戳 | 视频库里找"一个人在沙滩奔跑"的镜头 |

**共同本质**：把 query 和候选文档映射到同一向量空间，按相似度排序。四种任务只是 query 的模态和返回粒度不同（图片 vs 时间片段）。

### 1.2 检索 vs 匹配 vs 排序：三个易混概念

| 概念 | 问的问题 | 输入 | 输出 | 要求 |
|------|---------|------|------|------|
| 检索（Recall/Retrieval） | "库里有哪几个相关的？" | Query + 全库 | 候选集 Top-K | **全**：宁可多，不可漏（高召回） |
| 匹配（Matching） | "这一对到底匹不匹配？" | 固定的 pair | 分数 / 二分类 | **准**：单对判断要可靠（高精度） |
| 排序（Rerank/Ranking） | "候选集里谁最相关？" | 候选集（检索的输出） | 有序列表 | **序**：相对顺序要正确（NDCG/mAP） |

三者是流水线关系：**检索产生候选 → 匹配/排序精化**。检索是匹配的"召回版"（不能逐对精判，只能快速筛）、排序是检索的"精排版"（候选小了才付得起精细打分的成本）。

### 1.3 为什么这个领域值得单独复习

面试中"检索"是一个独立能力栈：模型（双塔）只是其中一环，其后还有索引（ANN）、存储（向量库）、评测（Recall@K/mAP）和系统工程（增量更新、缓存）。问题往往从"你的双塔怎么训练的"一路追到"HNSW 的 efSearch 是什么""FAISS 和 Milvus 的区别"，本文按这条链路逐层展开。

## 二、检索系统全流程（工程主线）

### 2.1 整体架构（一句话版）

```text
离线（索引侧）:
  文档/图像 → 双塔编码器(CLIP/SigLIP) → embedding → 向量库(建立 ANN 索引)

在线（查询侧）:
  query → 双塔编码器 → 查询向量 → ANN 检索 Top-K → (可选) Rerank 精排 → 返回
```

**核心思想：一切能在离线做好的计算绝不放到在线做。** 所有候选文档的 embedding 在入库时算好存好，在线查询只做"一次编码 + 一次索引查询"，全程毫秒级。

### 2.2 离线索引流程（写入侧）

```text
1. 数据准备：图像 → 预处理（resize/归一化）→ 批量喂编码器
2. 向量化：图像 → SigLIP/CLIP 图像塔 → L2 归一化 embedding（如 1024 维）
3. 入库：向量 + 元数据（image_id、URL、标签、时间戳）写入向量库
4. 建索引：向量库对向量建立 ANN 索引（IVF/HNSW/PQ）
5. 增量：新数据小批量合并、删除向量打标记、定期重索引
```

要点：
- **离线批量编码可以吃满 GPU 吞吐**（几百万张图也就几小时量级），成本摊薄；
- 入库时同时存元数据（MySQL/对象存储），向量库只负责"按相似度取 ID"，最终展示信息按 ID join；
- 索引构建是异步任务，构建期间查询走旧索引，构建完原子切换（双写/影子索引）。

### 2.3 在线查询流程（读侧）

```text
1. 接收 query（文本/图像）
2. 文本→tokenize；图像→预处理
3. query 向量 = 编码器(q) （单次前向，几毫秒）
4. 向量库相似度检索：ANN 返回 Top-K 候选（毫秒级）
5. (可选) Rerank：对 Top-K（如 50~100 条）用更强模型精排
6. 过滤规则：业务条件（类目、价格、鉴黄）裁剪
7. 按 score 降序返回 Top-N
```

延迟预算：编码 ~5-10ms + ANN 检索 ~5-20ms + 精排（若启用）~100-300ms。**召回阶段必须吃掉 99% 的库，用最快的结构；精排只面对 100 条内候选，可以上最准的模型。**

### 2.4 为什么必须用双塔编码器做召回，而不是 VLM 逐条打分

这是检索系统设计的第一性原理：**向量检索的复杂度与库规模无关（近似），逐条打分的复杂度与库规模线性相关。**

| 方案 | 一次查询的计算量 | 100 万图库的耗时量级 | 结论 |
|------|----------------|---------------------|------|
| 双塔 + 向量检索 | 编码 query 1 次 + 索引查询 | 10~30 ms | ✅ 工业可行 |
| VLM 逐条打分（每张图过一遍 LLaVA/Qwen-VL） | 编码 100 万次 | 小时级（单卡）/分钟级（千卡） | ❌ 不可行 |
| Cross-Encoder 逐条（图文对一起过 Transformer） | 100 万次双模态前向 | 小时级 | ❌ 不可行 |

原因拆解：
1. **双塔的向量可以离线预计算**：库里的图只编码一次，存成向量；query 每次只编码一次，然后交给向量索引做相似度搜索；
2. **VLM/cross-encoder 无法预计算**：它的交叉注意力在 query 和 doc 之间，每次打分都是一次完整前向，复杂度必然随库规模线性增长；
3. **向量检索用索引压缩了搜索空间**：HNSW/IVF 把"和每个向量都比一遍"变成"只在图/倒排列表里走几条路径"，常数时间级别。

> **一句话记忆**：双塔把"比对成本"从**在线计算**转移到**离线存储**；VLM 打分把成本全部留在在线，规模一大必然崩。

### 2.5 为什么"双塔召回 + 精排"是工业标准

| 环节 | 模型 | 目标 | 代价 |
|------|------|------|------|
| 召回（Recall） | 双塔（CLIP/SigLIP） | 高召回、低延迟、覆盖全库 | 精度有限（单向量概括整图，细粒度易丢） |
| 精排（Rerank） | Cross-Encoder / VLM / 多模态大模型 | 高精度、序正确 | 慢，只能面对小候选集 |

两级结构本质是**用精度换速度的工程妥协**：召回负责"不漏"，精排负责"不错"。单用双塔直接出最终结果，Top-K 里混入细粒度错误（比如"猫在沙发上"搜出"猫在地上"）；单用精排模型，库稍大就不可用。两者互补构成标准解。

## 三、双塔检索模型

### 3.1 数学形式

设 query 编码器 $E_q$、文档编码器 $E_d$（均为深度网络，如 SigLIP 的图像塔/文本塔），query $q$ 和文档 $d$ 的匹配分：

$$\text{score}(q, d) = E_q(q)^\top E_d(d) = \langle E_q(q), E_d(d)\rangle$$

- **双塔的"双"**：$E_q$ 和 $E_d$ 各自独立前向，query 编码时不看文档，文档编码时不看 query——这是向量预计算的前提；
- 输出通常做 L2 归一化，使 score 落在 $[-1, 1]$，等价于余弦相似度；
- 可加温度缩放 $\text{score} = t \cdot E_q(q)^\top E_d(d)$（见 05 笔记的 z 参数化）。

### 3.2 训练：对比学习（Batch 内负样本）

给定 batch 内 N 对配对样本 $(q_i, d_i)$，相似度矩阵 $S_{ij} = E_q(q_i)^\top E_d(d_j) \in \mathbb{R}^{N \times N}$，对角线为正样本对。InfoNCE（CLIP）损失：

$$\mathcal{L} = -\frac{1}{N}\sum_{i=1}^{N} \log \frac{\exp(S_{ii}/\tau)}{\sum_{j=1}^{N} \exp(S_{ij}/\tau)}$$

要点：
- **负样本全部来自 batch 内部**（其他样本的文档 $d_j, j \neq i$ 是 $q_i$ 的负样本），所以 batch size 直接决定负样本丰富度；
- 对称版本（图像塔视角 + 文本塔视角各算一遍）更稳定；
- 目标语义：让正样本对相似度最高，让 $q_i$ 与所有其他 $d_j$ 的相似度都低——这恰好训练出"排序能力"，与检索任务天然匹配。

### 3.3 Hard Negative Mining 对检索效果的重要性

**问题**：batch 内随机负样本大多是"一眼假"的简单负样本（"猫的照片" vs "汽车贷款广告"），模型学会区分简单负样本后就收敛了，但对难负样本（"猫坐在沙发" vs "猫躺在地板"）区分能力不足——**检索里这类 hard negative 恰恰是最常见的召回错误来源**。

| 负样本类型 | 定义 | 作用 |
|-----------|------|------|
| 随机负样本（In-batch） | batch 内其他样本 | 便宜，提供基础对比信号 |
| Hard Negative | 与 query 语义相近但错配的样本 | 逼模型学到细粒度区分，显著提升检索精度 |
| 难负样本挖掘方式 | 用当前模型对全库检索，取"高相似度但错误"的样本 | 迭代式：训练 → 挖负样本 → 加进训练集再训练 |

典型做法：
1. 先用随机负样本训一个初版模型；
2. 用初版模型对全库做一次检索，把"相似度很高但 label 不匹配"的样本挑出来（如 Top-50 内错配样本）；
3. 混入训练集（比例为 1:1 或 1:3）继续训练；
4. 重复 2-3 若干轮。

> 面试加分点：hard negative 挖掘是"检索模型效果提升性价比最高"的手段，通常比换模型带来的提升更直接。代价是训练慢（每轮要做全库检索）和存在"假负样本"风险（挖出来的难样本可能是标错的真匹配），需要人工抽检。

### 3.4 双塔 vs 单塔（Cross-Encoder）：一张表说清

| 维度 | 双塔（Bi-Encoder） | 单塔（Cross-Encoder） |
|------|-------------------|----------------------|
| 编码方式 | query、doc 各自独立编码成向量 | (query, doc) 拼接后一起过 Transformer |
| 交互 | 晚期交互（late interaction，仅向量点积） | 早期交互（交叉注意力，token 级） |
| 离线预计算 | ✅ 文档向量可预存 | ❌ 无法预计算 |
| 复杂度 | query 1 次前向 + 检索 | 每个候选 1 次前向，与库规模线性 |
| 精度 | 单向量信息瓶颈，细粒度弱 | 交互充分，细粒度强 |
| 应用阶段 | 召回 | 精排 |
| 代表 | CLIP / SigLIP / 双塔 Sentence-BERT | ITM 头（BLIP）、BLIP-2 Q-Former、VLM 打分 |

**面试要会讲的信息瓶颈**：双塔把整个文档压成一个向量，丢掉了"哪个词和哪个区域对齐"的信息；cross-encoder 的 token 级交叉注意力没有这个瓶颈，所以更准——但代价就是不能预计算，只能做精排。

### 3.5 编码器选型

- 通用英文：CLIP（ViT-B/L + text transformer）、SigLIP（损失更好、训练成本低，见 05 笔记）；
- 中文：Chinese CLIP、OpenCLIP 双语变体、SigLIP2 支持多语言；
- 域内检索（电商、医学）：在域内图文对上继续微调双塔；
- 换编码器对整个检索链路影响深远（embedding 维度、分布都变），线上切换必须**双索引并存灰度**，不能直接换。

## 四、向量相似度与 ANN（近似最近邻）检索（重点）

### 4.1 精确 kNN vs 近似 ANN：取舍本质

**精确最近邻（kNN）**：暴力扫描全库，计算每个向量与 query 的距离，取最小的 K 个。复杂度 $O(N \cdot d)$，$N=10^6, d=1024$ 时单次查询要做 $10^9$ 次浮点乘加，纯 CPU 毫秒级都不够（几十~几百毫秒），GPU 上可到几毫秒但无法支持高 QPS。

**近似最近邻（ANN）**：用空间索引（树、图、倒排、量化）预先组织向量，查询时只访问一小部分数据，把复杂度降到亚线性甚至近常数。代价是**可能漏掉真正的最近邻**——用召回率（见 4.9）衡量索引质量。

| 维度 | 精确 kNN | 近似 ANN |
|------|---------|----------|
| 复杂度 | $O(N \cdot d)$ | 亚线性/近常数（$O(\log N)$ 量级） |
| 结果 | 与暴力搜索完全一致 | 近似，可能漏真实最近邻 |
| 百万级延迟 | 10~100ms+ | 1~20ms |
| 何时用 | 库里测试、小库（<10 万）、质量基准 | 一切生产环境大库 |

**一句话：精确搜索是 ANN 的"标准答案"，ANN 的所有召回率指标都以它为基准来算。**

### 4.2 相似度度量：内积、余弦、L2 的关系

三种度量的定义：

$$\text{内积}: \text{IP}(q, d) = q^\top d = \sum_i q_i d_i$$

$$\text{余弦}: \cos(q, d) = \frac{q^\top d}{\|q\|_2 \|d\|_2}$$

$$\text{L2 距离}: \|q - d\|_2 = \sqrt{\|q\|_2^2 + \|d\|_2^2 - 2 q^\top d}$$

**关键恒等式（都做 L2 归一化后）**：设 $\|q\| = \|d\| = 1$，则

$$\|q - d\|^2 = 2 - 2 q^\top d = 2(1 - \cos(q,d))$$

于是 L2 距离排序 $\Leftrightarrow$ 余弦相似度排序 $\Leftrightarrow$ 内积排序（当模长相等时）。**归一化后三者完全等价**，这就是为什么双塔输出普遍 L2 归一化、向量库默认用内积的原因。

| 度量 | 特点 | 适用场景 |
|------|------|---------|
| 内积（IP） | 未归一化时受向量模长影响，归一化后=余弦；硬件最友好（点积） | 双塔对齐向量（已归一化） |
| 余弦 | 只关心方向，忽略模长；对文本长度/图像亮度鲁棒 | 通用首选，语义相似度 |
| L2 | 关心绝对距离，模长大者天然"更远" | 未归一化向量、聚类任务 |

> 注意：**未归一化**时三者排序可能完全不同（内积偏好大模长向量）。归一化后再选度量，工程上通常直接选内积或余弦，性能上内积更快。

### 4.3 IVF：倒排文件索引

**原理（文字版）**：
1. 建索引时对所有向量跑 k-means，得到 $K$ 个聚类中心（Voronoi 中心）$\{\mu_1, ..., \mu_K\}$；
2. 每个向量分配到最近的聚类中心，落在该中心的**倒排列表（inverted list / cell）**里；
3. 查询时先算 query 到 $K$ 个聚类中心的距离，取最近的 $n_{\text{probe}}$ 个列表（nprobe 参数），只在这几个列表里暴力扫描。

```text
            聚类中心 μ₁ μ₂ μ₃ ... μ_K
                │   │   │         │
倒排列表:     [v₁,v₅][v₂][v₃,v₇]...[v₁₀]
查询 q → 与 K 个中心算距离 → 挑最近的 nprobe 个列表 → 扫描其中全部向量
```

**关键参数**：
- $K$（nlist）：聚类数。越大每个列表越短，查询越快，但中心太多导致 k-means 不稳定、向量分配不准；
- $n_{\text{probe}}$：查询访问的列表数。**nprobe 是召回率-速度的调节旋钮**——越大召回越高、越慢。经验值 nprobe 取 nlist 的 0.5%~2%。

复杂度：$O(K \cdot d)$（中心距离）+ $O(n_{\text{probe}} \cdot L \cdot d)$（列表扫描，$L$ 为平均列表长度）。**IVF 本质是"粗筛 + 细扫"，是量化（PQ）之外最常用的加速结构。**

### 4.4 HNSW：层级可导航小世界图

**原理（文字版）**：
1. 每层是一个近邻图（Navigable Small World 图）：节点是向量，边连接"近邻"；
2. **层级结构**：底层包含全部节点（第 0 层），越往上节点越稀疏（节点按概率 $p \propto e^{-L}$ 出现在更高层）；
3. 查询从**最高层**入口进入，在该层用贪心搜索（从当前节点走向所有邻居中离 query 最近的那个）找到局部最近点，然后**下探一层**继续贪心，重复到底层；
4. 底层搜索时维护一个候选集合（大小 = efSearch），搜索完取其中最近的 K 个。

```text
L2 层:   ○──○──○         （稀疏，粗粒度导航）
L1 层:   ○──○──○──○
L0 层:   ○──○──○──○──○──○  （全部节点，细粒度）

查询路径: 从 L2 进入 → 贪心逼近 → 下探 L1 → 下探 L0 → 取 K 个最近
```

**关键参数**：
- $M$（每节点最大边数）：越大图越稠密、查询越准越慢，内存越大；
- $efConstruction$：建图时候选集大小，越大图质量越好、构建越慢；
- $efSearch$：查询时候选集大小，**召回率-延迟调节旋钮**（对应 IVF 的 nprobe）。

**特点**：查询延迟稳定（图搜索路径短）、召回率极高（接近精确）、无需训练/聚类；缺点是**内存占用大**（每条边都要存，$M$ 取 32 时 100 万向量约几百 MB~GB 级）、构建慢（逐点插入）。生产小中规模库（<1000 万）首选。

### 4.5 PQ / OPQ：乘积量化压缩向量

**原理（文字版）**：
1. 把 $d$ 维向量切成 $m$ 段子向量 $x = (x^{(1)}, ..., x^{(m)})$，每段 $d/m$ 维；
2. 对每一段单独做 k-means，得到该段的码本（codebook）$C^{(j)} \in \mathbb{R}^{k \times (d/m)}$，共 $m$ 个码本；
3. 每个子向量用它最近的质心编号 $c_j \in \{1,...,k\}$ 表示，整个向量压缩成 $m$ 个编号（code），即 `c(x) = (c₁, ..., c_m)`；
4. **内存**：原来存浮点 $d \times 4$ 字节，现在存 $m \times \log_2 k$ 比特。例：$d=1024, m=128, k=256$：原 4KB → $128 \times 8 = 128$ 字节，**压缩 32 倍**；
5. **非对称距离计算（ADC, Asymmetric Distance Computation）**：query **不压缩**，对每段子向量 $j$ 先算 query 子向量到该段 $k$ 个质心的距离表 $T_j \in \mathbb{R}^{k}$（$m$ 张查表），然后：

$$d(q, x) \approx \sum_{j=1}^{m} d(q^{(j)}, C^{(j)}_{c_j}) = \sum_{j=1}^{m} T_j[c_j]$$

  查表 + 累加，全程无浮点向量运算，极快。

**OPQ（Optimized PQ）**：PQ 的前提是各段子向量独立可量化；若维度间相关性强（embedding 常有），量化误差大。OPQ 学习一个正交旋转矩阵 $R$，先旋转再切段，使各段方差均衡、互不相关，量化误差显著降低。一般公式（对各段质心做二次优化），工业实现常用"用 PCA 旋转预处理"的近似做法。

| | PQ | OPQ |
|--|----|-----|
| 预处理 | 直接切段聚类 | 先学旋转矩阵再切段聚类 |
| 量化误差 | 维度相关时偏大 | 更小 |
| 额外成本 | 无 | 旋转矩阵 + 预处理 |
| 用法 | 内存敏感场景的基础选择 | PQ 的升级版，精度更高 |

**注意**：PQ 存的是**近似向量**（距离是近似距离），所以它通常配合 IVF（用 PQ 存列表内向量的压缩表示）或 HNSW（量化做距离近似）使用，而不是单独用。

### 4.6 LOPQ：局部优化乘积量化

**原理**：PQ 的码本是**全局**的（所有向量共享一套码本）；LOPQ 先用 IVF 分桶（Voronoi cell），在**每个 cell 内部**再各学一套 OPQ 码本（local codebook）。因为每个 cell 内的向量更相似、分布更集中，局部码本能更精细地表达它们。

- 优点：召回率高于"全局 PQ + IVF"，尤其在粗粒度结构差异大的库上；
- 缺点：**码本数量 = nlist 套**，内存和构建成本上升（每套码本 $m \times k \times (d/m) \times 4$ 字节）；
- 定位：在"PQ 压缩 + 高召回"都要时使用，通常是内存受限大库（亿级）的选择。

### 4.7 NSG：导航扩展图

**原理**：NSG（Navigating Spread-out Graph）基于 KNN 图构建：
1. 建一个 KNN 图（每个节点连最近的 k 个邻居），**剪枝**去掉冗余边——保留的边要保证邻居在空间中"散布开"（相邻两条边的夹角尽量大），形成导航扩展图；
2. 保留一个**导航点（navigating node）**作为全图入口（类似 HNSW 的高层入口）；
3. 查询：从导航点出发，在图上贪心搜索（每次走向离 query 最近的邻居），维护候选集。

```text
KNN 图 → 剪枝（去掉方向重复的边）→ NSG 图（稀疏但"方向全"）
查询: 导航点 → 贪心爬山 → 候选集 → Top-K
```

与 HNSW 的对比：NSG 图更稀疏（边更少），**查询更快的潜力**、内存更小；但**构建成本高**（要先建 KNN 图，$O(N^2)$ 量级或需采样近似）。HNSW 是动态增量插入友好，NSG 更适合离线一次性构建、查询 QPS 要求极高的场景。

### 4.8 ANN 算法对比总表（必背）

| 算法 | 原理一句话 | 查询速度 | 内存 | 召回率 | 构建成本 | 适用 |
|------|-----------|---------|------|--------|---------|------|
| 暴力扫描（精确） | 全库逐条算距离 | 慢 | 原始大小 | 100%（基准） | 无 | 基准测试 |
| IVF | k-means 分桶 + 只扫 nprobe 个桶 | 中（受 nprobe 控制） | 原始向量 | 中（受 nprobe 控制） | 低（一次聚类） | 快速建索引、内存宽裕 |
| HNSW | 多层近邻图，顶层粗导航底层细搜索 | 快且稳定 | **高**（存边） | **极高**（可近精确） | 中高（逐点插入） | 小中库、高召回要求 |
| IVF + PQ | 分桶 + 量化压缩桶内向量 | 快 | **低**（压缩 20~50 倍） | 中（量化有损） | 低 | 大库、内存受限 |
| IVF + OPQ | 旋转去相关后再量化 | 快 | 低 | 中上 | 中 | 大库高质量召回 |
| LOPQ | 每桶一套局部码本量化 | 快 | 低（但码本多） | 中上 | 高 | 亿级大库 |
| NSG | 剪枝 KNN 图 + 导航点 | **快** | 中 | 高 | **高** | 离线构建、超高 QPS |

**选型经验口诀**：<100 万选 HNSW（简单可靠、召回高）；100 万~亿级选 IVF+PQ/OPQ（内存是关键约束）；亿级以上且查询极热选 LOPQ/NSG（但要接受构建成本）。

### 4.9 ANN 检索的召回率指标（重要概念辨析）

**定义**：给定 query，精确 kNN 返回的真实最近邻集合 $R_{\text{exact}}^K$，ANN 返回的集合 $R_{\text{ann}}^K$：

$$\text{Recall}@K = \frac{|R_{\text{exact}}^K \cap R_{\text{ann}}^K|}{K}$$

即"返回的 K 个结果里，有多少个是真实 Top-K"。取值 0~1，衡量**索引的近似损失**，与模型精度无关。

| 常见取值 | 含义 |
|---------|------|
| Recall@10 = 0.95 | 返回的 10 个里有 9.5 个是真实最近邻（平均） |
| Recall@1 = 1.0 | 返回的第一个就是真实最近邻 |

> **⚠️ 最容易混淆的点（面试必考）**：模型评测的 Recall@K（如双塔模型的 R@10，含义是"query 的真实相关文档出现在返回 Top-10 中的比例"）和 ANN 索引的 Recall@K（返回结果命中精确最近邻的比例）**是两个不同概念**：前者衡量模型对齐质量，后者衡量索引近似质量。生产链路里两者相乘才是端到端召回——**模型 R@10 = 0.8、索引 R@10 = 0.9，端到端约 0.72**。

## 五、向量数据库选型对比

### 5.1 选型前先回答三个问题

1. **规模**：多少向量？10 万、100 万还是 10 亿？这决定单机 vs 分布式；
2. **部署形态**：要"库"（嵌入自己服务里的 SDK）还是"服务"（独立进程/云服务）？团队有没有运维能力？
3. **场景**：纯向量检索，还是需要向量 + 标量过滤（类目、价格、时间）混合检索？

### 5.2 主流向量库/服务对比表（重点）

| 方案 | 形态 | 索引支持 | 分布式/扩展 | 持久化 | 混合过滤 | 规模能力 | 适用场景 |
|------|------|---------|------------|--------|---------|---------|---------|
| FAISS | Python/C++ **库**（非服务） | IVF、HNSW、PQ/OPQ、LOPQ、NSG | 无内置，需自建 shard | 无（需自管） | 不支持（仅向量） | 单机百万~千万级 | 算法原型、离线近邻、深度定制索引 |
| Milvus | 分布式向量**服务** | HNSW、IVF、PQ、DiskANN 等 | ✅ 存算分离、分片 | ✅ | ✅（标量过滤） | 亿级+ | 生产级大规模向量检索 |
| Qdrant | 向量服务（Rust） | HNSW（自定义变体）、PQ | ✅ | ✅ | ✅（payload 过滤） | 千万~亿级 | 需要强过滤能力的检索 |
| Weaviate | 向量服务 | HNSW 为主 | ✅ | ✅ | ✅（GraphQL） | 千万级 | 与图谱/元数据查询结合 |
| Chroma | 嵌入式库（Python） | HNSW（hnswlib） | ❌ | ✅（本地文件） | 基础过滤 | 百万级 | 原型、RAG 学习、个人项目 |
| Pinecone | 全托管云服务 | 厂商管理（HNSW/PQ 自动） | ✅（Serverless） | ✅（托管） | ✅ | 任意规模 | 不想运维、快速上线 |
| ES + kNN | 搜索引擎扩展（Lucene 引擎） | HNSW、IVF（lucene9） | ✅ | ✅ | ✅（全文+向量融合） | 千万级 | 已有 ES 栈、需文本+向量混合检索 |

**关键理解**：
- **FAISS 是库不是数据库**：它不做持久化、不做副本、不处理并发——生产用法是"FAISS 做索引引擎 + 自建存储和 API 壳"，或者干脆用 Milvus/Qdrant 这类把 FAISS/hnswlib 包起来的服务；
- **Milvus vs Qdrant**：Milvus 分布式强（存算分离、支持大规模集群），Qdrant 单机部署轻量、过滤能力强、Rust 性能好；
- **ES + kNN**：Lucene 9 起原生支持 HNSW；典型场景是"关键词召回 + 向量召回"的**混合检索**（BM25 和向量分数加权融合），图文检索里常用在"向量 + 文本标签/标题"联合过滤；
- **Pinecone**：托管省心，但数据出境、成本、厂商锁定要评估；国内常用 Milvus/Zilliz 或自建 FAISS。

### 5.3 选型决策流程（文字版）

```text
规模 < 百万，原型验证 → Chroma / 单机 FAISS
规模 百万~千万，已有运维能力 → Qdrant 或自建 FAISS 服务
规模 千万~亿级，生产级 → Milvus（分布式）
需要文本+向量混合检索 → ES + kNN（或 ES + 向量服务并行再融合）
完全不想运维 → Pinecone 等托管云
```

## 六、多模态检索的特殊问题

### 6.1 图文 embedding 的模态对齐质量

检索质量的天花板是**对齐质量**，不是向量库。要点：

| 问题 | 表现 | 对策 |
|------|------|------|
| 模态空间未对齐 | 文本搜图时文本塔和图像塔向量分布不一致 | 用对比学习训练的双塔（CLIP/SigLIP）保证同空间 |
| 单向量信息瓶颈 | 复杂 query（多物体、空间关系）召回差 | 换成更精细对齐模型（如 SigLIP2）、提高输入分辨率、多 prompt 融合 |
| 损失函数影响 | CLIP vs SigLIP 训练效率/效果差异 | 优先 SigLIP 系（见 05 笔记） |
| 域不匹配 | 通用模型在垂直域（电商/医学）效果差 | 域内数据继续微调双塔（保留对齐损失） |

**经验**：换编码器是最重的改动（全部向量要重算、索引要重建），只有在评估指标明确提升（如 R@10 +3%）时才值得做，且要新旧双索引灰度切换。

### 6.2 中文场景

| 方案 | 说明 | 取舍 |
|------|------|------|
| Chinese CLIP（OFA/智源） | 中文图文对训练的开源模型 | 中文效果好，跨语种检索弱 |
| 双语 SigLIP 微调 | 用 SigLIP 权重 + 中文图文对继续训练 | 保留英文能力 + 获得中文能力 |
| 多语言 CLIP 变体（如 SigLIP2、M-CLIP） | 原生多语言训练 | 单模型覆盖多语，但中文占比不足时中文精度有限 |
| 翻译兜底 | 中文 query 翻译成英文查英文库 | 快但翻译损失语义 |

中文特有难点：中文一词多义、口语化 query、图片上的中文 OCR 文本（需要 OCR 融入检索链路）；评测用 MUGE、Flickr30K-CN 等中文基准。

### 6.3 视频检索：抽帧 → 帧 embedding → 时间戳定位

视频不是单张图，检索粒度是**片段（clip）+ 时间戳**：

```text
视频 → 抽帧（每秒 1~2 帧，或场景切换检测抽关键帧）
   → 每帧过图像塔 → 帧 embedding
   → 相邻帧聚合（平均池化/取最大相似度）成片段级表示
   → 片段 embedding 入库（元数据带 [start_ms, end_ms]）
查询: query 文本 → 文本 embedding → 检索片段 → 返回片段 + 时间戳
```

**时间戳定位质量指标 —— Temporal IoU**：预测区间 $A=[a_1, a_2]$ 与真实区间 $B=[b_1, b_2]$ 的重叠比：

$$\text{tIoU} = \frac{|A \cap B|}{|A \cup B|} = \frac{\max(0, \min(a_2,b_2) - \max(a_1,b_1))}{\max(a_2,b_2) - \min(a_1,b_1)}$$

- tIoU 越高说明定位越准（例：tIoU ≥ 0.5 视为命中，常用指标 Recall@tIoU）；
- 抽帧密度与精度的权衡：抽帧太稀会漏掉短镜头，太密增加存储和检索成本；
- 常见坑：整段视频平均池化会把"中间无关内容"稀释掉，应做**片段级切分**（按镜头/固定 3~5 秒窗口）再分别检索。

### 6.4 分层检索：粗召回 + 精排的工程结构

```text
                    ┌────────────────────────────┐
 query ──► 双塔编码 ──► 向量库 ANN 粗召回 Top-100   │  ~15ms，覆盖全库
                    └────────────┬───────────────┘
                                 ▼
                    ┌────────────────────────────┐
                    │ Rerank（VLM/ITM 精排）Top-50 │  ~200ms，只看 100 条
                    └────────────┬───────────────┘
                                 ▼
                    业务过滤（类目/鉴黄/价格）→ Top-10 返回
```

工程要点：
- 粗召回层**超参可调**（nprobe/efSearch）提供速度-召回旋钮；
- 精排层用 batch 推理（100 条候选一起前向）摊薄 VLM 延迟；
- 两层之间缓存中间结果（query 向量、粗召回 ID 列表），避免重复计算；
- **级联代价**：粗召回漏掉的，精排永远找不回来——所以粗召回宁可宽（K 取大，如 100~200），把"准"交给精排。

### 6.5 缓存与增量更新

| 问题 | 场景 | 方案 |
|------|------|------|
| embedding 缓存 | 同一张图/同一 query 反复编码（热点图、热搜词） | query 侧 LRU 缓存 embedding；图侧入库时只算一次 |
| 增量写入 | 每天新图几十万张 | 小批量写入 + 定时合并段（segment 合并），避免频繁全量重建 |
| 删除/过期 | 下架商品、版权移除 | 逻辑删除（标记过滤）为主，向量库删除后定期触发重索引/重平衡 |
| 索引重建 | 模型升级/数据大清洗 | 双索引影子构建 → 校验召回率达标 → 原子切换流量 |
| 冷热分离 | 热数据查得快、冷数据占内存 | 热区 HNSW 常驻内存，冷区上 DiskANN/SSD 索引 |

**面试加分点**：增量更新最大的坑是"删除只做逻辑删除导致倒排列表/图结构空洞"，所以生产系统普遍设计**每日/每周定时紧凑（compaction）+ 重索引**的维护窗口。

## 七、检索效果评测

### 7.1 核心指标定义

**模型级（衡量对齐质量，用标注数据测）**：

$$R@K = \frac{1}{|\mathcal{Q}|} \sum_{q \in \mathcal{Q}} \mathbb{1}[\text{真实相关文档} \in \text{Top-K}(q)]$$

**mAP（Mean Average Precision）**：对每个 query 算 AP，再对所有 query 平均：

$$\text{AP} = \frac{1}{|R_q|} \sum_{k=1}^{N} P(k) \cdot \mathbb{1}[\text{rank}_k \text{ 是相关文档}], \quad \text{mAP} = \frac{1}{|\mathcal{Q}|} \sum_{q} \text{AP}_q$$

其中 $P(k)$ 是前 k 个结果里的精度（相关文档比例），$|R_q|$ 是该 query 的相关文档总数。mAP 同时惩罚"漏"和"排后"，比 Recall@K 更严格。

**工程级（衡量系统性能）**：
- **P95 延迟**：95% 分位查询耗时（比平均值更抗毛刺，P99 用于看极端情况）；
- **QPS**：每秒可处理的查询数 = 并发数 / 平均延迟（延迟和 QPS 是一对矛盾指标，测两者权衡曲线）；
- **显存/内存占用**：索引占多少内存、编码器 batch 推理的显存峰值。

### 7.2 评测基准表设计（benchmark 模板）

| 维度 | 指标 | 目标参考值 | 说明 |
|------|------|-----------|------|
| 检索质量 | R@1 / R@10 / mAP | 数据集相关（Flickr30K R@10 通常 >80%） | 标注测试集上测模型 |
| 索引质量 | ANN Recall@10 | ≥ 0.95 | 与暴力搜索对比 |
| 在线延迟 | P95 端到端 < 50ms | 检索链路预算 | 拆解：编码 / ANN / 过滤 |
| 吞吐 | QPS ≥ 200（单实例） | 按业务峰值 | 关注延迟-吞吐曲线拐点 |
| 资源 | 索引内存、编码器显存 | 可部署于既定机器 | 量化指数级节省的代价 |

**评测流程要点**：
1. 测试集要**人工标注真实相关对**（不能只用配对样本当正例，需补充"语义相关但不配对"的正例）；
2. 模型 A/B 对比要**固定向量库和索引参数**，只变编码器，否则测不出模型差异；
3. 指标联测：模型 R@K × 索引 Recall@K ≈ 端到端召回，两处都要盯；
4. 线上兜底：抽样人工评审 Top-K 结果（badcase 归类：语义歧义 / 对齐差 / 索引漏），定位问题层。

## 八、与 RAG 的关系：检索增强生成

### 8.1 图文检索 = VLM 的外部知识来源

RAG（Retrieval-Augmented Generation）的经典链路："query → 检索 → 拼进 prompt → LLM 生成"。多模态版本就是：

```text
用户问题 → 文本编码 → 图文库检索（图片/图文对）→ 检索结果拼入 prompt
   → VLM（如 Qwen-VL、GPT-4V）综合图片 + 文本生成回答
```

图文检索系统在这里扮演"**外部记忆**"角色：模型参数里装不下的私有知识（公司图库、商品图、文档截图、历史资料）都放到向量库里，按需取用。

### 8.2 为什么能缓解幻觉

| 幻觉来源 | 检索增强的作用 |
|---------|--------------|
| 模型参数记忆有限/过时 | 检索拿到最新事实，prompt 里有据可依，模型"照着说"而非"编" |
| 生成模型倾向流畅编造（概率解码） | 强约束：检索结果作为上下文，VLM 的图文推理以图为锚点，编造空间被压缩 |
| 多模态长尾知识（罕见物体、专有名词） | 参数里没学过的，检索直接给图片 + 描述，相当于"开卷考试" |
| 缺乏可溯源证据 | 检索结果带出处（图片 ID、来源），幻觉被复核流程兜住 |

**机理**：检索增强本质是把"参数化记忆"转成"外部可查记忆"，生成时模型做的是**对给定证据的推理和转述**，而不是无中生有。前提是**检索质量足够高**——检索返回了错误图/错误文本，VLM 会被"带偏"（级联误差），所以检索评测（第七节）直接决定 RAG 质量上限。

### 8.3 检索质量 → 生成质量（级联效应）

- 检索召回率低 → prompt 缺关键证据 → 模型被迫编造（幻觉回升）；
- 检索结果顺序错 → VLM 更信 prompt 前面的内容 → 回答被次要证据主导；
- 精排（第二级）对 RAG 尤其重要：**进 prompt 的只有 3~5 条，每一条都要准**，召回可以宽，prompt 不能脏。

> 面试话术：检索是 RAG 系统的"上流"，上流漏一分，下流掉十分；评估一个 RAG 系统，先测检索指标（R@K、mAP），再看生成指标。

## 九、高频面试问答

**Q1：双塔和单塔（cross-encoder）检索有什么区别？为什么双塔适合召回、单塔适合精排？**
双塔把 query 和 doc 各自独立编码成向量，用点积打分；单塔把两者拼接一起过 Transformer，token 级交叉注意力打分。双塔的向量可离线预计算、查询只需一次编码 + 向量检索，速度快但单向量有信息瓶颈；单塔精度高（交互充分）但每个候选都要一次完整前向，只能处理小候选集。所以工业标准是双塔召回 + 单塔（VLM）精排两级结构。

**Q2：HNSW 的原理是什么？关键参数有哪些？**
HNSW 是层级近邻图：底层包含全部向量，向上逐层稀疏（概率分层）。查询从顶层贪心导航（每步走向当前节点邻居中离 query 最近者），逐层下探到底层，在底层用大小为 efSearch 的候选集搜索取 Top-K。关键参数：M（每节点最大边数，越大越准越费内存）、efConstruction（建图候选集）、efSearch（查询候选集，召回-延迟调节旋钮）。优点是召回高、延迟稳定；缺点是内存大、增量插入有构建成本。

**Q3：IVF 的原理是什么？nprobe 怎么调？**
IVF 用 k-means 把向量空间分成 K 个 Voronoi 单元，向量按最近中心落入倒排列表。查询时算 query 到各中心的距离，只扫描最近的 nprobe 个列表。nprobe 越大访问的列表越多，召回越高、延迟越大，是召回-速度的调节旋钮；调法：画 nprobe-Recall@K 曲线，在召回率达标（如 0.95）的前提下取最小 nprobe。

**Q4：为什么用 ANN 而不是精确搜索？**
精确 kNN 复杂度 O(N·d)，百万向量单查询几十~几百毫秒，扛不住在线 QPS。ANN 用空间索引（倒排/图/量化）把复杂度降到亚线性，百万级延迟降到毫秒级，代价是可能漏真实最近邻（用 ANN Recall@K 衡量，通常做到 0.95+ 时和精确搜索几乎无差别）。规模大时是"用可容忍的精度损失换数量级的性能"。

**Q5：FAISS 和 Milvus 的区别？**
FAISS 是元库（C++/Python 库），提供 IVF/HNSW/PQ 等索引算法，但不做持久化、分布式、并发管理——需要自己包装成服务。Milvus 是基于 FAISS 等引擎的分布式向量数据库服务，内置分片、副本、持久化、标量过滤、运维能力。选择：原型和深度定制用 FAISS；生产大规模检索用 Milvus（或 Qdrant 等）。

**Q6：Recall@K 怎么算？模型 Recall@K 和索引 Recall@K 有什么区别？**
模型级：对每个 query，看真实相关文档是否出现在返回 Top-K 里，取平均（衡量对齐质量）。索引级：ANN 返回的 K 个结果中命中精确 kNN 真实 Top-K 的比例（衡量索引近似损失）。两者完全不同：前者衡量"模型找得对不对"，后者衡量"索引找没找到模型认为最近的"。端到端召回率 ≈ 两者乘积。

**Q7：怎么提升检索质量？按性价比排序。**
1) 数据与负样本：域内数据微调双塔 + hard negative mining（性价比最高）；2) 精排层：召回后加 cross-encoder/VLM 精排 Top-100；3) 编码器升级：SigLIP/更高分辨率/更大模型（代价大，需重建索引）；4) 检索细节：多 query 扩展（改写/翻译多路召回融合）、混合检索（文本 BM25 + 向量融合）；5) 索引参数：nprobe/efSearch 调到召回率曲线平台期。

**Q8：PQ 量化为什么能把内存压缩 20~30 倍？距离怎么算？**
把 d 维向量切成 m 段，每段用 k 个质心量化，存成 m 个编号：内存从 4d 字节降到 m·log₂k 比特（d=1024, m=128, k=256 时 4KB→128B）。距离用 ADC 非对称计算：query 不量化，对每段预先算好 query 到该段 k 个质心的距离表，用存储的编号查表累加得到近似距离。OPQ 加一个旋转矩阵去相关，进一步降低量化误差。

**Q9：双塔召回 + 重排为什么是工业标准？**
因为单靠任何一级都不行：双塔召回快但 Top-K 里细粒度错误多（单向量信息瓶颈）；精排模型准但只能处理小候选集（逐条打分成本与库规模线性）。两级结构把"全库规模"的问题留给快的召回，把"精度"的问题留给贵但准的精排，各自在擅长的尺度上工作。这也是"任何生产检索系统都是这个结构"的根本原因。

**Q10：视频检索怎么做？**
视频先抽帧（固定频率或镜头检测），每帧过图像塔得到帧 embedding；按镜头/固定窗口聚合（平均或取最大相似度）成片段级向量入库，元数据带起止时间戳。查询时文本编码后检索片段，返回片段和定位区间，用 Temporal IoU 衡量定位精度。难点是抽帧密度权衡、长视频片段切分、以及时间戳边界的精准度。

## 十、常见误区

**误区 1：向量检索就是"存 embedding 然后暴力扫一遍"。**
错。生产级检索必须用 ANN 索引（IVF/HNSW/PQ），暴力扫描只存在于原型和小库。面试谈检索系统一定要说索引结构、参数（nprobe/efSearch）和召回-速度权衡。

**误区 2：模型 R@K 好 = 系统检索好。**
错。R@K 只测了模型，没测索引：索引近似损失（ANN Recall@K）和工程延迟（P95/QPS）都是独立维度。线上效果 = 模型质量 × 索引质量 × 工程延迟的乘积关系。

**误区 3：检索结果越准越好，所以只上精排不召回。**
错。没有召回层的精排在大库上不可行（逐条打分随库线性增长）；没有精排的召回层精度不够。两级结构不是可选项而是标准答案——召回求全、精排求准。

**误区 4：FAISS 就是向量数据库。**
错。FAISS 是索引库，不提供持久化、分布式、并发服务。生产中要么自己包装，要么选 Milvus/Qdrant 等服务型产品。回答"FAISS 和 Milvus 的区别"是高频考点。

**误区 5：IVF 和 HNSW 可以随便换着用，效果差不多。**
错。两者原理不同（倒排分桶 vs 层级图），参数、内存、召回特性不同：HNSW 召回高但内存大，IVF 内存友好但召回依赖 nprobe；大库还要叠加 PQ/OPQ 压缩。选型要按规模、内存预算、延迟要求做权衡。
