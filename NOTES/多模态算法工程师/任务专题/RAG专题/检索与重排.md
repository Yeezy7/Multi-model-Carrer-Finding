# 检索与重排：chunking、向量化、混合检索与 Rerank

> 本模块索引见 [RAG专题详解](RAG专题详解.md)

检索是 RAG 的中游枢纽，也是决定 RAG 质量的天花板：**检索漏一分，生成掉十分**。本篇把"文档怎么切 → 怎么向量化 → 怎么召回 → 怎么重排"这条主链路讲透，重点放在混合检索（RRF 融合）与重排（Rerank）两个高频考点。

## 一、文档切分（Chunking）策略

切分的本质：把长文档切成"检索时能独立命中的语义单元"。chunk 太大 → 一个片段里混进多个主题，检索粒度粗、相关度被稀释；chunk 太小 → 上下文残缺，实体/论点被切断，模型拿到碎片拼不出完整答案。

| 策略 | 原理 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- | --- |
| 固定长度 | 按固定 token/字符数切（如 256 token 一刀） | 实现简单、开销可预测、索引均匀 | 切断语义边界，产生大量废块 | 起步原型、均匀短文（新闻稿、公告） |
| 重叠窗口 | 固定长度 + 相邻块重叠 10~20% | 保住跨块语义（句/实体不丢） | 冗余存储、检索结果重复 | 长文连续叙述（论文正文、说明书） |
| 语义切分 | 按语义边界切：段落/句子向量相似度突变点切块 | 块内语义自洽，检索命中质量高 | 需要额外模型/算法，块大小不均 | 内容主题跳变明显的文档（教材、博客） |
| 按结构切分 | 按 Markdown 标题/章节、PDF 版面、表格边界切 | 保留文档层级，可做"父子块"检索 | 依赖结构化文档，实现成本最高 | 技术文档、手册、课程资料（最推荐） |

工程经验：

1. **默认起点**：512 token 一块 + 15% 重叠，再按文档类型调参；
2. **结构化文档优先按结构切**：Markdown 用标题层级（## → ###）切，配合"父子块"——子块用于检索、父块用于送 prompt，兼顾精度与上下文完整性；
3. **切分效果直接进评测**：换切分策略后必须复测检索侧 Recall@K，切分是"零训练成本的调优"，性价比极高；
4. 表格/代码/图片块要整块保留，不要从中间截断（详见 [多模态RAG与评估.md](多模态RAG与评估.md) 版面切分一节）。

### 1.1 父子块（Parent-Child Chunking）：解决"检索粒度 vs 上下文完整"的矛盾

一个 chunk 太小则上下文残缺，太大则检索命中不精准——父子块用两级结构同时满足：

```
父块（大，如整个章节 ~2048 token）── 送进 prompt，提供完整上下文
子块（小，如其中一小节 ~256 token）── 做向量化与检索
命中子块 ──► 回溯到所属父块 ──► 把整个父块拼进 prompt
```

- 检索用子块（粒度细、命中精准），生成用父块（上下文完整、前后文连贯）；
- 实现：子块存"父块 ID"元数据，检索返回子块后按 ID 取父块内容；
- 代价：prompt 变长（送的是父块），需要控制父块上限。

## 二、向量化（Embedding）

把文本/图像映射成稠密向量的模型称为 embedding 模型（双塔编码器，其训练与评测详见 [图文检索与向量库](../../算法论文基础/14_图文检索与向量库.md)）。

### 2.1 文本 embedding 模型

| 模型 | 特点 | 典型用途 |
| --- | --- | --- |
| bge（BAAI） | 中文强、带 instruction 前缀技巧，R@1 高 | 中文文档 RAG 首选 |
| m3e / text2vec | 轻量、部署友好 | 小规模知识库 |
| OpenAI text-embedding-3 | 英文强、支持 Matryoshka 降维 | 英文为主、云服务 |
| E5 / GTE | 多语言通用 | 跨语言检索 |

**选型铁律：中文场景用中文/双语模型，英文场景用英文模型；跨语言检索必须验证对齐质量，别拿英文模型硬跑中文库。**

### 2.2 多模态 embedding 模型

- **CLIP / SigLIP**：图文对比学习，把图像与文本编码到同一向量空间，是图文库检索的标准底座；
- **对齐问题的本质**：文本 query 和图像/文档块要落在"同一个语义空间"才能比余弦——对齐质量决定检索质量（详见 [多模态RAG与评估.md](多模态RAG与评估.md) 与 [图文检索与向量库](../../算法论文基础/14_图文检索与向量库.md)）；
- 多向量方案（ColBERT 等）：一个文档用一组向量而非单向量，缓解单向量信息瓶颈，但检索成本高。

### 2.3 向量化的两个工程要点

1. **归一化**：双塔输出做 L2 归一化后，余弦、内积、欧氏距离排序等价，向量库默认用内积（详见 [图文检索与向量库](../../算法论文基础/14_图文检索与向量库.md) 第四节证明）；
2. **离线入库**：全部文档的向量化在入库阶段一次性完成，在线 query 只编码一次文本，视觉塔计算从在线路径移到离线路径（大图库的成本关键点）。

## 三、检索：向量召回、BM25 与混合检索

### 3.1 向量检索（稠密检索）

query 与文档各自编码为向量，按余弦相似度取 Top-K：

$$\text{sim}(q, d) = \frac{q \cdot d}{|q|\,|d|} = \sum_{i=1}^{D} \hat{q}_i \hat{d}_i \quad (\hat{\cdot}\ \text{为 L2 归一化后向量})$$

- 优点：**语义相似**——"如何提升模型表现"能命中"模型性能优化方法"，词面不同也能召回；
- 缺点：依赖 embedding 对齐质量；对专有名词、精确 ID、代码符号不敏感（"API v3.2" 这种字面精确需求反而搜不准）。

### 3.2 BM25 稀疏检索

BM25 是"关键词精确匹配 + 统计加权"的经典稀疏检索：

$$\text{BM25}(q, d) = \sum_{t \in q} \text{IDF}(t) \cdot \frac{f(t, d)(k_1 + 1)}{f(t, d) + k_1\left(1 - b + b\frac{|d|}{\text{avgdl}}\right)}$$

$$\text{IDF}(t) = \log\left(\frac{N - n(t) + 0.5}{n(t) + 0.5} + 1\right)$$

参数含义：$f(t,d)$ 为词 $t$ 在文档 $d$ 中的词频；$|d|$ 为文档长度、$\text{avgdl}$ 为库内平均长度；$k_1$（默认 1.5）控制词频饱和程度，$b$（默认 0.75）控制长度惩罚强度；$N$ 为文档总数，$n(t)$ 为含词 $t$ 的文档数（DF）。

- 优点：**字面精确**、无需训练、可解释、冷启动快，专有名词/ID/代码命中率高；
- 缺点：词面不同即召回失败——同义词、改写、口语化 query 全漏。

### 3.3 稠密 vs 稀疏：一张表讲清互补性

| 对比项 | 稠密检索（向量） | 稀疏检索（BM25） |
| --- | --- | --- |
| 匹配粒度 | 语义相似 | 字面词项 |
| "如何提升模型表现" vs "模型性能优化方法" | 命中 ✓ | 漏 ✗ |
| "查一下 API v3.2 的文档" vs 精确含 "API v3.2" 的文档 | 可能漏 ✗ | 命中 ✓ |
| 是否需要训练 | 需要 embedding 模型 | 无需训练 |
| 依赖 | 对齐质量 + 向量库 | 分词器 + 词频统计 |
| 冷启动 | 模型未适配域内文本时效果差 | 直接可用 |
| 可解释性 | 黑盒 | 每个命中词项可枚举 |

**结论：两者是正交的互补，不是二选一**——这就是混合检索存在的全部理由。

### 3.3 混合检索 + RRF 融合（重点）

向量检索"懂语义不懂字面"，BM25"懂字面不懂语义"，**混合检索 = 两路各召回 Top-K，再融合成一个排名**。直接按分数加权不可靠（两路分数分布不同），工业标准是用**倒数排名融合（Reciprocal Rank Fusion, RRF）**：

$$\text{RRFScore}(d) = \sum_{r \in R} \frac{1}{k + \text{rank}_r(d)}$$

其中 $R$ 是参与融合的检索器集合，$\text{rank}_r(d)$ 是文档 $d$ 在检索器 $r$ 中的排名（从 1 起），$k$ 是平滑常数（**默认 60**，防止排名第 1 的文档权重过大）。

**推导直觉**：$\frac{1}{k+\text{rank}}$ 随排名单调递减、压缩头部差距——第 1 名贡献 $\frac{1}{61} \approx 0.0164$，第 5 名贡献 $\frac{1}{65} \approx 0.0154$，差距不大；但"只在某一路排第 60 名"（贡献约 0.0083）则明显吃亏。因此 RRF 奖励的是"**多路都靠前**"的文档，惩罚"单路侥幸上榜"的文档。

**示例**（$k=60$，两路各取 Top-10 融合；未进某路 Top-10 的文档视为该路无排名、不贡献）：

| 文档 | 向量检索排名 | BM25 排名 | RRF 得分（k=60） |
| --- | --- | --- | --- |
| A | 1 | 15 | 1/61 + 1/75 ≈ 0.0297 |
| B | 6 | 4 | 1/66 + 1/64 ≈ 0.0308 |
| C | 3 | —（未进 Top-10） | 1/63 ≈ 0.0159 |

B 虽然两路都不是第一，但**两路都靠前**，RRF 得分最高；C 只在向量路排第 3，总得分反而垫底——这就是融合的意义：用两路的共识替代单一模型的判断。

工程要点：RRF 只关心排名不关心原始分数，所以两路可以任意换模型、换打分方式而无需重标定，这是它比"分数加权"优雅的根本原因。

## 四、重排（Rerank）（重点）

### 4.1 为什么召回要快、排序要准

检索是"全库规模"的问题，排序是"小候选集规模"的问题，必须用两种不同模型分别解决：

| 对比项 | 双塔（召回用） | cross-encoder（重排用） |
| --- | --- | --- |
| 打分方式 | query 和 doc 各自独立编码成向量，余弦/内积打分 | query 与 doc 拼接成一条序列，过 Transformer，token 级交叉注意力打分 |
| 能否预计算 | 能，doc 向量离线算好入库 | 不能，每次打分都要完整前向 |
| 查询成本 | 一次 query 编码 + 向量库 ANN 检索，全库毫秒级 | 每个候选都要一次前向，成本与候选数线性 |
| 精度 | 单向量有信息瓶颈（query-doc 交互被压缩成一次点积） | 交互充分，精度显著更高 |
| 典型位置 | 召回层（Top-100） | 精排层（Top-100 → Top-N） |

**根本原因**：双塔牺牲了 query 与 doc 的 token 级交互，换来了"doc 向量离线预计算 + ANN 索引"这一数量级的性能优势；cross-encoder 把交互做足，但只能负担几十~几百条候选。所以工业标准是两级结构——**召回求全（快），重排求准（贵但只在小集合上贵）**。

### 4.2 top-N 重排流程

```
双塔召回 Top-100 ──► cross-encoder 逐条打分 ──► 按分数重排 ──► 取 Top-5 进 prompt
     (~10ms)         (100 条拼 batch 一次前向)      (排序)          (只有 N 条)
```

延迟账：100 条候选对（[CLS]q[SEP]d 拼接）打包成一个 batch 过一次 reranker，GPU 上单次前向约 10~50ms；若逐条串行才需要 100 次前向（数百 ms）——**必须 batch 推理**。这就是为什么"重排成本高"在实际系统中可控。

### 4.3 rerank 模型与双塔的差异（面试细节）

1. **交互方式**：双塔是"先压缩再比较"（各自编码后一次点积），rerank 是"先比较再压缩"（token 互看后逐层融合），后者能捕捉"苹果是水果还是公司"这类需要 query 上下文消歧的细粒度相关性；
2. **输入长度**：rerank 输入是 q+doc 的拼接序列，长度受限（常见 512~4096），所以只能处理小候选集，也解释了为什么 rerank 不能直接当召回用；
3. **训练方式**：双塔用对比损失（InfoNCE，看 [对比学习与CLIP](../../算法论文基础/04_对比学习与CLIP.md)）；rerank 常用排序损失（pairwise/listwise，如 RankNet、ListMLE）直接优化排序质量；
4. **效果定位**：rerank 主要修正**相对顺序**而非新增命中——召回没召到的文档，rerank 也无能为力，所以"先保证召回率，再上重排提精度"。

### 4.4 rerank 模型选型与效果度量

- **常用模型**：bge-reranker（中文强）、Cohere Rerank、Jina Reranker、或直接用自家精排 VLM 微调；
- **度量指标**：重排层用 **nDCG@K**（位置加权：排在前面的正确项权重更高）最贴切；对比召回层的 Recall@K/MRR，nDCG 还惩罚"正确项排太后"的损失；
- **nDCG 公式**（$rel_i$ 为第 $i$ 位相关性打分，IDCG 为理想排序下的 DCG）：

$$\text{DCG@K} = \sum_{i=1}^{K} \frac{2^{rel_i} - 1}{\log_2(i+1)}, \qquad \text{nDCG@K} = \frac{\text{DCG@K}}{\text{IDCG@K}}$$

- **调参路径**：召回 Top-K 取多少？K 太小则正确项可能没进来（rerank 无能为力），K 太大则 batch 变大、延迟上升——经验上 50~100 起步，画"K - nDCG@5"曲线找平台期。

## 五、查询改写与路由

检索的入口是 query，query 质量直接决定检索质量。Advanced/Modular RAG 在查询侧做三件事：

1. **查询改写（Rewrite）**：用 LLM 把口语、指代、多轮对话压缩成检索友好的独立问句——"它那个方法后来怎么样了" → "该方法后续的改进版本是什么"；
2. **查询扩展（Expansion）**：一个 query 扩展成多路（翻译、同义、子问题），各路各自检索后 RRF 融合——"多路召回、一路融合"，提升召回率；
3. **HyDE（Hypothetical Document Embeddings）**：先让 LLM 基于 query 生成一段"假设答案"，再拿假设答案的 embedding 去检索。原理：query 与文档在向量空间里往往"表达不对称"（问句向量 vs 陈述句向量），而假设答案与真实文档都是陈述式，距离更近：

$$\text{HyDE}: q' = \text{LLM}(q), \quad \text{retrieve}(q') \ \text{（拿} q' \text{的向量去检索）}$$

   HyDE 示例：query"食堂的番茄炒蛋多少钱"→ LLM 生成假设答案"食堂套餐中番茄炒蛋的售价为 8 元，属于小炒类"→ 拿这段陈述句去向量检索，比直接拿问句检索更容易命中"番茄炒蛋 8 元"的菜单文档。代价：每次检索多一次 LLM 生成，延迟换取召回率。

4. **查询路由（Routing）**：Modular RAG 的招牌能力——LLM/轻量分类器判断"这个问题该走向量库 / BM25 / 网页搜索 / 还是直接回答"，避免无关检索引入噪音（如闲聊问题直接答，不检索）。

## 六、源码实现：手写小型 RAG 检索管线（可运行）

纯 Python（无第三方依赖），演示"文档库 → embedding → 向量 Top-K → BM25 Top-K → RRF 融合 → 排序输出"完整链路。

```python
import math
import random

DOCS = [
    "Transformer 模型使用自注意力机制处理序列",
    "自注意力通过查询 键 值三个矩阵计算",
    "CLIP 模型把图片和文本编码到同一个向量空间",
    "SigLIP 使用成对二元分类损失改进 CLIP",
    "向量检索用余弦相似度衡量文本相关性",
    "BM25 是基于词频与逆文档频率的稀疏检索算法",
    "重排序模型把查询和文档拼接后计算相关性",
    "混合检索融合稠密向量与稀疏关键词的结果",
]

def tokenize(text: str) -> list:
    """中文按字切分，英文单词按词切分"""
    tokens, cur = [], []
    for ch in text.lower():
        if "\u4e00" <= ch <= "\u9fff":          # 汉字：单独成 token
            if cur:
                tokens.append("".join(cur)); cur = []
            tokens.append(ch)
        elif ch.isalnum() or ch in "._-":
            cur.append(ch)                        # 字母/数字：攒成单词
        else:
            if cur:
                tokens.append("".join(cur)); cur = []
    if cur:
        tokens.append("".join(cur))
    return tokens

# ---------- 1. 模拟 embedding：每个 token 一个固定随机向量，文档向量=词向量平均 ----------
DIM = 16
rng = random.Random(42)
VEC = {}
def tok_vec(t):
    if t not in VEC:
        v = [rng.gauss(0, 1) for _ in range(DIM)]
        n = math.sqrt(sum(x * x for x in v)) or 1.0
        VEC[t] = [x / n for x in v]
    return VEC[t]

def doc_vec(tokens):
    vec = [0.0] * DIM
    for t in tokens:
        vec = [a + b for a, b in zip(vec, tok_vec(t))]
    n = math.sqrt(sum(x * x for x in vec)) or 1.0
    return [x / n for x in vec]

def cos(a, b):
    return sum(x * y for x, y in zip(a, b))

# ---------- 2. BM25 稀疏检索 ----------
def bm25_score(q_tokens, d_tokens, corpus, k1=1.5, b=0.75):
    n_docs = len(corpus)
    avgdl = sum(len(d) for d in corpus) / n_docs
    dl, score = len(d_tokens), 0.0
    for t in set(q_tokens):
        df = sum(1 for d in corpus if t in d)
        idf = math.log((n_docs - df + 0.5) / (df + 0.5) + 1.0)
        tf = d_tokens.count(t)
        score += idf * tf * (k1 + 1) / (tf + k1 * (1 - b + b * dl / avgdl))
    return score

# ---------- 3. RRF 融合 ----------
def rrf_fuse(rank_lists, k=60):
    scores = {}
    for ranks in rank_lists:
        for pos, doc_id in enumerate(ranks, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + pos)
    return sorted(scores.items(), key=lambda x: -x[1])

# ---------- 4. 完整管线：query → 两路召回 → 融合 ----------
corpus = [tokenize(d) for d in DOCS]
query = "如何把图片和文本的语义向量做相似度检索"
q_tokens = tokenize(query)
q_vec = doc_vec(q_tokens)

vec_top = sorted(range(len(corpus)),
                 key=lambda i: -cos(q_vec, doc_vec(corpus[i])))[:5]
bm25_top = sorted(range(len(corpus)),
                  key=lambda i: -bm25_score(q_tokens, corpus[i], corpus))[:5]

print("向量检索 Top-5:", [i + 1 for i in vec_top])
# 向量检索 Top-5: [5, 3, 2, 1, 7]   —— 语义路：5(余弦相似度)、3(CLIP 图文编码) 领先
print("BM25 检索 Top-5:", [i + 1 for i in bm25_top])
# BM25 检索 Top-5: [5, 3, 8, 7, 6]  —— 字面路：5、3 依旧靠前，8(融合)、7(拼接) 字面命中
fused = rrf_fuse([vec_top, bm25_top])
print("RRF 融合 Top-5:")
# RRF 融合 Top-5:
for i, score in fused[:5]:
    print(f"  文档 {i+1}  RRF={score:.4f}   {DOCS[i]}")
#   文档 5  RRF=0.0328   向量检索用余弦相似度衡量文本相关性
#   文档 3  RRF=0.0323   CLIP 模型把图片和文本编码到同一个向量空间
#   文档 7  RRF=0.0310   重排序模型把查询和文档拼接后计算相关性
#   文档 2  RRF=0.0159   自注意力通过查询 键 值三个矩阵计算
#   文档 8  RRF=0.0159   混合检索融合稠密向量与稀疏关键词的结果
# 解读：文档 5、3 两路都进前五 → RRF 得分最高；文档 7 靠字面命中（向量路第 5）
# 加分；文档 2 只有向量路前五、BM25 路没进 → 得分骤降到 0.0159 量级。

# ---------- 5. 重排：模拟 cross-encoder，对 RRF 前 5 名逐条"精排打分" ----------
def rerank_score(q_tokens, d_tokens):
    """模拟交叉注意力：共享词越多 + 语义向量越近 → 分数越高"""
    overlap = len(set(q_tokens) & set(d_tokens))
    return overlap + cos(q_vec, doc_vec(d_tokens)) * 2.0

rerank_candidates = fused[:5]
reranked = sorted(
    ((i, rerank_score(q_tokens, corpus[i]), DOCS[i]) for i, _ in rerank_candidates),
    key=lambda x: -x[1])
print("\nRerank 后 Top-3:")
# Rerank 后 Top-3:
for i, s, text in reranked[:3]:
    print(f"  文档 {i+1}  精排分={s:.3f}   {text}")
#   文档 5  精排分=9.713   向量检索用余弦相似度衡量文本相关性
#   文档 3  精排分=8.311   CLIP 模型把图片和文本编码到同一个向量空间
#   文档 8  精排分=5.005   混合检索融合稠密向量与稀疏关键词的结果
# 解读：精排分 = 共享词数 + 2×余弦。文档 5 与 query 共享 9 个词（检/索/向/量/
# 相/似/度/文/本…）且余弦最高 → 稳居第一；文档 3 共享 8 个词 → 升到第二；
# 文档 8 靠 5 个共享词挤进前三，而 RRF 排第 3 的文档 7 只有 4 个共享词、掉到第 4
# ——重排用"词级交互"修正了融合排名的粗粒度（这正是双塔做不到的）。
```

## 七、常见问题与排查

| 问题 | 表现 | 常见原因 | 排查/解法 |
| --- | --- | --- | --- |
| 召回不全 | 相关文档没进 Top-K，答案无从谈起 | chunk 粒度不当、embedding 域不匹配、缺混合检索 | 换切分策略、换对齐模型、加 BM25 路 RRF 融合 |
| 语义漂移 | query 与文档表述差异大（口语 vs 书面） | 单路向量检索、无查询改写 | query 改写 / 扩展 / HyDE 多路召回 |
| chunk 边界切断语义 | 实体、论点被切在相邻两块里 | 固定长度硬切 | 重叠窗口、结构切分、父子块 |
| 证据冲突 | 库里矛盾文档同时被召回 | 多版本文档共存 | 元数据（版本/时间）过滤 + 路由 |
| 知识过时 | 检索到旧版本内容 | 索引更新不及时 | 增量入库、版本号、定时重建索引 |
| 重排失效 | Top-5 精度提不上去 | 召回层已漏掉正确项 | 回到召回层：加路、换模型、调 chunk |

排查方法论：**先用检索侧指标（Recall@K/MRR）定位问题在召回还是重排，再改对应环节**——不要一上来就换生成模型，检索是天花板。

## 八、高频面试问答

**Q1：RAG 和微调的区别？**
RAG 把知识放权重之外，检索后拼 prompt 生成，更新快、可溯源、无需训练；微调把知识写进权重，改行为强但更新贵、不可溯源、有灾难性遗忘。知识类需求用 RAG，能力类需求用微调，生产系统两者组合。

**Q2：为什么需要重排（Rerank）？**
双塔召回快（doc 向量可预计算 + ANN 索引）但精度有信息瓶颈；cross-encoder 交互充分、精度高但逐条前向太贵。两级结构：双塔在毫秒级从全库粗召回 Top-100，cross-encoder 只在这 100 条上精排取 Top-N 进 prompt——"召回求全、重排求准，各自在擅长的规模上工作"。

**Q3：混合检索是什么？为什么有效？**
向量检索懂语义不懂字面，BM25 懂字面不懂语义。混合检索 = 两路各召回 Top-K 再融合，同时覆盖语义相近与精确匹配两类需求，专有名词、ID、口语化表达都救得回来。融合用 RRF 排名融合而不是分数加权，因为两路分数分布不可比。

**Q4：RRF 怎么算？给个例子。**
$\text{RRFScore}(d) = \sum_{r \in R} \frac{1}{k + \text{rank}_r(d)}$，k 默认 60。例：文档 A 向量路第 1、BM25 路第 15 → 1/61+1/75≈0.0297；文档 B 两路分别第 6、4 → 1/66+1/64≈0.0308，B 胜出——"多路都靠前"胜于"单路第一"。

**Q5：chunk 大小怎么定？**
没有银弹。经验起点 512 token + 15% 重叠，结构化文档按 Markdown 标题/版面切；切分后必须复测检索侧 Recall@K 验证，切分是零训练成本的最优调优点。

**Q6：双塔和 cross-encoder 的本质区别？**
双塔先压缩再比较（独立编码 + 点积），向量可预计算、靠 ANN 撑全库规模；cross-encoder 先比较再压缩（拼接 + 交叉注意力），精度高但每次都要前向，只能处理小候选集。前者是召回标配，后者是精排标配。

**Q7：HyDE 是什么？原理？**
先用 LLM 基于 query 生成"假设答案"，拿假设答案的向量去检索。原理是 query（问句）与文档（陈述句）在向量空间表达不对称，而假设答案与真实文档都是陈述式、距离更近。代价是每次多一次 LLM 生成，延迟换召回。

**Q8：检索效果差，怎么排查？**
分层定位：先看检索侧指标（Recall@K/MRR）——低则问题在召回（切分/embedding/缺混合检索），高而生成差则问题在重排或 prompt 组装；再逐环节验证（badcase 归类：语义歧义 / 对齐差 / 切分坏）。
