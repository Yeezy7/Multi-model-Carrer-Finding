## 一、一句话解释

**RAG（Retrieval-Augmented Generation，检索增强生成）= 先检索相关的知识片段，再让 LLM/VLM 基于这些片段生成回答。**

拆成三步理解：

1. **检索**：从外部知识库（文档库 / 图库 / 数据库）中按 query 找出最相关的 Top-K 片段；
2. **增强**：把这些片段（原文 + 来源）拼进 prompt，作为生成的"开卷材料"；
3. **生成**：模型不再只靠参数里的记忆"闭卷答题"，而是基于证据做转述、推理与综合。

RAG 主要解决三类问题：

| 问题 | 表现 | RAG 的解法 |
| --- | --- | --- |
| 幻觉 | 模型对没学过的事实"一本正经地编" | 检索给出证据，模型"照着材料说"，编造空间被压缩 |
| 知识过时 | 预训练数据截止于某个时间点，之后的事实一概不知 | 检索指向最新文档库，换文档即换知识 |
| 私有知识 | 公司文档、个人资料、商品图库不在训练数据里 | 检索提供外部通道，不经过训练直接可用 |

一句话记忆：**"开卷考试"——答案来源从"脑子里"换成"参考资料 + 大脑推理"，参考资料还可以随时换。**

## 二、RAG 完整链路图

RAG 由两条链路组成：离线入库（一次做、批量跑）和在线查询（每次问答跑一遍）。

```
① 离线入库链路
┌─────────────────────────────────────────────────────────────┐
│  文档/图库 ─► 切分 Chunk ─► Embedding ─► 向量库 + 元数据        │
│  (PDF/Markdown)  (文本块/图像块)  (向量)   (ANN索引,来源/页码)    │
└─────────────────────────────────────────────────────────────┘

② 在线查询链路
┌──────────────────────────────────────────────────────────────────┐
│ query ─► 查询改写 ─► Embedding ─► 向量检索 Top-K ─┐                │
│ (问题)    (扩展/HyDE)   (同一塔)   (ANN 毫秒级)    ├► 重排 Rerank ─►  │
│ query ────────────────► BM25 稀疏检索 Top-K ─────┘  (精排 Top-N)     │
└──────────────────────────────────────────────────────────────────┘
        ─► 拼接 prompt（原文片段+来源） ─► LLM/VLM 生成 ─► 带引用的答案
```

各环节一句话定位（详细展开见 [检索与重排.md](检索与重排.md)）：

| 环节 | 输入 | 输出 | 一句话要点 | 详解 |
| --- | --- | --- | --- | --- |
| 切分 Chunking | 原始文档 | chunk 列表 | 块是检索与送 prompt 的最小单元，大小直接决定检索粒度 | [检索与重排.md](检索与重排.md) 第一节 |
| 向量化 | chunk 文本/图像 | 向量 | 文本塔（bge/m3e）与视觉塔（CLIP/SigLIP），同空间可比才能比相似度 | [检索与重排.md](检索与重排.md) 第二节 |
| 入库 | 向量 + 元数据 | ANN 索引 | 向量库（FAISS/Milvus）建索引，牺牲极小精度换毫秒级检索 | [图文检索与向量库](../../算法论文基础/14_图文检索与向量库.md) 第五、六节 |
| 召回 | query | Top-K | 向量路 + BM25 路多路召回求全，RRF 融合排名 | [检索与重排.md](检索与重排.md) 第三节 |
| 重排 | Top-K | Top-N | cross-encoder 精排求准，只有 Top-N 进 prompt | [检索与重排.md](检索与重排.md) 第四节 |
| 生成 | prompt（证据 + 问题） | 答案 | LLM/VLM 依据证据转述推理，可标注来源 | [多模态RAG与评估.md](多模态RAG与评估.md) 第二、三节 |

## 三、为什么 RAG 而不是只微调

微调（SFT）是把知识"写进权重"，RAG 是把知识"放在权重之外"。两条路解决的不是同一类问题：

- **微调擅长改造行为**：让模型学会某任务的格式、风格、推理方式（如"按 JSON 输出"）；
- **RAG 擅长补充知识**：让模型拿到权重里没有的最新/私有/长尾信息；
- **两者可以叠加**：微调决定"怎么答"，RAG 决定"用什么答"，工业界主流是"微调行为 + RAG 喂料"的组合。

| 维度 | 只微调（SFT） | 只 RAG | RAG + 微调 |
| --- | --- | --- | --- |
| 知识更新速度 | 天~周级（要重训） | 分钟级（换文档即生效） | 兼具 |
| 私有/新知识 | 需收集标注数据 + 训练 | 直接入库即用 | 同 RAG |
| 可追溯性 | 无（黑盒，答了不知道依据） | 强（每句可带引用来源） | 强 |
| 幻觉控制 | 弱（仍靠参数记忆"闭卷"） | 中~强（证据约束） | 强 |
| 一次性成本 | 训练 GPU + 数据标注人力 | 向量化 + 检索服务部署 | 两者之和 |
| 推理成本 | 低（纯生成） | 略高（多一次检索 + 更长 prompt） | 略高 |
| 行为改造（格式/风格） | 强 | 无 | 强 |
| 失败模式 | 灾难性遗忘、过拟合旧数据 | 检索不准时"被证据带偏" | 组合后仍受检索质量上限约束 |

**结论**：知识类需求优先 RAG（便宜、快、可溯源）；能力类需求才微调；生产系统几乎都是组合。

**为什么微调"补知识"天生不划算**：

1. **知识不可枚举**：模型参数是有限的（70B ≈ 1.4×10¹¹ 参数），而文档世界是无限的——"不断微调喂知识"的边际成本无限上升，RAG 的边际成本只是文档入库；
2. **更新成本不对等**：一次知识更新 = 一次微调（收集数据 → 训练 → 评测 → 灰度），周期天~周；RAG 换一份文档，分钟级生效；
3. **灾难性遗忘**：微调新知识会冲刷旧知识，需要回放数据保平衡；RAG 不存在遗忘问题，文档删掉知识就"撤回"；
4. **可追溯性**：微调后的回答无法指出"这句话依据哪份文档"；RAG 天然带引用。

**什么时候必须微调（RAG 替代不了的）**：模型不懂任务的输入输出格式（如按固定 JSON schema 输出、遵循某领域写作风格）、推理能力不足（复杂的领域推理链）、生成风格要求高（客服话术）。这些属于"能力"而非"知识"，检索喂再多材料也没用。

### 3.1 成本对比数字示例（10 万文档的企业知识库）

| 成本项 | 只微调 | 只 RAG |
| --- | --- | --- |
| 数据准备 | 清洗 + 人工标注 QA 对（数人·周） | 文档整理入库（数人·天） |
| 一次性开销 | GPU 微调训练（数千~数万元/轮） | embedding 离线编码（CPU 即可，小时级） |
| 知识更新 | 每轮重训 + 回归评测（天~周） | 增量入库，分钟级生效 |
| 硬件要求 | 训练卡（A100/H100 级） | 检索服务（CPU 也能扛，GPU 仅生成时用） |
| 回归风险 | 灾难性遗忘、旧行为漂移 | 检索质量劣化（可回滚文档） |

数字的启示：**知识规模越大、更新越频繁，RAG 的成本优势越悬殊**；这也是为什么企业内部知识库、客服助手几乎清一色走 RAG。

## 四、RAG 演进：Naive → Advanced → Modular

| 阶段 | 核心结构 | 新增能力 | 代表技术 | 典型局限 |
| --- | --- | --- | --- | --- |
| Naive RAG | 切分 → 向量检索 → 拼 prompt → 生成 | 最基础的检索增强 | 首个 RAG 论文（2020 Facebook） | 检索质量决定一切，召回差则全盘崩；一次检索无反馈、无修正 |
| Advanced RAG | 在 Naive 的检索**前后**加优化 | 让"检索得更好" | 查询改写、HyDE、多路检索、混合检索（BM25+向量+RRF）、Rerank、上下文压缩 | 仍是单轮静态管线，检索失误无法自纠 |
| Modular RAG | 把 RAG 拆成可编排的独立模块 | 让"系统更聪明" | 查询路由（Routing）、多检索器编排、记忆模块、Self-RAG 反思、Agentic RAG（多轮规划检索） | 工程复杂度高，需要编排框架与评测兜底 |

关键理解：**演进的主线不是生成模型更强，而是"检索这一环越来越讲究"**——从"只做一次向量召回"到"多路召回 + 精排 + 按需路由"。面试答"RAG 现在发展成什么样"时，按这条主线讲就能站住。

- Naive RAG 三件套：切分、embedding、拼接；
- Advanced RAG 加四件套：改写、HyDE、混合检索、Rerank（本模块 [检索与重排.md](检索与重排.md) 的重点）；
- Modular RAG 的亮点：路由（判断该不该检索、该检索哪里）、自反思（生成后自己检查证据是否支持答案）、多轮 Agent 化（先规划检索计划再执行）。

### 4.1 用同一个例子看三个阶段的差距

query："ChatGPT 是什么时候发布的"（假设知识库里有 2023 年发布的资料，模型训练截止 2022）。

- **Naive RAG**：拿原始 query 去向量检索 → 库里文档写的是"2022 年 OpenAI 发布相关产品"→ 检索结果不精准，模型照样答错或模糊——**一次检索、没有修正**；
- **Advanced RAG**：检索前改写为"OpenAI ChatGPT 首次公开发布时间"→ 混合检索（向量 + BM25）+ Rerank → 命中 2023 年的准确文档 → 答案正确——**优化了"怎么找"**；
- **Modular RAG**：路由判断"这是时效性事实题，优先检索而非直接答"→ 检索后 Self-RAG 检查"答案是否被证据支持"→ 不满足则再检索——**多了"该不该找、找得对不对"的判断**。

### 4.2 Modular RAG 的模块清单

| 模块 | 职责 | 例子 |
| --- | --- | --- |
| 查询路由 | 决定检索来源（向量库/BM25/网页/不检索） | 闲聊问题直接答，事实题走检索 |
| 查询改写/扩展 | 让 query 更利于检索 | 口语转书面、多路同义扩展 |
| 检索编排 | 多检索器并行、融合 | BM25 + 向量 + RRF（见 [检索与重排.md](检索与重排.md) 3.3） |
| 记忆模块 | 多轮对话中复用/累积检索结果 | 把上一轮的检索结果带入本轮 |
| 自反思（Self-RAG） | 生成后验证证据支持度 | 答案被支持 → 输出；不支持 → 重新检索 |
| 规划（Agentic） | 拆解复杂问题、分步检索 | 先查背景再查细节，多轮检索后汇总 |

## 五、多模态 RAG 概述

RAG 天然向多模态扩展：生成器从 LLM 换成 VLM，知识库从纯文本变成"文本 + 图像 + 图文混合文档"。三种典型形态（详见 [多模态RAG与评估.md](多模态RAG与评估.md)）：

1. **文本检索辅助 VLM**：检索的是文本片段，但生成器是 VLM——文档 RAG 的常见落法；
2. **图像检索（图库检索）**：query 文本 → 图像库（CLIP/SigLIP 向量）→ 检索到图片作为证据 → 喂给 VLM 看图作答；
3. **图文混合文档**：PDF/扫描件经版面分析切成文本块 + 图像块，各自向量化后统一索引，检索时把"图 + 其标题/上下文文本"一起组装进 prompt。

多模态 RAG 的核心收益仍是**缓解幻觉**：VLM 对着检索到的图片做推理（看图说话），比凭参数记忆凭空编造可靠得多，且每张图都可溯源。但代价是检索侧必须解决**跨模态对齐**（文本 query 与图像向量同空间可比），这是 [图文检索与向量库](../../算法论文基础/14_图文检索与向量库.md) 的核心议题。

三种形态各举一个落地例子：

| 形态 | 落地例子 | 检索链路 | 生成链路 |
| --- | --- | --- | --- |
| ① 文本检索辅助 VLM | 制度问答助手：检索公司制度条款，VLM 引用条款作答 | 文本块 → bge 向量 → 文本库检索 | 条款拼 prompt → VLM 读文作答 |
| ② 图像检索 | 电商图库：查"红色跑鞋"返回商品图 | 文本 query → CLIP 文本侧 → 图库检索 | 商品图 + 标题进 prompt → VLM 看图描述 |
| ③ 图文混合文档 | 财报问答：检索"图 3 柱状图 + 周边段落" | 版面分析 → 文本块/图像块双塔编码 → 混合索引 | 图 + caption + 上下文按序组装 → VLM 综合回答 |

## 六、RAG 评估指标

RAG 是"检索 + 生成"的级联系统，评估必须分层：**先测检索侧，再测生成侧**（检索漏一分，生成掉十分）。

### 6.1 检索侧（衡量"找没找对"）

| 指标 | 公式 | 含义 |
| --- | --- | --- |
| 命中率 HitRate@K | $\frac{1}{\|Q\|}\sum_{q\in Q}\mathbb{1}[\exists\ \text{相关项}\in \text{TopK}(q)]$ | 多少 query 在前 K 里至少有一条相关 |
| Recall@K | $\frac{1}{\|Q\|}\sum_{q\in Q}\mathbb{1}[g_q \in \text{TopK}(q)]$ | 标准答案（GT）排进前 K 的比例，R@1 最严格 |
| MRR | $\frac{1}{\|Q\|}\sum_{q\in Q}\frac{1}{rank_q}$ | 首个相关结果排位的倒数，衡量"第一条就要准" |

### 6.2 生成侧（衡量"答没答对、有没有据"）

| 指标 | 公式/口径 | 含义 |
| --- | --- | --- |
| 忠实度 Faithfulness | 被检索证据支持的句子数 / 总句子数 | 回答是否"言必有据"，幻觉的直接对立面 |
| 答案准确率 | EM / F1（有标准答案的任务） | 与标准答案的对齐程度 |
| 幻觉率 | 不被证据支持的句子占比 | 1 - 忠实度的另一种表述 |
| 引用准确性 | 被引用片段确实支持对应句子的比例 | 引了来源，来源要真的对得上 |

### 6.3 端到端框架

RAGAS（最流行的开源框架）：LLM-as-judge 打分，核心四个指标——**faithfulness**（忠实度）、**answer relevancy**（答案相关性）、**context precision**（上下文精确度，证据是否精准无冗余）、**context recall**（上下文召回，证据是否覆盖答案所需）。多模态场景另有 MM-RAG / RAG-MM 等基准，指标思想相同。

### 6.4 MRR 手算示例

两个 query：

- q1 的 GT 排在第 2 位 → 贡献 $\frac{1}{2} = 0.5$；
- q2 的 GT 排在第 5 位 → 贡献 $\frac{1}{5} = 0.2$；

$$\text{MRR} = \frac{0.5 + 0.2}{2} = 0.35$$

对比 Recall@1：两个 query 的 GT 都没进前 1，Recall@1 = 0——**MRR 能反映"离成功只差一点"的进步，R@K 只看硬性阈值**，评估检索效果时两个指标要一起看。

**评估顺序铁律**：先看检索侧（Recall@K/MRR）——检索不好则生成侧指标再高也是假的（回答是模型硬编的）；检索好而生成差，问题在 prompt 组装或生成器本身。

### 6.5 评估执行清单

1. **建评测集**：50~200 个真实 query，每条标注 GT 相关文档（检索侧）与标准答案（生成侧）；
2. **先测检索侧**：HitRate@K / Recall@K / MRR，定位问题在召回还是重排（见 [检索与重排.md](检索与重排.md) 第七节排查法）；
3. **再测生成侧**：faithfulness / 答案准确率 / 引用准确性，抽样人工复核 LLM judge 的判定；
4. **回归机制**：每次改切分、换模型、改 prompt 都跑一遍全套指标，检索侧与生成侧分开看，别只看最终答案像不像。

## 七、与图文检索模块的关系

RAG 的"检索内核"就是图文检索系统——两者是**复用与编排**的关系，不是并列关系：

```
┌─────────────────────── 知识分层 ───────────────────────┐
│                                                       │
│  [14_图文检索与向量库]：检索内核                          │
│    双塔(CLIP/SigLIP) / ANN 索引 / 向量库 / Recall@K 评测 │
│          ▲                                              │
│          │ 提供"又快又准地找到"的底层能力                  │
│          │                                              │
│  [本模块 RAG专题]：应用编排                               │
│    切分 / 检索 / 重排 / 路由 / 生成 / 端到端评估           │
│          ▲                                              │
│          │ 多模态扩展                                    │
│  [多模态RAG与评估]：图文文档 / 图库 / 幻觉缓解            │
│                                                       │
└───────────────────────────────────────────────────────┘
```

职责划分一句话：**图文检索解决"怎么从库里又快又准地找到 Top-K"（双塔召回、HNSW、模型级 vs 索引级 Recall@K 评测等都已在那里讲透，本模块不重复）；RAG 解决"找到之后怎么用"（切分、融合、重排、路由、拼 prompt、端到端评估）。**

检索系统的问题归属（复习用）：

| 问题 | 归属模块 | 一句话答案 |
| --- | --- | --- |
| 双塔怎么训练、负样本怎么挖 | [图文检索与向量库](../../算法论文基础/14_图文检索与向量库.md) | 对比损失 + hard negative mining |
| 用什么索引、怎么调 nprobe/efSearch | 同上 | IVF/HNSW，画召回-延迟曲线取平台期 |
| 文档切成多大、怎么切 | 本模块 [检索与重排.md](检索与重排.md) | 512 token + 15% 重叠起步，结构化按标题切 |
| 向量 + BM25 怎么融合 | 同上 | RRF：score = Σ 1/(k+rank)，k=60 |
| 为什么需要 rerank、怎么做 | 同上 | 双塔召回求全，cross-encoder 精排求准 |
| 端到端质量怎么评估 | 本模块 [多模态RAG与评估.md](多模态RAG与评估.md) | 先检索侧指标，再生成侧 faithfulness，RAGAS 收尾 |

面试串联话术："RAG 的检索层就是标准图文检索系统，双塔 ANN 召回 + cross-encoder 重排两级结构；检索质量是 RAG 的天花板，所以评估要先测检索侧的 Recall@K 再测生成侧的 faithfulness。"

## 八、高频面试问答

**Q1：RAG 是什么？解决了什么问题？**
检索增强生成：先从外部知识库检索与 query 相关的 Top-K 片段，拼进 prompt，再让 LLM 基于证据生成。解决三大问题：幻觉（证据约束）、知识过时（换文档即换知识）、私有知识（不入训练集也能用）。

**Q2：RAG 和微调怎么选？**
知识类需求选 RAG（更新快、可溯源、成本低）；能力/行为类需求选微调（格式、风格、推理方式）；生产系统两者组合——微调教模型"怎么答"，RAG 提供"答什么"。

**Q3：RAG 的检索质量怎么保证？**
链路式保证：① 切分合理（结构切分 + 重叠窗口）；② 混合检索（向量 + BM25 + RRF 融合）提高召回；③ Rerank 精排保证进 prompt 的 Top-N 全精准；④ 评估分层（检索侧 Recall@K/MRR + 生成侧 faithfulness）定位问题层。

**Q4：多模态 RAG 和文本 RAG 的核心差异？**
① 知识库里多了图像块，需要版面分析切分 + 跨模态对齐的 embedding；② 检索结果要"图 + 上下文文本"一起组装进 prompt，顺序影响 VLM 理解；③ 幻觉缓解从"文本证据"升级为"视觉证据"，可溯源更强，但级联误差风险也更大（检索到错图会带偏 VLM）。

**Q5：RAG 检索到错误信息怎么办？**
分两层：① 事前——提高检索质量（混合检索 + rerank + 阈值过滤 + 元数据版本过滤），prompt 里要求模型"上下文无证据就回答不知道"；② 事后——生成侧自检（Self-RAG：判断答案是否被证据支持，不支持则重新检索或拒答），引用准确性评测兜底。

**Q6：RAG 不适合哪些场景？**
① 答案不依赖外部知识（闲聊、创意写作，检索反而引入噪音）；② 检索源本身不可靠（错误百出的文档库，检索=系统性投毒）；③ 强时效且极高频的推理任务（检索链路延迟占比过高）；④ 能力型需求（格式、推理、风格）——这类归微调管。
