## 一、一句话解释

**多模态 Agent = 多模态大模型（VLM）做"大脑" + 工具调用做"手脚" + 循环推理（思考→行动→观察）做"执行引擎"，能自主完成多步任务。**

- **大脑（VLM）**：接收图文/音视频输入，负责理解任务、拆解步骤、生成动作；
- **手脚（工具）**：OCR、目标检测、图像检索、浏览器、计算器、代码执行器等，弥补模型"看不见、算不动、摸不着"的短板；
- **循环推理（ReAct）**：Agent 不是"问一句答一句"，而是 思考 → 行动 → 观察结果 → 再思考，直到任务完成或达上限。

一句话记忆：**"模型负责想，工具负责做，循环负责把想和做串起来"**。多模态 Agent 的特殊之处在于"想"和"做"的输入输出里都包含图像/视频。

三个组件的分工：

| 组件 | 角色 | 多模态版本 | 失败后果 |
| --- | --- | --- | --- |
| 大脑（VLM） | 理解任务、拆解步骤、生成动作 | 能看图/截图/视频做决策 | 理解错 → 全盘皆错 |
| 手脚（工具） | 提供模型没有的能力 | OCR/检测/检索/GUI 操作 | 工具错 → 错误信息进入循环 |
| 循环（ReAct） | 把思考与行动串成多步过程 | 每轮把截图与工具结果拼回上下文 | 状态丢失 → 前后矛盾 |

## 二、Agent 核心范式

### 2.1 ReAct：思考→行动→观察（最主流的范式）

```
指令: "帮我看货架图，酸奶多少钱，库存够不够"
  │
  ▼
┌────────────┐    ┌────────────────┐    ┌──────────────┐
│  1. Thought │───▶│ 2. Action(工具) │───▶│ 3. Observation│
│  模型思考     │    │  调用 OCR        │    │  OCR 返回文字   │
└────────────┘    └────────────────┘    └──────────────┘
      ▲                                        │
      └────────── 把结果拼回对话，继续思考 ──────────┘
```

- 英文名 ReAct = **Re**ason + **Act**，源自论文《ReAct: Synergizing Reasoning and Acting in Language Models》（ICLR 2023）；
- 关键设计：**推理轨迹（thought）和动作交替出现、互相促进**——thought 利用 Observation 修正下一步动作，避免"瞎猜"；
- 实现上就是"带工具的多轮对话"：模型每轮要么输出工具调用，要么输出最终答案（详见 [工具调用与ReAct.md](工具调用与ReAct.md) 第三节）。

### 2.2 Plan-and-Execute：先规划，后执行

与 ReAct"边想边做"不同，Plan-and-Execute **先一次性生成完整计划**，再逐步执行：

1. **Planner（规划器）**：根据任务拆出步骤列表 $[s_1, s_2, ..., s_n]$（可包含工具调用）；
2. **Executor（执行器）**：逐步执行每一步，失败或情况变化时**回到 Planner 修订计划**；
3. 优点：少调用模型、省钱省延迟；缺点：计划可能脱离实际，动态修正能力弱于 ReAct。

典型应用：BabyAGI、LangChain 的 Plan-and-Execute executor、复杂的多工具长流程任务。

### 2.3 Reflexion：给 Agent 装上"复盘"

Reflexion（NeurIPS 2023）在 ReAct 基础上加了一层**自我反思**：

```
执行任务 → 失败 → 生成反思(Reflection): "我上一步错在OCR漏了价格标签，应该先放大截图"
                → 把反思写回记忆，下次尝试避开同样的坑
```

- 核心：把**失败经验转成文本存入记忆**，多轮尝试（episode）之间共享；
- 适合：代码修复、游戏、需要多次试错才能成功的任务；
- 与 ReAct 关系：ReAct 是单次轨迹的循环，Reflexion 是跨多次尝试的元循环。

一次反思的文本形态：

```json
{"reflection": "上一轮失败原因：OCR 把『500ml』误识别为『50Oml』，导致检索失败；"
 "改进策略：OCR 后先做数字白名单校验，可疑字符重试或转 VLM 直读。"}
```

### 2.4 三种范式对比

| 范式 | 核心机制 | 优点 | 缺点 | 典型代表 |
| --- | --- | --- | --- | --- |
| ReAct | 思考↔行动逐轮交替 | 灵活、可纠错、可解释 | 多轮调用成本高 | GPT-4 + function calling、大多数 Agent |
| Plan-and-Execute | 先计划后执行 | 成本低、稳定 | 计划僵化、应变差 | BabyAGI、LangChain Plan-Execute |
| Reflexion | 反思写回记忆重试 | 试错能力强 | 慢、需要任务可重复 | Reflexion（代码/游戏） |

### 2.5 一次 ReAct 轨迹走读（以多模态为例）

指令："帮我看货架图，确认酸奶价格和库存后下单 2 盒。"

| 轮次 | Thought | Action | Observation |
| --- | --- | --- | --- |
| 1 | 需要先读出图片里的价格 | `ocr(scene1.png)` | 酸奶 12.8 元，牛奶 9.9 元 |
| 2 | 价格拿到了，还要查库存 | `retrieve("酸奶 库存")` | 库存 128 件 |
| 3 | 库存充足，直接下单 2 盒 | `order(酸奶, 2)` | 下单成功，订单号 A1024 |
| 4 | 信息齐全，汇总给用户 | 最终回答 | — |

注意第 3 轮：**模型把"中间结论"（库存充足）当作调用 `order` 的前提**——这正是 ReAct 的纠错机制：如果第 3 轮库存不足，Observation 会提示失败，模型转而回答"库存不足，无法下单"，而不是硬编答案。

## 三、为什么多模态 Agent 特别

### 3.1 视觉输入：看屏幕、看图做决策

纯文本 Agent 只能"猜"画面内容；多模态 Agent 直接把图像喂给 VLM：

- **看屏幕**：截图进模型，直接判断"当前页面有没有登录按钮、弹窗挡住了什么"（见 [GUI与多模态操作Agent.md](GUI与多模态操作Agent.md)）；
- **看实物图**：用户发一张货架照片问"哪个酸奶在打折"，模型需要理解图像内容本身；
- **看图表/文档**：PDF 扫描件、票据、图表，视觉理解是唯一入口。

### 3.2 工具返回图像/视频

工具调用后，Agent 拿到的 Observation 不只是文本，还可以是**图片、视频、结构化视觉结果**：

| 工具 | 返回类型 | 下游用途 |
| --- | --- | --- |
| OCR | 文本 + 坐标框 | 提取文字后检索、问答 |
| 目标检测 | 类别 + bbox | 判断画面里有什么、定位 |
| 图像检索 | 图像/路径 | 拿"长像"去匹配商品、找相似图 |
| 视频工具 | 关键帧/视频片段 | 事件识别、动作判断 |

### 3.3 多模态工具链：OCR→检测→检索→VLM 复核

多模态场景几乎总是**多个工具串联**，而不是单次调用：

```
图片 → OCR(读文字) → 检测(定位物体) → 检索(查知识库) → VLM复核(综合判断) → 回答
```

例如图文一致性校验（见 [工具调用与ReAct.md](工具调用与ReAct.md) 第四节）：OCR 提取商品名 → 检测定位图中商品 → 检索商品库资料 → VLM 比对图文是否一致。

### 3.4 与纯文本 Agent 的对比总结

| 维度 | 纯文本 Agent | 多模态 Agent |
| --- | --- | --- |
| 输入 | 文本指令 + 文本工具返回 | 文本 + 图像/视频/截图/音频 |
| 视觉理解 | 无 | VLM 提供"看"的能力（屏幕、实物、图表） |
| 工具返回 | 文本/结构化数据 | 图像、视频、坐标框、OCR 文本 |
| 典型工具 | 搜索、代码执行、计算器 | OCR、检测、图像检索、GUI 操作、视频分析 |
| 状态表示 | 消息历史（纯文本） | 消息历史 + 截图序列 + 工具返回的多媒体结果 |
| 主要难点 | 推理长链、工具选择 | 视觉理解的置信度 + 成本 + 长上下文 |

## 四、主流框架与产品

| 框架/产品 | 类型 | 关键能力 |
| --- | --- | --- |
| OpenAI Function Calling（GPT-4o / o 系列） | API 能力 | 模型原生输出结构化工具调用 JSON，用户定义 schema，官方消息协议 `tool_calls` |
| LangChain / LangGraph | 开发框架 | Agent 编排、工具注册、记忆、条件循环图；LangGraph 用图定义 Agent 状态机 |
| AutoGPT / BabyAGI 类 | 自主 Agent 应用 | 长目标自动拆解、多工具循环，证明"自主 Agent"可行但稳定性差 |
| Anthropic Computer Use | 产品能力 | Claude 通过截图 + 鼠标/键盘动作直接操作电脑（见 [GUI与多模态操作Agent.md](GUI与多模态操作Agent.md) 第四节） |
| Qwen 系 GUI Agent（Qwen2.5-VL / Qwen-Agent / UI-TARS） | 开源模型+框架 | Qwen2.5-VL 输出 UI 定位框与绝对坐标 JSON；Qwen-Agent 提供多工具编排；UI-TARS 是端到端 GUI Agent 模型 |

**一句话点评**：Function Calling 是"基础设施"（模型会调工具），LangGraph 是"编排框架"（怎么调、调几次），Computer Use / GUI Agent 是"最硬核应用"（模型直接操控物理屏幕）。

各家的关键设计细节：

- **OpenAI Function Calling**：把工具 schema 注入对话，模型输出 `tool_calls` 消息（name + JSON arguments），由应用执行后再以 `tool` 角色回填结果——这套消息协议后来成为行业事实标准，国产模型 API 基本兼容；
- **LangGraph**：用**图结构**定义 Agent（节点=模型/工具，边=条件跳转），支持循环、中断、人工介入（human-in-the-loop），比 LangChain 的链式调用更适合复杂 Agent；
- **AutoGPT 类**：不依赖任何平台，用"目标→拆解→循环执行"跑长任务，验证了自主性但也暴露了失控风险（乱花钱、乱调 API），现已更多退化为研究/教学案例；
- **Anthropic Computer Use**：Claude 直接看图操作真实桌面，动作是底层鼠标键盘事件，在虚拟机里安全执行（详见 [GUI与多模态操作Agent.md](GUI与多模态操作Agent.md)）；
- **Qwen 系**：从模型侧下手——Qwen2.5-VL 训练了"UI 元素定位"能力（输出框/点 + 绝对坐标 JSON），Qwen-Agent 提供路由与工具编排，UI-TARS 把"看图→输出动作"端到端一体化，开源程度最高。

## 五、多模态 Agent 典型场景

### 5.1 GUI 操作（电脑/手机自动化）

- 例子：按指令打开购物 App、搜索、加购物车、下单；网页表单自动填写；
- 技术栈：截图 → OCR/UI 检测 → 坐标预测 → 点击/输入 → 新截图（详见 [GUI与多模态操作Agent.md](GUI与多模态操作Agent.md)）。

### 5.2 文档问答 + 工具

- 例子：把合同扫描件 OCR 成文本 → 检索历史条款 → 回答"本合同的违约金比例是否合规"；
- 特点：视觉解析（OCR/版面）与文本推理（检索+LLM）必须**分工**，单靠模型"硬读"长文档成本高、准确率低。

### 5.3 商品分析（电商/巡检）

- 例子：拍货架照片 → 识别商品与价格标签 → 检索库存 → 输出补货建议；
- 例子：外观质检——拍产品图 → 检测缺陷 → 查缺陷标准 → 判定合格/不合格。

### 5.4 巡检/安防（视频）

- 例子：工地监控画面 → 检测是否戴安全帽 → 触发告警并生成图文报告；
- 特点：视觉检测（实时）与 LLM 总结（事后）分层，Agent 负责"多路信号的综合决策"。

### 5.5 一个完整示例：从指令到动作

以"商品分析"为例，模型在循环中产出的动作轨迹：

```json
[
  {"thought": "先识别货架图里的商品与价格", "tool": "ocr", "args": {"image_path": "shelf.png"}},
  {"thought": "查一下酸奶库存", "tool": "retrieve", "args": {"query": "酸奶"}},
  {"thought": "库存充足，生成补货建议", "answer": "酸奶 12.8 元，库存 128 件，建议补货 2 箱。"}
]
```

这条轨迹同时展示了多模态 Agent 的核心三要素：**视觉工具（OCR 读图）→ 外部信息（检索）→ 决策输出（最终回答）**。

## 六、Agent 评测

Agent 是"多步过程"，评测也按"最终结果 + 过程质量"两层：

**① 任务成功率（Success Rate）**

$$S = \frac{1}{N}\sum_{i=1}^{N} \mathbb{1}[\text{任务 } i \text{ 的最终状态满足目标}]$$

**② 步骤准确率（Step Accuracy）**

$$SA = \frac{1}{N}\sum_{i=1}^{N}\frac{\text{任务 } i \text{ 中正确步骤数}}{\text{任务 } i \text{ 总步骤数}}$$

**③ 幻觉工具调用率（Hallucinated Tool Call Rate）**

$$HR = \frac{\text{非法/无中生有的工具调用次数}}{\text{总工具调用次数}}$$

| 指标 | 衡量什么 | 典型值（公开评测） |
| --- | --- | --- |
| 成功率 | 任务最终是否完成 | OSWorld 上 SOTA 约 20%~50%（任务难度差异大） |
| 步骤准确率 | 过程是否每一步都对 | 通常 50%~80%，与任务粒度相关 |
| 幻觉工具调用率 | 是否乱调工具/编造参数 | 生产中必须压到 1% 以下（见 [工具调用与ReAct.md](工具调用与ReAct.md) 第六节） |
| 平均轮次/延迟 | 效率 | 越少越好，Plan-and-Execute 的优势点 |

**评测难点**：一是环境需要可复现（GUI 操作要真实/模拟环境，如 OSWorld）；二是"过程对但结果错"（比如走了弯路但最终成功）需要人工/规则逐步标注。

### 6.1 常用基准（Benchmark）

| 基准 | 模态 | 任务类型 | 说明 |
| --- | --- | --- | --- |
| OSWorld | GUI（真实 Ubuntu） | 计算机操作 | 369 个任务，截图对比判成功，SOTA 约 20% |
| Mind2Web | GUI（网页） | 网页操作 | 137 个网站的 2350 个任务，按步骤准确率评估 |
| ScreenSpot | GUI（截图） | 屏幕元素定位 | 只测"能不能点对位置"，隔离定位能力 |
| GAIA | 通用（文本+图） | 多步推理+工具 | 需检索、计算、调用 API，考察组合能力 |
| MMBench-Agent | 多模态 | 看图决策 | 视觉 Agent 专用，含图片理解+工具链任务 |

**面试提示**：能报出 OSWorld ~20%、Mind2Web ~50% 级别这两个数字，并解释"为什么低"（截图理解难、误操作不可逆、环境动态），说明你真正了解这个方向。

### 6.2 评测的三个层次

1. **能力层**：单点能力评测（OCR 准不准、点得准不准——ScreenSpot 就是这种）;
2. **任务层**：完整任务成功率（OSWorld / Mind2Web）；
3. **成本层**：轮次、延迟、token 花费——生产上线必须和成功率一起看。

三层缺一不可：能力满分也可能任务失败（推理链断），任务成功也可能成本爆炸。

## 七、高频面试问答

**Q1：Agent 和普通多轮对话的区别？**
普通对话模型"想完就说"；Agent 多一个"行动"环节——模型可以在对话中调用工具、拿到结果后再回答，本质是**把推理扩展到外部世界**。

**Q2：ReAct 和 Chain-of-Thought（CoT）的区别？**
CoT 只有"想"（纯文本推理），ReAct 是"想+做"（推理轨迹穿插工具行动），ReAct 的 Observation 来自外部真实反馈，可纠错；CoT 的中间推理无法被验证。

**Q3：什么任务适合用 Agent，什么不适合？**
适合：多步、需要外部信息（查询、计算、操作）、可拆解的任务。不适合：单轮常识问答、纯推理题——多调一次工具就多一分出错与延迟。

**Q4：为什么多模态 Agent 比纯文本 Agent 难？**
① 视觉输入要过 VLM，截图分辨率/token 成本高；② 视觉理解的置信度低，工具调用更容易建立在错误理解上；③ 工具返回图片/坐标等非文本结果，循环的状态表示更复杂。

**Q5：Agent 评测为什么不能只看成功率？**
成功率只看终点，可能掩盖过程问题（幻觉工具调用、绕远路、重复试错），生产环境要同时盯步骤准确率、幻觉率、轮次成本。

**Q6：多模态工具链为什么通常设计成"小模型工具 + 大模型编排"？**
检测/OCR 用小模型逐帧快跑便宜稳定，LLM/VLM 只负责需要语义理解的编排与复核，成本和质量都能兼顾。

**Q7：Agent 的循环什么时候该停下来？**
三个停止条件：① 模型输出最终答案/`finish` 动作；② 达到 `max_steps` 上限（强制熔断，防止死循环烧钱）；③ 高风险操作触发了人工介入（human-in-the-loop），等待人确认后再继续。

**Q8：长上下文多模态 Agent 的成本问题怎么解决？**
视觉 token 很贵（一张截图可能上千 token），常用手段：截图降分辨率/裁剪关键区域、只把"变化区域"送入下一轮、历史截图用文本摘要替代、工具返回的图像做特征压缩（如 [参数高效微调PEFT](../技术基础/参数高效微调PEFT/参数高效微调PEFT.md) 之外的 token 压缩思路）。
