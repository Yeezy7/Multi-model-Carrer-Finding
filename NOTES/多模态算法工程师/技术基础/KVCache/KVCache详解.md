## 一、一句话解释

**KV Cache（Key-Value Cache）= 把已经生成的 token 的 Key/Value 缓存下来，自回归解码时不再重复计算，是 LLM/VLM 推理加速与显存优化的核心机制。**

拆开看它的三个关键词：

- **K/V 是什么**：Transformer 每一层把输入 $x$ 投影成三个向量，$Q = xW_Q$（查询）、$K = xW_K$（键）、$V = xW_V$（值），注意力用 $QK^\top$ 打分、按权重对 $V$ 加权求和。其中 **K/V 会被"后来的 token"反复查询**（以后所有步都要来匹配），而 Q 只服务当前这一个位置；
- **缓存（Cache）**：推理时，一旦某个位置的 K/V 算出来了，它的值就固定不再变（因果注意力 + 权重冻结），于是存进缓存；下一次生成只要把新 token 的 K/V 追加进去，历史行**直接复用**；
- **核心机制**：没有它，生成第 $n$ 个 token 时要把前 $n-1$ 个 token 的 K/V 全部重算，解码会慢几百倍；有了它，重复计算被整体消除，同时 KV 也成了长上下文/高并发下显存的第一大头——"**又省算力、又吃显存**"的同一块内存。

在标准 pipeline 中它长这样：

```
                     ┌──────────────────── token 流 ────────────────────┐
                     ▼                                                  ▼
  prompt ──► prefill ──┐   生成 w3 ──► decode ──► 生成 w4 ──► decode  … 
      （一次性算整个      │   （新 K/V 拼入）         （新 K/V 拼入）
        prompt 的 K/V） ▼
                    ╔══════════════════════════════════╗
                    ║   KV Cache（每层一份，逐 token 递增） ║
                    ╚══════════════════════════════════╝
```

一句话记忆：**"算过的不再重算——把历史的 K/V 存下来随取随用。"**

### 1.1 前置回顾：Q/K/V 与注意力公式（30 秒）

不了解这三个向量的读者，先看这一个式子就够了。对序列每个 token 的隐藏状态 $x$：

$$Q = xW_Q, \quad K = xW_K, \quad V = xW_V, \qquad \text{Attn}(Q,K,V) = \text{softmax}\!\Big(\frac{QK^\top}{\sqrt{d_{head}}}\Big)\,V$$

- **Q（Query）= 这个 token"想找什么"**，用它去匹配所有 K；
- **K（Key）= 每个 token"被找的标签"**，QKᵀ 决定谁和谁相关；
- **V（Value）= 每个 token"能被分享的内容"**，按相关度加权取出来。

因果注意力要求位置 $i$ 只能看 ≤ $i$ 的位置（矩阵下三角）。KV Cache 的舞台正是这三个向量里"被反复查询的两个"。

## 二、为什么需要 KV Cache

### 2.1 自回归是逐 token 生成的

LLM 生成文本是**自回归（autoregressive）**：一次只产生 1 个 token，把它拼到输入末尾，再预测下一个：

$$p(w_1, w_2, \dots, w_n) = \prod_{t=1}^{n} p(w_t \mid w_1, \dots, w_{t-1})$$

要预测 $w_t$，必须把 $w_1 \dots w_{t-1}$ 完整地交给模型。序列每生成一个 token 就长一位——**如果不做缓存，第 $t$ 步要对整个长度为 $t$ 的序列重新前向**，越后面越夸张。

### 2.2 已算过的 K/V 永远不会变

只要两个前提成立（严格推导见 [KV Cache原理与实现.md](KV Cache原理与实现.md) 第二节）：

1. **因果注意力**：位置 $i$ 的隐藏状态只依赖 ≤ $i$ 的输入（看不到未来）；
2. **权重冻结**：推理过程模型参数不变。

⟹ 位置 $i$ 的 $K_i = x_i W_K$、$V_i = x_i W_V$ 一旦算出，无论后面再生成多少 token 都**保持恒等**。因此缓存是**精确复用**（数学等价、零近似），不是压缩近似——这点常被误解（见子篇误区）。

### 2.3 算力从 O(n²) 降到 O(n)

- **无缓存**：生成第 $t$ 个 token 时要重算前缀 0..t 的全部 K/V（O(t) 次投影），累计 $n$ 步 **O(n²)** 的重复计算；
- **有缓存**：第 $t$ 步只投影新 token 的 K/V（O(1)），累计 **O(n)**；注意力每次对历史 KV 打分 O(t) 是必要开销，但"重复计算"被彻底删掉。

**数值示例**（prompt=1024，再生成 1024 token）：

| 方案 | K/V 投影处理的位置次数 | 开销 |
| --- | --- | --- |
| 无缓存 | $\sum_{t=1024}^{2047} t = \frac{(1024+2047)\times1024}{2} \approx 1{,}572{,}352$（约 157 万） | O(n²) |
| 有缓存 | prefill 1024 次 + 每新 token 1 次 ×1024 = 2048 次 | O(n) |
| 加速比 | $1{,}572{,}352 \div 2048 \approx 768$ 倍 | —— |

也就是说：**同样生成 1024 个 token，K/V 投影从 157 万次骤降到 2048 次，省约 767 倍**（注意力打分两种方案一致，不受此项优惠影响，见子篇第三节）。

### 2.4 省在哪、不省在哪（边界要说清）

| 计算项 | 无缓存 | 有缓存 | KV Cache 是否能省 |
| --- | --- | --- | --- |
| 历史 K/V 投影 | 每步全部重算 | 只算新 token 1 行 | **省**（这就是主收益） |
| Q 投影 | 每步 1 个 | 每步 1 个 | 无差异 |
| 注意力打分 | 每步重算前缀全部行 | 新 query 对全部历史 KV 打分 O(S) | 只省"重复计算历史行的打分"，每步打分仍 O(S) |
| 输出投影 / FFN | 每步只算末位 | 每步只算末位 | 无差异 |

**边界**：KV Cache 消灭的是"历史 K/V 的重复投影 + 重复注意力"；**decode 每步的注意力仍随序列长度线性增长**（O(S)），这一步省不掉——那是窗口化/稀疏注意力的任务（[KV Cache优化技术.md](KV Cache优化技术.md) 第五节）。

### 2.5 一个类比：图书馆 vs 反复抄档案

- 无缓存 = 每次来读者（新 token），都把**整本档案从头抄一遍**再回答（每步重算全历史）；
- KV Cache = 档案室把**每页档案复印一份固定存着**，新读者来了直接翻旧的、只给新的一页复印（每步只新建 1 页）；
- 代价：档案室要**占一块地方存**（显存开销），这正是第五节的矛盾与第六章所有优化的起点。

## 三、为什么只缓存 K/V 而不缓存 Q

一句话：**Q 是"当下这步的主动查询"，只服务当前这个 token；K/V 是"历史档案"，要被未来的每一步反复查询。**

### 3.1 角色对比

| 向量 | 角色 | 是否可缓存 | 原因 |
| --- | --- | --- | --- |
| Q | 当前新 token 的"查询请求"，生成本步输出后即弃 | 不能 | 每个 token 位置不同，Q 必须用自己当前的隐藏状态现场算 |
| K | 历史 token 的"档案标签"，未来每个 token 都要来匹配打分 | 能 | 权重不变 + 因果依赖已固定 ⟹ 恒定 |
| V | 历史 token 的"档案内容"，未来每个 token 都要来加权取值 | 能 | 同上 |

### 3.2 从公式看

生成第 $t+1$ 个 token 的注意力：

$$\text{attn} = \text{softmax}\!\Big(\frac{Q_{t+1}\,[K_0, K_1, \dots, K_t]^\top}{\sqrt{d_{head}}}\Big)\,[V_0, \dots, V_t]^\top$$

- $Q_{t+1}$ 只在第 $t+1$ 步出现一次（属于新 token，用完丢弃）；
- $[K_0..K_t]$, $[V_0..V_t]$ 会在第 $t+2, t+3, \dots$ 步被反复查询——**谁被重复用，谁才值得缓存**。

### 3.3 为什么训练时不用 KV Cache

训练是**一次性并行**过整段序列（teacher forcing），每个位置的 Q/K/V 同时算、不存在"边生成边复用"的循环；且训练需要 K/V 的梯度回传，插缓存会把图切断。KV Cache 是**推理专用**的机制。

### 3.4 如果硬要缓存 Q 会怎样

假设把历史所有 Q 也存下来：每一种序列状态下，第 $t$ 步的 $Q_t$ 只被用一次就作废，缓存它**只是白白吃显存**——它永远不会被第二次查询。反观 K/V，被每个后续 token 查询 $n-t$ 次。所以缓存对象是"**未来会被反复查询的量**"，Q 不符合。这也解释了为什么 KV Cache 里只有 K、V 两类张量而没有 Q 的影子。

## 四、KV Cache 是全序列共享的吗

不是。**KV Cache 按"层"独立存放、按"位置"各占一行、按"请求"独立一份，互不共享。**

### 4.1 逐层独立（每层一份）

每一层都把自己的投影结果单独存一份：模型 32 层 = 32 份 KV Cache。上一层输出 $x$ 流向下一层，下一层重新投影自己的 K/V，走完 $L$ 层：

$$\text{每层 KV 显存} = 2 \times (\text{该层 KV 维度}) \times (\text{序列长度} S)$$

### 4.2 逐位置一行、逐请求独立

- 一个序列里每个 token 一行 K、一行 V，值各不相同；
- **不同请求/不同生成序列各自有独立缓存**，互不干扰；同一请求内部也不存在"全序列共享一份"这种事——是"每 token 追加一行"。

### 4.3 所以要区分三件"共享"的事（常被混为一谈）

| 说法 | 是否共享 | 说明 |
| --- | --- | --- |
| 模型权重跨请求共享 | 是 | 权重只加载一份，所有请求共用（这是对权重） |
| KV Cache 跨请求共享 | **否** | 每请求独立；只有 prefix caching 能复用**公共前缀**那一段 |
| 多头共享 | 部分 | MHA 全独立；GQA/MQA 让多个 Q 头**共享同一份 K/V**（正是省 KV 显存的架构手段，见 [KV Cache优化技术.md](KV Cache优化技术.md)） |

## 五、KV Cache 显存占比：长上下文下是推理显存最大头

### 5.1 每 token 消耗多少

单序列 KV Cache 显存公式（完整账本与推导见 [KV Cache原理与实现.md](KV Cache原理与实现.md) 第四节）：

$$M = 2 \times L \times n_{kv\_heads} \times d_{head} \times S \times \text{bytes}$$

7B、32 层、d=4096、GQA 8 组（$d_{head}=128$）、FP16 代入：

- 每 token 每层：$2 \times 8 \times 128 \times 2 = 4096$ B = **4 KB**；
- 32 层 → 每 token **128 KB**；
- 2048 token 单序列 → **0.25 GB**；batch=8 → 2 GB（128 KB/token × 2048 × 8）；
- 对比：**全 MHA（32 个 KV 头，每 token 512 KB）下 2048 token = 1 GB**——网文常说的"7B @2048 token 约 1GB"对应的是 MHA 模型（如 LLaMA-2-7B），或 GQA-8 模型在 batch=4 时的合计。

### 5.2 为什么说它是"最大头"：与权重/激活对比

| 开销 | 量级（7B，FP16） | 特点 |
| --- | --- | --- |
| 模型权重 | 14 GB | 固定、一次性加载 |
| 激活（中间结果） | 短时、与 batch 相关 | 一次前向用完即释放 |
| **KV Cache** | **与 $S \times$ batch 线性增长，且每层一份** | **常驻显存，随上下文/并发只涨不跌** |

关键在"**与序列长度、并发数同时线性**"——所以上下文一长或并发一高，KV 立刻反超激活、逼近甚至超过权重：

| 场景 | KV 占用（7B，FP16） | 占权重（14GB）比 |
| --- | --- | --- |
| GQA-8，2048 token，单序列 | 0.25 GB | ~2% |
| GQA-8，32K 上下文，单序列 | 4 GB | ~29% |
| MHA（32 头），32K 上下文，单序列 | 16 GB | **>100%** |
| GQA-8，8K 上下文，batch=32 | 16 GB | >100%（纯 KV 一项就比权重贵） |

再看更大的模型：**70B（80 层、MHA 64 头）：每 token $2\times80\times64\times128\times2 = 2.5$ MB** —— 单序列 32K 就 80 GB、128K 达 320 GB，纯 KV 就远超 140 GB 的权重。**长上下文 + 大模型 + 高并发，KV Cache 必然是显存第一大头**，这就是第六节所有优化存在的直接原因。

### 5.3 长输出同样吃 KV

不只是长输入（上下文长）——**长输出**（生成 8K~64K token 的摘要、续写、Agent 工具调用）也按生成的 token 数逐 token 累涨 KV 显存。对 streaming 服务来说，KV 是"边生成边涨、涨了不还"的常驻占用。

### 5.4 账本怎么口算（面试速估）

快速估算只要两步：**先算每 token 显存，再乘序列长度与 batch**。

$$\text{每 token 显存} = 2 \times L \times n_{kv} \times d_{head} \times \text{bytes}$$

- 7B GQA-8 FP16：$2\times32\times8\times128\times2 = 128$ KB/token；
- 7B MHA FP16：$2\times32\times32\times128\times2 = 512$ KB/token（GQA 的 4 倍）。

随后一眼看：`32K 上下文单请求 = 128KB × 32768 ≈ 4GB（GQA-8）`；`batch 8 × 32K = 32GB`——**全部在线服务的 KV 显存 = 每 token 显存 × 总 token 面积（Σ 各请求序列长度）**，与模型参数量无关，只看"同时活着的 token 有多少"。这也是 vLLM 用"token 级"而非"请求级"管理 KV 的直觉来源。

## 六、优化手段地图

KV Cache 优化的本质：**在"显存"与"算力/精度"之间做取舍**。五条主线（每项一句话，系统性解法见 [KV Cache优化技术.md](KV Cache优化技术.md)）：

| 手段 | 一句话原理 | 收益 / 代价 |
| --- | --- | --- |
| **GQA / MQA（共享 KV 头）** | 多个 Q 头共享同一组 K/V 头（MHA → GQA → MQA），KV 头数从 $n_q$ 降到 $n_{kv}$ | KV 显存降为 $n_{kv}/n_q$（GQA-8 相对 MHA 省 75%；MQA 更低）；代价是表达力略降 |
| **KV Cache 量化（FP8/INT4）** | K/V 用低精度（int8/int4/FP8）存储，读取时反量化；配合分组量化 + 通道异常值保护敏感通道 | 显存与带宽降至 1/2~1/4；代价是缓存精度损失（本文是唯一允许有损的手段） |
| **PagedAttention（vLLM）** | 逻辑上连续的 KV 序列切成固定大小块（如 16 token/块），用页表映射到任意物理位置 | 消除显存碎片、动态 batch 近乎零浪费、支持请求间共享公共 KV；代价是实现复杂度 |
| **窗口化 / 滑窗注意力** | 只保留最近 $W$ 个 token 的 KV，更远的直接丢弃（Longformer/Mistral 滑动窗口） | KV 常数化 O(W)；代价是丧失对超旧信息的直接注意力 |
| **序列 / 视觉 token 裁剪** | 从源头削减进入注意力的 token 数：次要 token 剪枝、视觉 token 压缩/重采样 | KV 总量成比例下降，同时降 prefill 时延（TTFT）；代价是丢信息、需调理 |

（架构级补充：DeepSeek-V2/V3 的 **MLA** 用共享潜在向量 + 低秩映射压缩 K/V，同属 KV 显存与带宽优化，归入优化子篇。）

> **怎么选**：能改架构用 GQA/MQA（收益最大）；已有模型用量化 + PagedAttention（最实用）；超长上下文加窗口化；多模态先做视觉 token 裁剪。五者可叠加。

## 七、多模态场景：视觉 token 大量 → 视觉 KV 占大头

多模态（VLM）里 KV Cache 问题被**成倍放大**，根源是视觉 token 比文本 token 多得多、又常驻上下文全程。

### 7.1 数量级碾压

| 输入 | token 数（量级） |
| --- | --- |
| 一句短文本 | ~100 |
| 一张 896×896 图（patch 化 + 少量压缩） | 数百 ~ 1K |
| 一张 2K 高清图（tiling 切多块） | 数千 ~ 1 万 |
| 一段视频 / 超长文档 | 数万 |

一张 5000 视觉 token 的图，在 7B（GQA-8）下 KV ≈ 5000 × 128 KB = **0.61 GB**，乘上 batch 与上下文翻倍轻松数 GB——**视觉 KV 远超文本 KV**，是 VLM 推理显存的第一阵地。

### 7.2 视觉 token 还推高 TTFT（首 token 延迟）

视觉 token 多 ⟹ prefill 长度长（要一次性算完所有视觉 token 的 K/V 与注意力）⟹ **TTFT 被拉高**。图越长、视频越久，用户"第一屏反应"越慢。这会直接传导到两件事：

1. **显存**：视觉 KV 常驻整个对话（图放前面，后面每步注意力都要查它）；
2. **时延**：prefill 变长拖垮首 token 出字速度。

### 7.3 Qwen3-VL 部署的 token 裁剪动机

Qwen2.5-VL / Qwen3-VL 系的部署实践（正是上述矛盾的工程回应）：

- 对输入图按 `min_pixels / max_pixels` **动态缩放**控制分辨率，防止"原图多大 token 多大"；
- 对生成的**视觉 token 做重采样压缩（resample）**，把稠密 patch 表示聚合成更紧凑的 token 序列；
- 对超长纯文本默认只保留其 token 预算内的一段（如最长 32K）。

动机一句话：**视觉 token 海量 → 视觉 KV 占满显存、TTFT 居高不下 → 从源头做 token 裁剪，KV 显存与 prefill 时间同比例下降**。这是 VLM 部署里"KV 优化第一杠杆"，详见 [KV Cache优化技术.md](KV Cache优化技术.md) 第六节。

### 7.4 视频/多帧：视觉 KV 的增量叠加

多帧/视频类任务（VideoQA、多模态 Agent 看多图）里，视觉 KV 是**逐帧累加且全程常驻**的：

- 每帧重采样后约 1K visual token，一段 60 帧 ≈ 6 万 token，7B（GQA-8）下 KV ≈ $60{,}000 \times 128\ \text{KB} \approx 7.9\ \text{GB}$——**单并发就接近权重（14 GB）的一半**；
- 这些帧 token 从第一帧起就常驻序列：对话后面每一步 attention 都要"回头"查整个视频的 KV ⟹ **TPOT 也随视频长度上升**，不只是显存问题；
- 常见对策：帧抽稀/关键帧采样、H2O 式 KV 淘汰（保留 attention 重的关键帧）、Qwen 系的 multimodal 压缩与"思考预算"控制（演进到 [KV Cache优化技术.md](KV Cache优化技术.md) 第五、六节）。

> 一句话总结第七节：**VLM 的 KV 大头永远是视觉——token 数量级碾压文本、tiling/resample 放大、逐帧常驻全程，靠源头裁剪与压缩才能压住。**

## 八、常见面试考点预告

高频考点浓缩（完整答案见 [KV Cache原理与实现.md](KV Cache原理与实现.md) 第九节）：

1. **KV Cache 是什么？** —— 缓存历史 K/V 避免自回归重复计算，精确复用、零近似。
2. **为什么只缓存 K/V 不缓存 Q？** —— Q 只服务当前步，K/V 被未来反复查询（本文第三节）。
3. **KV Cache 显存怎么算？** —— $M = 2\times L\times n_{kv}\times d_{head}\times S\times \text{bytes}$；7B GQA-8 → 0.25 GB/2048 token，MHA → 1 GB。
4. **prefill 与 decode 区别？TTFT/TPOT？** —— prefill 一次并行、compute-bound 决定 TTFT；decode 逐 token、memory-bound 决定 TPOT。
5. **KV Cache 有损耗吗？** —— 没有，数学等价（量化/共享才有损）。
6. **与 FlashAttention、PagedAttention 的关系？** —— FA 是注意力 kernel 提速、不动 KV 语义；PagedAttention 管 KV 内存布局。
7. **长上下文 KV 爆显存怎么办？** —— GQA / 量化 / PagedAttention / 窗口化 / token 裁剪五件套。
8. **多模态里视觉 token 为什么是 KV 大头？** —— 数量级碾压 + tiling 放大 + 常驻全程，Qwen3-VL 靠 token 裁剪缓解。
9. **KV Cache 什么时候初始化/分配多大？** —— prefill 后按 max_len 预分配、长度指针写入；多请求独立、prefix caching 才共享（原理篇第六、八节）。
10. **为什么 decode 慢、GPU 利用率低？** —— 每步只算 1 个 token 却要读全部权重 + 全部 KV，是"带宽瓶颈"（memory-bound），靠 batch/量化缓解。
