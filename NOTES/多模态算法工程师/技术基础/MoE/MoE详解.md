## 一、一句话解释

**MoE（Mixture of Experts，混合专家）= 多个专家网络 + 路由器，每个 token 只激活其中少数几个专家（top-k），其余专家保持冻结。**

- **多个专家（Experts）**：把标准 Transformer 里单个 FFN 替换成 $N$ 个并行的 FFN 块，每个 FFN 是一个"专家"；
- **路由器（Router / Gate）**：一个轻量线性层，给每个 token 对每个专家打分，选出分数最高的 $k$ 个专家（top-k 稀疏选择）；
- **稀疏激活（Sparse Activation）**：每个 token 的前向只经过 $k$ 个专家，其余 $N-k$ 个专家不参与计算（但权重仍在显存里）。

一句话记忆：**"模型容量看总参数，计算开销看激活参数"**——MoE 用"参数量大、激活量小"的架构，把两者解耦。

## 二、为什么需要 MoE

### 2.1 根本矛盾：想要参数量大，但算力花不起

深度学习有个经验规律：**模型越大，下游能力越强**。但参数量 $\times$ 训练数据量的总计算量约等于 $6ND$ FLOPs，参数量 $N$ 直接换算成训练成本：

- 7B 密集模型训练 2T token 需要约 $8.4\times10^{22}$ FLOPs（单卡约 9 年，见 [分布式训练详解](../分布式训练/分布式训练详解.md) 1.2）；
- 参数量翻 10 倍到 70B，训练成本也近似翻 10 倍——**"把模型做大"和"把成本压低"在密集架构里是同一个变量，无法两全**。

### 2.2 容量与计算解耦：MoE 的核心创新

MoE 的关键洞察：**参数量（容量）与计算量（成本）不必成正比**。

- 总参数量 $N_{total}$ 决定模型的"知识容量"（能记住多少模式、多少事实）；
- 激活参数量 $N_{active}$（每个 token 实际经过的参数）决定"单次前向的计算成本"；
- 密集模型里 $N_{total} = N_{active}$；MoE 里 $N_{total} \gg N_{active}$。

以 Mixtral 8x7B 为例：总参 47B，每 token 激活 13B——**用密集 13B 的计算成本，换接近 47B 的表达能力**。

### 2.3 推理算力按激活参数计

大模型推理（尤其长上下文）的成本瓶颈是**单 token 前向的 FLOPs**，它与激活参数成正比：

$$\text{单 token 前向 FLOPs} \approx 2 \times N_{active} \times L$$

代入具体数字感受一下：

- 密集 70B：每 token 都要算 70B 参数 → 单 token 约 140B FLOPs/层；
- MoE 671B（激活 37B）：参数量接近密集 70B 的 10 倍，但每 token 只算 37B → 单 token 约 74B FLOPs/层，**推理吞吐可以逼近 13B 级密集模型**。

这也是"MoE 是省训练成本还是省推理成本"面试题的答案：**训练时按总参数算显存、按激活参数算算力；推理时 GPU 算力只花在激活参数上，但显存必须装下全部专家权重**（详见第七节对比表）。

### 2.4 一个类比：餐厅后厨

- 密集模型 = 一个全能厨师，无论点什么菜都亲自做（每道菜成本都高）；
- MoE = 一个餐厅 + 一个前台（路由器）：有 8 位专职厨师（专家），每道菜（token）由前台判定后只交给最擅长的 2 位厨师（top-2）做，其余 6 位休息；
- 厨房面积（显存）得按 8 位厨师配置，但每道菜的人工成本（算力）只按 2 位算——**"备得全、做得省"**。

## 三、核心组件：路由器 + 专家池 + 门控

```
                 ┌───────────────────────────────────────────┐
                 │           路由器 Router (门控)              │
                 │   打分: g(x) = Softmax(W_g · x)            │
                 │   选择: 每 token 取分数最高的 top-k 个专家      │
                 └───────────────────────────────────────────┘
                          │              │              │
              ┌───────────┘              │              └───────────┐
              ▼                          ▼                          ▼
      ┌───────────────┐          ┌───────────────┐          ┌───────────────┐
      │   专家 1 FFN   │          │   专家 2 FFN   │    …     │   专家 8 FFN   │
      │   (被激活)     │          │   (被激活)     │          │   (未激活，跳过) │
      └───────────────┘          └───────────────┘          └───────────────┘
              │                          │                          │
              └────────── 加权求和: y = Σ g_i(x) · FFN_i(x) ──────────┘
                                              │
                                              ▼
                                          输出 y
```

### 3.1 专家池（Expert Pool）

- 结构：$N$ 个并行的 FFN 块（$W_1 \to \text{GELU} \to W_2$），替换掉标准 Transformer 每个 block 里的单个 FFN；
- 常见规模：Mixtral 每层 8 个专家；DeepSeek-V3 每层 1 个共享专家 + 256 个路由专家；
- 关键点：**所有专家权重常驻显存**，训练/推理都要为全部专家分配显存。

**专家要不要初始化成一样的？**

两个常见选择：

1. **随机初始化**（主流）：各专家初始权重独立随机，训练早期由路由器自由分配 token，专家自然分化；
2. **复用预训练 FFN**（蒸馏/升级场景）：把已训好的密集模型 FFN 复制多份作为专家初值（如 Mixtral 初始化的常见做法），收敛快但专家分化慢。

### 3.2 路由器（Router / Gate）

- 一个不带偏置的线性层 $W_g \in \mathbb{R}^{d \times N}$，输入 token 表示 $x$，输出每个专家的分数：
  $$g(x) = \text{Softmax}(W_g \cdot x)$$
- 选 top-k：只取分数最高的 $k$ 个专家（$k$ 通常为 1~8）；
- 参数量极小（$d \times N$，可忽略），是 MoE 里"最便宜也最关键"的组件——它决定了专家们"忙不忙、忙什么"。

**为什么门控通常不加 bias？**

如果 $g(x) = \text{Softmax}(W_g \cdot x + b_g)$，bias 会无条件抬高某些专家的分数——**不看 token 内容就偏心**，加剧路由坍缩（少数专家吸收所有 token）。去掉 bias 后，路由完全由 token 内容驱动，均衡由独立的负载均衡机制负责。DeepSeek-V3 恰恰反其道而行：**显式加一个专家级 bias 用于均衡**（内容打分和均衡 bias 分离，互不干扰，详见子篇第四节）。

### 3.3 门控（Gating / 加权）

- 每个 token 的最终输出 = 被选中的 $k$ 个专家输出的**加权和**：
  $$y = \sum_{i \in \text{top-k}(x)} g_i(x) \cdot \text{FFN}_i(x)$$
- 权重 $g_i(x)$ 在选中集合内归一化（$\sum g_i = 1$），保证输出尺度与密集 FFN 一致；
- 加权方式还有变体：softmax 门控（Mixtral）、sigmoid 门控（DeepSeek-V3）、无归一化的专家输出拼接（GShard 早期版本）等，详见 [路由机制与负载均衡.md](路由机制与负载均衡.md) 第一、二节。

## 四、关键数字示例

| 模型 | 总参数 | 每 token 激活参数 | 稀疏度（激活/总参） | 每层专家配置 | top-k |
| --- | --- | --- | --- | --- | --- |
| Mixtral 8x7B | 47B | 13B | ~28% | 8 个专家 | 2 |
| DeepSeek-V3 | 671B | 37B | ~5.5% | 1 共享 + 256 路由 | 8（路由部分） |
| Qwen3-30B-A3B | 30.5B | 3.3B | ~11% | 128 个专家 | 8 |

几个解读：

1. **Mixtral 8x7B 的"8x7B"是命名法不是参数量**：总参 47B（8 个约 7B 的 FFN 块分摊在 32 层里 + 共享的 attention 层），每 token 激活 13B（8 选 2 的一半 FFN + 全部 attention）；
2. **DeepSeek-V3 是"高稀疏度"的极致**：256 个路由专家里每 token 只激活 8 个 + 1 个共享专家，稀疏度低到 5.5%，671B 总参的推理成本逼近 37B 密集模型；
3. **Qwen3-30B-A3B 命名法**：A3B 表示每 token 激活约 3.3B（"A" = active），是"中等总参、极低激活"的移动端友好形态；
4. **稀疏度越低越省算力，但对路由均衡要求越高**——8 选 2 时每个专家至少得处理约 25% 的 token，256 选 8 时平均只有约 3%，负载不均衡的放大效应更强（详见子篇"路由机制与负载均衡"）。

## 五、稀疏激活的原理

### 5.1 逐 token 走 top-k 个专家 FFN

对一条长度为 $T$ 的序列，MoE 层的前向流程：

1. 每个 token 独立计算门控分数 $g(x_t) = \text{Softmax}(W_g \cdot x_t)$；
2. 每个 token 独立选 top-k 专家（**不同 token 可以选不同专家，互不干扰**）；
3. 按 token 分组，把属于同一专家的 token 打包成 batch，一次并行前向该专家的 FFN；
4. 各专家输出乘以各自门控权重后累加回对应 token。

### 5.2 稀疏激活省多少算力

$N$ 个专家、top-k 选择时，FFN 部分计算量降为密集版的 $k/N$：

- Mixtral（8 选 2）：FFN 计算量 ×25%，整个模型约省一半算力；
- DeepSeek-V3（256 选 8 + 1 共享）：FFN 计算量 ≈ ×3.5%；
- 结论：**稀疏激活让"每层有 $N$ 个专家但只算 $k$ 个"成为可能，这是 MoE 省算力的全部来源**。

把上面的直觉换成 FLOPs 公式：标准 Transformer 中 FFN 约占单层计算量的 2/3。MoE 化后单层计算量为

$$C_{layer} = C_{attn} + \frac{k}{N} \cdot C_{ffn}$$

当 $k/N = 0.25$（Mixtral）时单层算力约为密集版的 0.33 + 0.67×0.25 ≈ 0.5，即**整体减半**；$k/N \approx 0.035$（DeepSeek-V3）时更是逼近"只算注意力"。

### 5.3 稀疏激活与 batch 调度的关系

稀疏激活会带来一个工程麻烦：**每个专家的输入 batch 大小不一**。

- 密集模型：所有 token 走同一个 FFN，天然是一个大矩阵乘；
- MoE 模型：token 要先按专家分组，再分别做矩阵乘——专家之间的负载不均衡直接变成"快专家等慢专家"的 GPU 空转；
- 因此"让每个专家拿到的 token 数尽量均匀"（负载均衡）不只是训练稳定的问题，也是**推理吞吐**问题（详见 [路由机制与负载均衡.md](路由机制与负载均衡.md) 第四节）。

### 5.4 为什么稀疏反而更强

直觉上"少算了参数"应该更弱，但实验（Switch Transformer / Mixtral）反复证明 MoE 在**同激活算力**下显著优于密集模型，原因：

1. **专家专业化（Specialization）**：不同的专家被路由到不同"领域"的 token（数学符号、代码语法、中文实体、图像 token 等），训练中自然分化出分工——总体表达能力超过任何一个单专家；
2. **容量大 = 记忆强**：47B 的总参可以"背"下比 13B 密集模型多得多的知识，而每 token 只花 13B 的成本去"检索+计算"；
3. **训练更稳定**：同总参比密集模型，MoE 的训练曲线通常更平滑（Dropout 只加在非专家部分，路由噪声有正则化效果）。

## 六、优势与代价

| 维度 | 优势 | 代价 |
| --- | --- | --- |
| 训练速度 | 同效果下训练 FLOPs 更少（Switch Transformer 论文：同算力提升 4~7 倍效率） | 分布式通信开销增加（token 要在专家所在卡之间 all-to-all 搬运） |
| 推理速度 | 每 token 只算 top-k 专家，吞吐可逼近小得多的密集模型 | 显存需求仍按**全部专家权重**计，70B 级 MoE 必须多卡部署 |
| 模型容量 | 总参数可做到同级别密集模型的 5~10 倍，知识容量大 | 需要额外的负载均衡机制，否则少数专家"坍缩"吸收所有 token（routing collapse） |
| 扩展性 | 新增专家即"增量扩参"，可复用已有训练好的专家（modular 式升级） | 专家越多，负载均衡越难、通信越重，收益递减 |
| 微调 | 下游微调可只更新被激活的专家（参数高效） | 全量微调复杂：需要处理路由坍缩、aux loss 权重、冻结/解冻策略；SFT 后路由分布漂移需回填训练数据 |

**一句话权衡**：MoE 用"显存换算力"——训练和推理的**算力**大幅节省，但显存、通信、调优**复杂度**显著上升。

### 6.1 哪些场景适合用 MoE

| 场景 | 是否适合 | 原因 |
| --- | --- | --- |
| 万亿级预训练、超大集群 | 非常适合 | 算力成本是主约束，稀疏激活省 FLOPs 立竿见影 |
| 高并发推理服务（API 网关） | 非常适合 | 多用户并发下算力优势充分释放，batch 填充掩盖带宽瓶颈 |
| 单卡/低算力环境推理 | 不适合 | 权重常驻显存，单卡放不下大 MoE；小 batch 带宽瓶颈严重 |
| 长上下文多模态推理 | 适合 | 视觉 token 海量，稀疏激活收益被放大 |
| 快速迭代的小规模微调 | 谨慎 | 全量微调路由易坍缩，多用 LoRA 冻结路由的策略 |

### 6.2 与分布式训练的关系（衔接模块）

MoE 与 [分布式训练](../分布式训练/分布式训练详解.md) 紧密相关：专家并行（EP）是分布式训练章节里的"第六种并行"——各专家放不同卡，token 经 **all-to-all** 通信发往目标专家所在卡，算完再收回来。训练一个 671B 的 MoE，至少需要 EP × DP（甚至 EP × TP × DP × PP 的 3D 组合），这也是"MoE 省算力但费工程"的另一层含义。

## 七、与密集模型的对比

| 对比项 | 密集模型（Dense） | MoE 模型 |
| --- | --- | --- |
| 参数量 | 训练用多少就是多少（7B/13B/70B） | 总参 47B~671B，命名常写 "总参-A激活" |
| 激活量 | 每 token 激活全部参数 | 每 token 只激活 top-k 专家（如 671B 中激活 37B） |
| 显存需求 | 按参数量线性（70B ≈ 140GB BF16 权重） | 按**总参**计（671B 权重 >1.3TB，单卡放不下，必须 EP/TP） |
| 训练成本 | 约 $6ND$ FLOPs，与参数量严格线性 | 按激活参数算 FLOPs（约 $6N_{active}D$），同效果成本可低数倍 |
| 推理成本 | 单 token 算力 = 全部参数 | 单 token 算力 ≈ 激活参数，但显存带宽仍可能被全部权重访问拖累 |
| 显存带宽瓶颈 | 权重加载与算力匹配 | **带宽成为隐藏瓶颈**：FP8 下 671B 每 token 需读 671GB，即使只算 37B 的参数 |
| 训练稳定性 | 相对简单 | 需要路由均衡（aux loss / bias 路由）、容量截断、专家 dropout 等机制 |
| 部署复杂度 | 单卡/数据并行即可 | 需要专家并行（EP）、all-to-all 通信、容量管理 |
| 微调 | 成熟简单 | 路由分布可能坍缩/漂移，需专门策略 |

**工程视角补充**：MoE 推理有一个反直觉现象——**显存带宽成为瓶颈**。以 DeepSeek-V3 为例，FP8 下每 token 都要把 671B 权重（671GB）从显存读到寄存器（即使只计算其中 37B），内存带宽消耗接近密集 671B 模型；因此 MoE 在高吞吐场景（多并发）优势显著，在低并发、小 batch 时优势被带宽稀释。这也是"MoE 到底省不省算力"的正确答法：**省 FLOPs，但不一定省带宽**。

## 八、多模态中的 MoE

多模态模型天然是 MoE 的受益者：视觉 token 数量巨大（一张图 256~1024 个 patch token），用稀疏激活能大幅压低视觉前向算力；同时多模态任务类型差异大（OCR、图表、具身、视频），专家更容易分化出跨模态分工。

### 8.1 Qwen3-VL（MoE 旗舰）

- 主力版本 Qwen3-VL-235B-A22B：总参 235B、每 token 激活 22B，是当前开源最强多模态 MoE 之一；另有 Qwen3-VL-32B-A3B 面向端侧；
- 视觉编码器与 LLM 解耦：视觉塔（Vision Transformer）负责把图像/视频/UI 界面转成视觉 token，送入 MoE 的 LLM 主干；
- 特点：视觉 token 也走 MoE 路由，且支持超长上下文——上下文越长、视觉 token 越多，稀疏激活的算力优势越被放大；
- 多模态 MoE 新问题：**图像 token 与文本 token 的专家偏好不同**，若均衡损失把两类 token 强行拉均匀，会损伤模态专业化。

### 8.2 DeepSeek-VL2

- 总参 27.5B、每 token 激活约 4.5B，底座直接继承 DeepSeek-MoE 的**细粒度专家 + 共享专家**架构（sigmoid 门控、bias 均衡，无 aux loss）；
- 多模态适配要点：
  - 视觉侧做 **Pixel Shuffle（像素打散）**：把相邻 2×2 patch 的特征拼进通道维度，视觉 token 数降为 1/4，缓解视觉 token 对路由与注意力的双重压力；
  - 输入图切分（Tiling）+ 全局/局部双注意力，适配高分辨率文档、图表；
  - 共享专家保证"通用计算"不被稀疏路由丢掉——多模态 token 差异大，纯 top-k 路由可能丢公共模式。

### 8.3 多模态 MoE 的共性挑战

1. **模态不平衡**：文本 token 通常远少于视觉 token，路由均衡（aux loss）必须考虑模态维度，否则文本专家被视觉 token 挤占；
2. **视觉 token 语义稠密**：同一张图的不同 patch 高度相关，top-k 路由可能把相关 patch 塞进同一专家造成局部过载，容量管理更关键；
3. **路由稳定性**：SFT/RLHF 阶段视觉 token 分布变化大，路由漂移风险高于纯文本模型；
4. **训练成本**：视觉塔通常冻结 + 只训 MoE 主干与投影层，与 [参数高效微调PEFT](../参数高效微调PEFT/参数高效微调PEFT.md) 组合使用。

### 8.4 两个代表模型的横向对比

| 对比项 | Qwen3-VL-235B-A22B | DeepSeek-VL2 |
| --- | --- | --- |
| 总参 / 激活参 | 235B / 22B | 27.5B / 约 4.5B |
| MoE 底座 | Qwen3 系（自研 MoE，多路由） | DeepSeek-MoE（细粒度专家 + 共享专家） |
| 门控方式 | softmax 系门控 + 均衡策略 | sigmoid 门控 + 专家级 bias（无 aux loss） |
| 视觉压缩 | 标准 ViT + 长上下文优化 | Pixel Shuffle（视觉 token 压缩 4 倍）+ Tiling |
| 典型场景 | 高分辨率文档、视频、Agent | 高分辨率图表、OCR、移动端 |

（门控与均衡策略的差异详解见 [路由机制与负载均衡.md](路由机制与负载均衡.md) 第二、四节。）

## 九、高频面试问答

**Q1：MoE 相比密集模型到底省了什么、不省什么？**
省的是**计算量（FLOPs）**：每 token 只算 top-k 个专家，训练和推理的单 token 算力按激活参数计。不省的是**显存**（全部专家权重常驻）和**显存带宽**（每 token 都要读全部权重）。

**Q2：为什么 MoE 参数量大反而训练更快？**
训练成本 ≈ $6N_{active}D$，只与激活参数挂钩。47B 总参、13B 激活的 Mixtral，训练算力接近 13B 密集模型，但效果接近同容量密集模型。

**Q3：8x7B 是 56B 吗？**
不是。Mixtral 8x7B 总参 47B：32 层每层 8 个专家 FFN + 共享 attention 层，8 个"7B"分摊进整层里，总参不是简单相乘。

**Q4：MoE 推理的隐藏瓶颈是什么？**
显存带宽。671B 模型每 token 必须把全部权重从显存读到计算单元（即使只算 37B），小 batch 时带宽是主导瓶颈，高并发时算力优势才充分体现。

**Q5：多模态 MoE 和纯文本 MoE 的差别？**
① 视觉 token 数量大，稀疏激活收益更明显；② 模态不平衡影响路由均衡；③ 需要视觉 token 压缩（Pixel Shuffle）与控制；④ SFT 阶段路由漂移风险更高。

**Q6：MoE 适合微调吗？**
可以，但要注意路由分布坍缩与漂移：轻量做法是只微调激活的专家参数（类似 LoRA 但天然稀疏），全量微调需配合均衡损失与回填数据。
