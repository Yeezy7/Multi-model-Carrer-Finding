# 专家并行与推理：MoE 的分布式与部署

> 本模块索引见 [MoE详解](MoE详解.md)

## 一、定义与公式

### 1.1 什么是专家并行（EP）

**专家并行（Expert Parallelism，EP）= 把 $N$ 个专家按 GPU 切开，每张卡只持有其中一部分专家权重；token 由路由器决定去哪个专家，再通过 all-to-all 通信把 token 发到目标专家所在的卡上计算，算完把结果收回来。**

先复习 MoE 层前向（详见 [MoE详解](MoE详解.md) 第三节）：

$$g(x) = \mathrm{Softmax}(W_g x), \qquad \mathcal{S} = \mathrm{TopK}(g, k), \qquad y = \sum_{j=1}^{k} \hat{g}_{i_j} \cdot f_{i_j}(x)$$

- $N$ 个专家 FFN $f_1, \dots, f_N$，每 token 只激活 $k$ 个（top-k），其余 $N-k$ 个**权重仍在显存里，但不参与计算**。

矛盾：Mixtral 权重 ≈ 94GB（FP16）、DeepSeek-V3 权重 ≈ 1.34TB（FP16），单卡装不下；但每个 token 只算 13B / 37B 的参数。**"权重必须全部常驻、算力只花一小部分"** 这个矛盾决定了 MoE 必须有新的切分方式——按专家切（EP），而不是按数据切（DP）或按矩阵切（TP）。

### 1.2 与数据并行/张量并行的核心区别

| 维度 | 数据并行 DP | 张量并行 TP | 专家并行 EP |
| --- | --- | --- | --- |
| 切什么 | 数据（batch） | 权重矩阵内部（行列） | 专家（按专家编号） |
| 每卡持有什么 | 完整模型副本 | 每个矩阵的 1/P | 一部分专家 + 全部共享层 |
| 单步计算 | 完整前向 + 反向 | 多卡协作一次 matmul | 只算本卡上的专家 |
| 主要通信 | 梯度 all-reduce（每步 1 次） | 每层激活 all-reduce | 每层两轮 all-to-all |
| 通信量 | ∝ 权重大小 | ∝ 激活 $O(T \cdot h)$ | ∝ $T \cdot k \cdot h$（$k$ = top-k） |
| 本质 | 时间换吞吐 | 显存换单卡算力 | 显存换容量（专家数） |

一句话：**DP 复制模型、TP 切开矩阵、EP 切开专家**。

### 1.3 为什么稠密模型用不上 EP

稠密模型所有参数每 token 都参与计算，任意时刻整卡都在算同一份权重，DP/TP 已覆盖全部需求。EP 是 MoE 特有的切分：专家之间相互独立、可任意分布，而"每个 token 访问哪 k 个专家"由路由动态决定——于是"专家放哪张卡"和"token 送到哪张卡"就成了新问题。

## 二、核心原理：all-to-all 两轮通信

### 2.1 一条 token 的完整旅程

EP 下 MoE 层前向分 5 步（$P$ 张卡，卡 $p$ 拥有专家子集 $\mathcal{E}_p$）：

1. **路由**（本卡完成，零通信）：每卡对自己分到的 token 算门控分数、取 top-k；
2. **第一轮 all-to-all（dispatch / send）**：把"选中专家在别卡"的 token 打包发给目标卡，同时接收别卡发给本卡本地专家的 token；
3. **专家计算**：每卡对自己收到的 token 跑本地专家 FFN（纯计算，零通信）；
4. **第二轮 all-to-all（combine / gather）**：专家输出原路送回 token 出发的卡；
5. **加权还原**：每卡把送回的结果按门控权重加权求和，恢复 batch 顺序。

第 2、4 步都是**全连接**的（任意两卡之间都可能互发数据）——这正是 all-to-all 与 all-reduce / point-to-point 的本质区别。

### 2.2 第一轮 dispatch：token 跟着路由走

```
  卡0 本地 token: [A B C D E F]          卡1 本地 token: [G H I J K L]
        │ 路由: A→专家1(卡0) B→专家5(卡1) C→专家3(卡0) ...
        ▼
  卡0 发送给卡1: [B, ...]  ────────────────▶ 卡1 接收
  卡1 发送给卡0: [H, ...]  ────────────────▶ 卡0 接收
        │ 第 1 轮 all-to-all（send 与 receive 同时进行）
        ▼
  卡0 的本地专家（专家0~3）收到自己应处理的 token；卡1 的本地专家（专家4~7）同理
```

关键点：路由是纯局部的（不需要通信），但**谁要发什么取决于路由结果**，而路由结果依赖输入——所以发送内容每步都在变，EP 通信无法像 TP 那样预先规划静态通信模式。

### 2.3 第二轮 combine：结果送回原地

专家算完后，结果必须回到 token 原本的位置（否则 batch 顺序错乱，后续层无法计算）。第二轮是"反向的 all-to-all"：

```
  卡0 专家输出: [B的结果, ...]  ────────▶ 送回卡1（B 的出发地）
  卡1 专家输出: [H的结果, ...]  ────────▶ 送回卡0（H 的出发地）
        │ 第 2 轮 all-to-all（gather）
        ▼
  每卡恢复各自 token 的完整输出（每个 token 的 k 个专家结果按门控权重求和）
```

两轮合起来是"一次完整往返"：**send 前一轮、gather 后一轮**。所有主流实现（Tutel、FastMoE、DeepSpeed、vLLM）都逃不开这个结构，差别只在用真正的 all_to_all 还是 all_gather + scatter 的组合、以及是否做计算-通信重叠。

### 2.4 通信量公式

设全系统 $T$ 个 token、每 token 激活 $k$ 个专家、隐藏维 $h$、每元素 $b$ 字节：

- 第一轮（dispatch）：每个 token 的 $k$ 份表示（每份 $h$ 维）移动一次；
- 第二轮（combine）：每个 token 的 $k$ 份输出（每份 $h$ 维）再移动一次。

$$C_{\text{EP}} = 2 \times T \times k \times h \times b \quad (\text{全系统、每层})$$

单卡视角（负载均衡时）：每卡每层进出各约 $\frac{T}{P} \times k \times h \times b$ 字节。

代入真实模型：

| 模型 | T | k | h | b | 每层两轮 | MoE 层数 | 每步合计 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Mixtral 8x7B | 2048 | 2 | 4096 | 2B(FP16) | ≈ 67MB | 32 | ≈ 2.1GB |
| DeepSeek-V3 | 8192 | 8 | 7168 | 1B(FP8) | ≈ 940MB | 58 | ≈ 54GB |

结论：**通信量 ∝ token 数、top-k、隐藏维，与专家总数 $N$ 无关**。$k$ 从 2 涨到 8，通信量直接 ×4——这是"专家变多"时推理工程最先撞到的墙。

### 2.5 为什么 EP 通信是 MoE 的主要开销

1. **每层都有**：每个 MoE 层两轮 all-to-all，稠密模型每步才一次梯度通信；
2. **随 k 线性放大**：TP 的通信是 $O(T \cdot h)$（一次激活的大小），EP 是 $O(T \cdot k \cdot h)$——$k=8$ 时 EP 每层搬运的数据 ≈ 8 个完整激活；
3. **动态不可规划**：发送内容由路由决定，计算-通信重叠困难；
4. **负载不均衡放大**：某专家收 token 过多时，该卡通信量和计算量同时超载，成为整层瓶颈（木桶效应）——负载均衡不仅是训练问题，也是通信问题的放大器（详见 [路由机制与负载均衡](路由机制与负载均衡.md)）；
5. **反向再翻倍**：反向传播的梯度也要按路由原路返回，通信成本再 ×2。

## 三、源码实现：纯 tensor 模拟两卡专家并行

以下代码用纯 tensor 操作完整模拟"路由 → 第 1 轮 all-to-all（按专家重排）→ 专家计算 → 第 2 轮 all-to-all（还原顺序）→ 加权求和"，并输出负载统计与通信量。可直接运行：

```python
import torch

torch.manual_seed(0)

# ---------- 配置 ----------
T, N, K, H = 24, 8, 2, 8      # token 数、专家数、top-k、隐藏维
P = 2                         # 模拟 2 张卡
E_per_rank = N // P           # 每卡 4 个专家
T_per_rank = T // P           # 每卡 12 个 token

# ---------- 1. 路由（本卡完成，零通信） ----------
x = torch.randn(T, H)                        # 24 个 token 的表示
Wg = torch.randn(H, N) * 0.2
gates = torch.softmax(x @ Wg, dim=-1)        # [T, N] 门控分数
topk_val, topk_idx = torch.topk(gates, K, dim=-1)     # [T, K] 选中的专家
scores = topk_val / topk_val.sum(-1, keepdim=True)   # top-k 内归一化权重

# ---------- 2. 负载统计（通信前，路由的天然分布） ----------
loads = torch.zeros(N)
loads.scatter_add_(0, topk_idx.flatten(), torch.ones(T * K))
print("各专家负载:", loads.int().tolist())
print(f"最大/平均 = {loads.max().item() / loads.mean().item():.2f}")
# 输出示例: 各专家负载: [9, 5, 2, 4, 8, 7, 7, 6]
#          最大/平均 = 1.50   （随机路由天然不均衡，后续由负载均衡机制校正）

# ---------- 3. 第 1 轮 all-to-all（dispatch）：把 token 按专家重排 ----------
tok_id = torch.arange(T).repeat_interleave(K)        # 每个 slot 属于哪个 token
exp_id = topk_idx.flatten()                          # 每个 slot 选中的专家
score_flat = scores.flatten()
order = torch.argsort(exp_id, stable=True)           # 按专家排序 = 到达目标卡后的收件顺序
tok_sorted, exp_sorted, score_sorted = tok_id[order], exp_id[order], score_flat[order]

counts = torch.bincount(exp_id, minlength=N)         # 每个专家的收件数
bounds = torch.cat([torch.zeros(1, dtype=torch.long), counts.cumsum(0)])

# 模拟"谁发给谁"：token 出发卡 vs 专家所在卡
sender = tok_id // T_per_rank
receiver = exp_id // E_per_rank
send_mat = torch.zeros(P, P, dtype=torch.long)
send_mat.index_put_((sender, receiver), torch.ones_like(sender), accumulate=True)
print("第 1 轮 all-to-all 发送矩阵（行=出发卡，列=目标卡）:\n", send_mat)
# 输出示例: tensor([[12, 12], [8, 16]])  → 卡0 发给卡1 共 12 个 slot，卡1 发给卡0 共 8 个 slot

# ---------- 4. 专家计算（每卡只算自己的 4 个专家） ----------
def expert_ffn(z, e):                       # 每个专家的 FFN（简化版）
    torch.manual_seed(100 + e)              # 同一专家权重固定，便于第 6 步验证
    W1 = torch.randn(H, H) * 0.2
    W2 = torch.randn(H, H) * 0.2
    return torch.relu(z @ W1) @ W2

out_sorted = torch.zeros(T * K, H)
for e in range(N):
    s, en = bounds[e].item(), bounds[e + 1].item()
    if s == en:                             # 本批没有 token 路由到这个专家
        continue
    owner = e // E_per_rank                 # 专家 e 所在的"卡"
    # 真实实现：第 1 轮 all-to-all 之后，[s:en] 这段 token 已躺在 owner 卡的显存里
    out_sorted[s:en] = expert_ffn(x[tok_sorted[s:en]], e)   # 取 token 向量送进专家 FFN
    print(f"专家 {e}（卡{owner}）：处理 {en - s} 个 token")
# 输出示例: 专家 0（卡0）：处理 9 个 token
#          专家 1（卡0）：处理 5 个 token ...

# ---------- 5. 第 2 轮 all-to-all（combine）：结果按原 slot 放回 ----------
out_orig = torch.zeros(T * K, H)
out_orig[order] = out_sorted                 # 逆置换 = 结果原路送回
restored = out_orig.view(T, K, H)            # [T, K, H]：每个 token 的 k 个专家输出
y_ep = (restored * scores.unsqueeze(-1)).sum(dim=1)   # 门控加权求和 → [T, H]

# ---------- 6. 与逐 token 参考实现对比（验证正确性） ----------
y_ref = torch.zeros(T, H)
for t in range(T):
    for j in range(K):
        y_ref[t] += scores[t, j] * expert_ffn(x[t:t + 1], topk_idx[t, j].item())[0]
print("EP 模拟结果与参考实现一致:", torch.allclose(y_ep, y_ref, atol=1e-5))
# 输出: EP 模拟结果与参考实现一致: True

# ---------- 7. 通信量统计 ----------
bytes_per_round = T * K * H * 4              # FP32 每元素 4 字节
print(f"每层两轮 all-to-all ≈ {2 * bytes_per_round / 1024:.1f} KB（T={T}, k={K}, h={H}）")
# 输出: 每层两轮 all-to-all ≈ 3.0 KB
```

**代码与真实系统的对应关系**：
- `argsort(exp_id)` = 第 1 轮通信结束后，目标卡上 token 按专家聚拢的排列；
- 循环 `for e in range(N)` 中只处理 `owner` 卡上的专家 = 真实世界"每卡只持有 4 个专家权重"；
- `out_orig[order] = out_sorted` = 第 2 轮通信把结果送回原卡；
- `loads` / `send_mat` / `counts` 与线上观察负载均衡、通信矩阵的统计完全同构。

## 四、深入分析

### 4.1 与 TP/DP/PP 的组合：DeepSeek-V3 的 EPTB

671B 权重、每 token 激活 37B——没有单一并行能独自扛住，DeepSeek-V3 用的是 **EP + TP + DP（EPTB）** 混合：

1. **专家切分（EP）**：全部 256 个路由专家分布在 **4 个节点共 32 张卡**上，每卡 8 个专家、每节点 64 个专家；节点内 8 卡即一个 EP 子组（卡间 NVLink 互联）；
2. **token 分发**：每 token 激活 8 个专家，可能落在 1~4 个节点上 → dispatch/combine 的 all-to-all **节点内走 NVLink（约 900GB/s）、跨节点走 InfiniBand（约 200GB/s）**；
3. **注意力层**：节点内 8 卡做 TP（张量并行），共享/稠密层权重每个 EP 组各有一份；
4. **数据并行（DP）**：不同 EP 组之间复制模型、分配不同 batch，把吞吐做上去（训练 2048 卡时 EP 组之外全走 DP）；
5. 配套优化：MLA 压缩 KV cache、FP8 权重减半、MTP 模块配合推测解码（见 4.4）。

为什么这样组合：**只靠 TP 切不动**（专家按"个"为单位，TP 切矩阵要求全组每层 all-reduce，专家一多通信爆炸）；**只靠 DP 装不下**（每卡要复制全部 671B 权重）；**只靠 PP 吃不饱**（流水线气泡浪费大）。EP 管"专家放哪"、TP 管"注意力怎么切"、DP 管"并发多大"——各司其职。

### 4.2 推理显存真相：全部专家必须常驻显存

**最常见的误解：MoE 推理省显存。错。** 路由是输入相关的，服务端无法预知下一个 token 会激活哪个专家——**所有专家权重必须同时驻留显存，一个都不能少**。省的是算力（FLOPs），不是显存。

以 Mixtral 8x7B 为例的完整账本（FP16 权重）：

| 项目 | 数值 | 说明 |
| --- | --- | --- |
| 总参数 | 46.7B | 8 专家 FFN + 共享注意力/embedding |
| 每 token 激活参数 | 12.9B | 全部注意力 + 2/8 的专家 FFN |
| 权重显存（FP16） | ≈ 93.4GB | 46.7B × 2B——**必须全部加载** |
| 权重显存（INT8 / INT4） | ≈ 47GB / ≈ 23GB | 量化后才能塞进单卡 |
| 每 token 计算量 | ≈ 2 × 12.9B ≈ 26 GFLOPs | 不含注意力 |
| 同规模稠密 47B 的每 token 计算量 | ≈ 93 GFLOPs | MoE 只需约 1/3.6 |
| KV cache（4K 上下文、单请求） | 约 1~2GB | 与稠密模型相当，非 MoE 特有 |
| 激活（中间结果） | 数 GB 级 | 远小于权重 |

**三个结论**：
1. 显存账 = 总参数账（94GB 一分不少），算力账 = 激活参数账（26 vs 93 GFLOPs）——MoE 的"省"与"不省"截然分开；
2. 单卡 80GB 放不下 FP16 的 Mixtral（94GB），需 2×80GB；INT4 量化（≈23GB）后单卡可跑；
3. 放大到 DeepSeek-V3：FP16 权重 1.34TB，FP8 ≈ 671GB ≈ 8×80GB 打满——官方称单节点 8×H800 可部署（极限配置），社区更稳的方案是 8×96GB（H20）或 16 卡。

### 4.3 为什么 MoE 吞吐高、但单请求延迟不一定低

**吞吐高（每 token 算得少 → 单卡可并发更多请求）**：
- H800 约 800 TFLOPS（FP8）：DeepSeek-V3 每 token ≈ 74 GFLOPs（2×37B），理论单卡约 10k token/s；同算力下稠密 671B（每 token 1.34 TFLOPs）只有约 600 token/s——**吞吐差一个数量级**；
- 高并发服务 batch 大、算力被填满，EP 通信被计算掩盖 → 吞吐优势充分兑现（vLLM/SGLang 部署 MoE 的收益主要来自这里）。

**单请求延迟不一定低（通信 + 同步在低并发下暴露）**：
- 小 batch 时每层两轮 all-to-all 的**往返时延 + 同步等待**无法被计算掩盖：跨节点单 token 每层搬运 ≈ $k \times h \times b$ = 8×7168×1B ≈ 57KB，两轮 ≈ 115KB，IB（200GB/s）理论仅约 0.6µs，但网络时延、排队、卡间同步会把实际开销推到数 µs 级；
- 与计算对比：V3 每层激活 ≈ 638M 参数 ≈ 1.3 GFLOPs，单卡约 1.6µs——**低并发下通信与计算同量级**，延迟几乎翻倍；
- **负载不均衡放大**：最慢的卡（收 token 最多的卡）决定整层耗时，快卡算完也要干等；
- 所以：**MoE 适合"高并发聚合吞吐"，不适合"单请求低延迟"**（实时流式对话需配合推测解码等手段，见 4.4）。

### 4.4 推理工程：vLLM、推测解码与预填充优化

**vLLM 对 MoE 的支持**：
- vLLM（0.6+）原生支持 Mixtral、DeepSeek-V2/V3、Qwen3-MoE 等；
- TP>1 时默认把专家按 rank 分片（每 rank 持有 $N/\text{TP}$ 个专家），token 用 all-to-all 分发——**本质上就是用 TP 通信域实现的专家并行**；
- DeepSeek-V3 官方推荐 SGLang（或自研框架）部署：MLA + EP + FP8，公开方案即 8×H800 单节点；
- 部署要点：**EP 组要尽量落在同一节点内**（NVLink），跨节点 EP 只适合高带宽 IB；优先保证"全部专家在一个节点装得下"。

**推测解码（Speculative Decoding）**：小模型（或 MoE 的 MTP 头）先草拟 $n$ 个 token，主模型一次并行验证。对 MoE 意义特殊——每 token 计算少但通信/调度开销高，一次验证 $n$ 个 token 把"两轮 all-to-all"的次数摊薄 $n$ 倍。DeepSeek-V3 训练期训练的 MTP（multi-token prediction）模块，推理时正好当草稿模型用。

**预填充（Prefill）优化**：
- 预填充阶段 token 海量、算力吃满、通信占比低 → 策略是"算得快"：chunked prefill 把长 prompt 切块、与解码混排，避免空闲；
- 解码阶段 token 稀少、通信/带宽占比高 → 策略是"延迟低"：连续批处理 + 专家负载感知的调度（让每个专家的 batch 尽量均衡）；
- 与 KV cache 配合：MLA 把 KV 压缩后，长上下文下 KV 不再是瓶颈，MoE 侧的通信成为唯一大头。

## 五、优缺点总结

| 优点 | 缺点 |
| --- | --- |
| 突破单卡显存上限：671B 级 MoE 才能训练/部署 | 每层两轮 all-to-all，通信量 ∝ T·k·h |
| 专家可独立加载/替换（热更新、A/B 试验） | 低并发下通信时延无法掩盖，单请求延迟高 |
| 与 DP/TP 正交，组合灵活（EPTB） | 负载不均衡直接放大通信与计算瓶颈 |
| 权重只存一份（不复制），显存利用高效 | 依赖 NVLink/IB 全互联，硬件门槛高 |
| 反向只更新被激活专家，梯度稀疏 | 路由动态使通信模式不可预测，难做计算-通信重叠 |

## 六、与同类对比：EP vs TP vs DP vs PP

| 维度 | DP | TP | PP | EP |
| --- | --- | --- | --- | --- |
| 切分对象 | 数据 | 权重矩阵 | 层序列 | 专家 |
| 每卡权重 | 全部 | 每个矩阵的 1/P | 自己的层 | 自己的专家 + 共享层 |
| 主要通信 | 梯度 all-reduce | 每层激活 all-reduce | 层间点对点 | 每层两轮 all-to-all |
| 通信频率 | 每 step 1 次 | 每层 1 次 | 每个 micro-batch 边界 | 每层 2 次 |
| 通信量 | ∝ 权重大小 | ∝ 激活 $O(T \cdot h)$ | ∝ 激活边界 | ∝ $O(T \cdot k \cdot h)$ |
| 瓶颈形态 | 梯度同步带宽 | 组内带宽（NVLink） | 气泡率 | 网络往返 + 负载均衡 |
| 适合规模 | 稠密任意规模 | 单机 8 卡内 | 超大模型跨机 | MoE（专家放不下） |
| 典型组合 | — | TP×DP | TP×PP×DP | **EP×TP×DP**（DeepSeek-V3） |

**选择口诀**：专家放不下 → EP；矩阵太大单卡算不动 → TP；层太多放不下 → PP；并发不够 → DP。MoE 的训练和推理至少 EP×DP，大模型再加 TP。

## 七、高频面试问答

**Q1：MoE 为什么显存大？**
总参数（47B/671B）的权重必须全部常驻显存——路由是输入相关的，无法预知下一个 token 激活哪个专家，所有专家都得在线待命。而算力只花在激活参数（13B/37B）上。所以"省算力不省显存"：显存按总参算、算力按激活参算。

**Q2：EP 和 TP 的区别？**
TP 切单个权重矩阵（每卡持 1/P，协作算一次 matmul，all-reduce 归并）；EP 按专家整块切（每卡持 N/P 个完整专家，token 经两轮 all-to-all 送到目标卡算完再送回）。TP 通信量 O(T·h) 必须在 NVLink 组内；EP 通信量 O(T·k·h)，可跨节点但延迟敏感。

**Q3：all-to-all 通信怎么工作？**
两轮。第一轮 dispatch：每卡把"路由到别卡专家"的 token 发给对应卡（同时收别卡发来的 token）；第二轮 combine：专家算完后把输出送回 token 出发的卡，恢复顺序。两轮都是全连接交换，发送内容由路由动态决定。

**Q4：MoE 推理为什么吞吐高、但单请求延迟不一定低？**
吞吐高：每 token 只算激活参数（13B/37B），同算力下可并发更多请求。延迟不一定低：低并发时两轮 all-to-all 的往返时延和同步等待无法被计算掩盖，且收 token 最多的卡拖慢整层（木桶效应）。

**Q5：EP 的通信量跟什么成正比？**
C = 2×T×k×h×b：token 数、top-k、隐藏维、精度——**与专家总数 N 无关**。k 从 2 到 8，通信量翻 4 倍。

**Q6：为什么 MoE 难微调？**
① 小 batch 下路由分布波动大，负载易失衡；② 部分专家长期不激活（死专家），微调后"活专家"过拟合、死专家更死；③ 路由与任务分布绑定，SFT 数据分布一变路由要重学；④ 通信开销在微调的小 batch 下占比高。实践上多用 LoRA 冻结路由、只调专家。

**Q7：DeepSeek-V3 的 EPTB 怎么组织？**
256 个路由专家分布在 4 节点 32 卡（每卡 8 个、每节点 64 个）；注意力层节点内 TP8；MoE 层节点内 NVLink all-to-all + 跨节点 IB all-to-all；组间 DP 扩大吞吐；MLA 压缩 KV、FP8 减半权重、MTP 配合推测解码。

**Q8：为什么路由在本卡算、专家在别的卡算？**
路由器是 d×N 的小线性层，任何卡都能算；但专家权重是分片存放的，token 必须"人肉"送到专家所在卡才能计算。所以"路由决策本地化 + 计算物理化"：决策零通信、计算必通信。
