# 构建流程与图优化：从 ONNX 到 engine 的"编译"全过程

> 本模块索引见 [TensorRT详解](TensorRT详解.md)

## 一、构建流程五步

"构建（build）"= 把 ONNX 静态计算图编译成针对**目标 GPU** 的可执行 engine，与"推理（inference）"是两个完全独立的阶段：构建可能花几分钟~几小时，推理每次只要毫秒级。

```
┌──────────────┐   ┌──────────────┐   ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│ ① 模型解析    │──►│ ② 精度设置    │──►│ ③ 图优化     │──►│ ④ engine 构建 │──►│ ⑤ 序列化      │
│              │   │              │   │              │   │              │   │              │
│ ONNX 图 →    │   │ FP32/FP16/   │   │ 层融合        │   │ tactic 实测    │   │ 写入         │
│ TRT Network  │   │ INT8/TF32    │   │ 常量折叠      │   │ 选最快 kernel │   │ .engine 文件  │
│              │   │              │   │ 算子替换      │   │ 生成执行计划   │   │              │
└──────────────┘   └──────────────┘   └──────────────┘   └──────────────┘   └──────────────┘
```

逐步说明：

1. **模型解析（Parse）**：`OnnxParser` 把 ONNX 图转成 TRT 的内部 IR（Network，由张量 + 层组成）。除了 ONNX，老接口还支持 UFF/TensorFlow；PyTorch 需要先 `onnx.export` 导出（或用 torch2trt/torch_tensorrt 桥接，本质也是先生成 ONNX 再解析）；
2. **精度设置（Precision Flags）**：在 BuilderConfig 里声明"允许使用的精度"（FP16/INT8 等）。注意这是**允许**而非**强制**——具体每层用 FP32 还是 FP16 由第 ③ 步图优化决定；
3. **图优化（Graph Optimization）**：本模块核心（见第二节）。层融合、常量折叠、死代码消除、逐层精度分配，把"多算子图"变成"少 kernel 图"；
4. **engine 构建（Build）**：耗时最长的阶段。为每个层枚举候选 CUDA kernel（tactic）并在**目标 GPU 上实测计时**，挑最快的固化，最终产出一张可执行计算图；
5. **序列化（Serialize）**：把 engine 写成 `.engine` 字节流落盘；推理端 `deserialize` 加载即可用。**注意：序列化 ≠ 可移植**，engine 仍与 GPU 型号/CUDA/TRT 版本绑定。

> Timing Cache 的作用在第三节 3.3；构建慢的模型务必用它避免每次重跑 tactic。

## 二、图优化（本模块核心）

### 2.1 为什么需要图优化：两类开销

GPU 上每多一个 kernel，就有两类固定成本：    

1. **kernel 启动开销**：CPU 向 GPU 提交一次任务，约 3~10µs。一个几十~上百算子的模型，naive 执行会有上百次启动——纯 GPU 干活的时间可能还不如"喊 GPU 干活"的时间；
2. **中间张量显存读写**：每个算子的输出要写回全局显存，下个算子再读回来。逐元素类算子（加、乘、ReLU、BN）是**内存密集**的：读写花的时间远超计算本身，把它们并进前一个 kernel 的"尾部（epilogue）"几乎白赚。

**融合 = 把多个算子合并成一个 kernel**：启动次数变少 + 中间数据留在寄存器/共享内存不落显存。这是 TRT"快"的最大来源。量化直觉：若某中间张量 10MB，naive 执行要被"写一次 + 读一次"共 20MB 显存流量，融合后直接省掉；逐元素算子多的模型，省下的流量占全体流量大头。

### 2.2 Conv + Bias + ReLU 融合（CBR）

卷积后紧跟 bias 加法与 ReLU 是 CNN 最常见组合：

$$y = \max(0, W \cdot x + b)$$

三个算子的**计算**都是必须的，但三者合到一个 kernel 里：

- 卷积算完一个输出 tile → 在寄存器里加 bias → 过 ReLU → 写回显存；
- 效果：3 个 kernel → 1 个，省 2 次中间张量往返。这是"kernel 内融合"的代表：逐元素算子（bias、激活）被并进前一个算子的 epilogue。

### 2.3 Conv + BN 融合（BN 参数折叠，公式推导）

BN 在推理时是确定的仿射变换（用训练期累计的 running mean/var，不是 batch 统计量），可以直接"折叠"进 Conv 权重，零额外计算、零精度损失。

BN 推理公式：

$$\hat{x} = \frac{x - \mu}{\sqrt{\sigma^2 + \epsilon}} \cdot \gamma + \beta$$

把卷积输出 $x = W \cdot a + b$ 代入：

$$\hat{x} = \frac{\gamma}{\sqrt{\sigma^2 + \epsilon}} \left( W \cdot a + b - \mu \right) + \beta = \underbrace{\frac{\gamma}{\sqrt{\sigma^2+\epsilon}} W}_{W'} \cdot a + \underbrace{\frac{\gamma\left(b - \mu\right)}{\sqrt{\sigma^2+\epsilon}} + \beta}_{b'}$$

折叠后的等效卷积：

$$y = W' \cdot a + b'$$

关键点：

- 折叠只发生在**推理路径**：训练时 BN 依赖 batch 统计量（每个 batch 都变），不能折叠；所以"推理图 ≠ 训练图"；折叠后模型里**不再有 BN 层**，省掉一个逐元素 kernel + 其显存往返；
- 折叠通常由 ONNX 导出时的 graphsurgeon 或 TRT 图优化自动完成，无需手写——但面试必须能推出上面的公式；
- 折叠必须在**量化之前**做：先折叠 BN 再量化权重，误差更小（否则量化误差会被 BN 放大）。

### 2.4 Multi-head Attention 的融合（Transformer 的关键）

自注意力三步：QKV 投影 → 注意力打分 → 输出投影。TRT 把每一段都做了融合。

**QKV 融合**：三个线性层 $Q = XW_Q,\ K = XW_K,\ V = XW_V$ 输入都是同一个 $X$，权重沿输出维拼接成一个矩阵：

$$W_{QKV} = \left[ W_Q,\ W_K,\ W_V \right], \qquad \left[ Q, K, V \right] = X \cdot W_{QKV}$$

3 次 GEMM → 1 次：计算量不变，但省 2 次 kernel 启动，以及中间 $Q,K,V$ 的排布开销。前提是三个权重形状一致（同 $d_k$），否则不能简单拼接。

**Softmax 融合**：

$$\text{Attn} = \text{softmax}\left( \frac{QK^{\top}}{\sqrt{d_k}} + M \right) V$$

$QK^{\top}$ 之后依次是 scale（$\div \sqrt{d_k}$）、mask 加偏、softmax、再乘 $V$——这 4~5 步全是逐元素/矩阵运算。TRT 的 fused attention kernel 把它们合成一步：$QK^{\top}$ 的结果和 softmax 的中间矩阵**都不落显存**（与 FlashAttention 思路一致，顺序分块 + 在线 softmax 技巧）。

**输出融合**：多头拼接（reshape）→ 输出投影（GEMM）→ 残差相加（elementwise）→ LayerNorm，均可并入 kernel 的 epilogue。

一个 Transformer block 融合前后的 kernel 数（约数，因 TRT 版本与实现而异）：

| 子结构                               | 融合前（naive 拆分）    | 融合后                        |
| --------------------------------- | ---------------- | -------------------------- |
| QKV 三个线性层                         | 3 个 GEMM kernel  | 1 个 GEMM kernel            |
| 注意力主体（QK^T/scale/mask/softmax/PV） | 约 5 个 kernel     | 1 个 fused attention kernel |
| 输出投影 + 残差                         | 2 个 kernel       | 1 个 kernel                 |
| LayerNorm                         | 2~3 个 kernel     | 1 个 kernel                 |
| 合计                                | 约 12~13 个 kernel | 约 4 个 kernel               |

### 2.5 残差与 elementwise 融合

- **残差** $y = x + \text{Sub}(x)$：add 是逐元素，融合进 sublayer kernel 的 epilogue，残差张量不必单独读写一遍；
- **归一化**：LayerNorm（mean/var/仿射/激活）整段融合；**1×1 卷积**等价 GEMM 自动映射；
- **常量折叠**：全是常量的子图（如某些 mask 生成）在构建期直接算完写死，推理期不存在。

### 2.6 融合小结

| 融合类型                     | 原理                                 | 收益               |
| ------------------------ | ---------------------------------- | ---------------- |
| 逐元素/激活融合（Conv+Bias+ReLU） | elementwise 并入前序 kernel 的 epilogue | 省启动 + 省显存往返      |
| BN 折叠（Conv+BN）           | 仿射变换折进 Conv 权重                     | 少一个 kernel，零精度损失 |
| QKV 融合                   | 三个 GEMM 拼一个权重矩阵                    | 3 启动 → 1 启动      |
| Softmax/注意力融合            | scale/mask/softmax/PV 一段合成         | 中间矩阵不落显存         |
| 残差/归一化融合                 | elementwise 并入 epilogue            | 省显存读写            |

> 面试一句话：**融合的本质是"让中间结果不出寄存器"，把"内存密集"的部分变成"免费"**。

## 三、kernel 自动选择：tactic 机制

### 3.1 什么是 tactic

同一个"卷积/矩阵乘"在 GPU 上有几十种实现，差异在于：计算单元（SIMT 普通 CUDA core vs Tensor Core）、tile 大小（共享内存复用 vs 寄存器压力）、数据布局（NHWC/NCHW）、来源（cuDNN/cuBLAS 标准库 vs TRT 自研 CUTLASS 系 kernel）。

TensorRT 把每层的一堆候选实现叫 **tactic**，构建时全部在**目标 GPU 上真实跑一遍计时**，选最快的固化进 engine。这就是"engine 必须针对具体 GPU 现测现选、不能跨卡复用"的根本原因——同一层在 A100 与 RTX 4090 上的最优 kernel 可能不同。

### 3.2 plugin：自定义算子

ONNX 里没有的算子（NMS、RoIAlign、多模态的采样/拼接、LLM 的 RoPE 变体等）通过 **Plugin** 注册进 Network：自己实现 kernel，提供 `getOutputType/getOutputShape/serialize` 等接口，让 TRT 像原生层一样参与构建与序列化。Plugin 也可参与 tactic 选择（多实现时实测挑选）。

### 3.3 构建时间 vs 推理速度的权衡

这是本模块最重要的工程权衡：

| 手段                                     | 推理收益        | 构建代价                    |
| -------------------------------------- | ----------- | ----------------------- |
| 候选 tactic 越多                           | 每层更可能选中更快实现 | 实测耗时线性增长                |
| 动态 shape                               | 灵活          | opt 档位要做多组形状的 tactic，更慢 |
| 低精度（FP16/INT8）                         | 更快          | 候选更少，构建反而更快             |
| `builder_optimization_level`（0~5，默认 3） | 更高可能更优      | 更高越慢                    |

**Timing Cache（推荐必用）**：`--timingCacheFile=timing.cache` 把 tactic 实测结果缓存到文件。同 GPU 型号 + 同配置下二次构建直接复用结果，**跳过实测**，构建时间从小时级降到分钟级。缓存要随"GPU 型号 × TRT 版本"分开管理，混用会得到错误的 kernel 选择。

> 工程默认：构建参数（精度、timing cache、workspace）写进 CI 脚本、产物归档；禁止每次启动服务时重新构建。

## 四、精度设置

| 精度 | 说明 | 相对 FP32 吞吐 | 何时用 |
| --- | --- | --- | --- |
| FP32 | 默认基准 | 1× | 保底、对精度敏感的层 |
| TF32 | FP32 的截断版（10 位尾数），Ampere+ Tensor Core 原生，TRT 默认开启 | 约 2~8×（A100） | 无需手动开，精度接近 FP32 又接近 FP16 的吞吐 |
| FP16 | 半精度，动态范围小 | 约 2× | 视觉/LLM 的默认首选 |
| INT8 | 需校准，精度损失最大 | 约 4× | 高吞吐在线服务（精度验证通过后） |
| FP8 | Hopper（H100）+，TRT 9.0+，E4M3 | 约 2×（vs FP16） | 大模型推理（TensorRT-LLM） |

要点：

- **flag 是"允许"不是"强制"**：`config.set_flag(trt.BuilderFlag.FP16)` 之后，TRT 逐层权衡——敏感层保持 FP32，其余降 FP16，最终每层精度由构建决定；
- **TF32 说明**：Ampere+ 上 TRT 默认启用（`--tf32` / 默认开），需要严格 FP32 时显式关掉（`--noTF32`）。它用 19 位（1+8+10）表示数，误差远小于 FP16，却能用 Tensor Core 提速；
- **INT8 必须校准**：喂一批**代表性数据**，统计每层激活分布，用熵校准（默认）/min-max 等方法算出量化 scale。校准数据分布必须贴近线上真实输入，否则掉点（详见 [精度与量化.md](精度与量化.md)）；
- **每个精度都要评测**：切精度前先定评测集与指标，量化后跑一遍对比，掉点超标就回退或做敏感层保护。

## 五、动态 shape（重点）

### 5.1 静态 vs 动态

- **静态**：构建时 batch、H、W 全固定（如 `1x3x224x224`）。engine 为这个形状专门优化，**性能最好**，但换个形状就要重新构建——在线服务没法接受；
- **动态**：构建时声明每个输入的（min, opt, max）区间，推理时允许区间内任意实际形状，TRT 运行时自动调整 kernel 与缓冲。**前提是构建时用 `EXPLICIT_BATCH`**（batch 也是显式维度）。

### 5.2 profile：min / opt / max

一个 **profile** 是"每个动态输入的一组 (min, opt, max) 三元组"：

| 档位 | 含义 | 影响 |
| --- | --- | --- |
| min | 最小合法形状（如 batch=1） | 运行时的下界 |
| opt | 最常见形状 | **kernel 按它挑选**（tactic 搜索基准） |
| max | 最大合法形状（如 batch=32） | 显存按它预留的上界 |

关键规则：

- 推理时 `context.set_input_shape(name, shape)` 给出的实际形状**必须在 [min, max] 内**，否则报错；
- **形状离 opt 越远，性能越差**（kernel 是按 opt 选的，其余形状尽量复用）——所以 opt 一定要填最常见的形状；
- 多输入网络每个动态输入都要在 profile 里给三元组，可独立设区间；输入名必须与 ONNX 图一致（profile 写 `"input"`，ONNX 里就叫 `input`）。

### 5.3 为什么多模态必须动态 shape

1. **batch 变化**：在线服务请求量波动，无法按固定 batch 构建，min=1、opt=服务平均 batch、max=峰值 batch；
2. **分辨率可变**：ViT 输入不是固定 224/336——高分辨率文档（4096+）、多尺度检测、任意宽高比图像，H/W 都要动态；
3. **token 序列长度可变**：视觉 token 数量随分辨率变，与文本拼接后序列长度变化 → LLM 侧由 TensorRT-LLM 的 PagedAttention 处理（见子篇三），视觉塔侧用动态 shape engine；一条链路两套动态（H/W/batch + 序列长/batch），各自独立管理。

### 5.4 多 profile 与代价（含显存）

- 一个 engine 可加**多个 profile**（如"低分辨率 1~4 batch" + "高分辨率 1 batch"），推理时 `context.set_optimization_profile(i)` 切换再设形状；
- **代价**：engine 文件更大（每 profile 带自己的 kernel 选择与缓冲规划）、构建时间更长（每 profile 都做 tactic 搜索）、运行时多一步选 profile；
- **原则**：能用一个 profile 的区间覆盖就绝不加第二个；极端形状差异（如 224 vs 4096 分辨率）才值得拆 profile；
- **显存**：推理峰值按 **max shape** 预留——maxShape 设太大显存白占，设太小高分辨率输入直接爆显存。动态 shape 本质是"用显存上限换灵活性"。

## 六、显存池（workspace）

**workspace = 构建/推理时允许 TRT 使用的临时显存池（scratch memory）**，与"模型总显存"是两个概念。

| 阶段  | workspace 的作用                                                                                      |
| --- | -------------------------------------------------------------------------------------------------- |
| 构建  | tactic 基准测试可用的临时显存上限。越大 → 越复杂的 kernel（大 tile、更激进算法）越可能被选中；太小 → 某些候选 kernel 内存不够，被迫退回"省显存的慢 kernel" |
| 推理  | 每个 execution context 的中间缓冲 arena。构建时已按计算图分析好各张量生命周期，推理全程**零动态分配**，从池里按计划复用                         |


配置方式：trtexec 用 `--memPoolSize=workspace:2147483648`（单位**字节**，8.5+ 新参数，替代旧 `--workspace`）；Python 用 `config.set_memory_pool_limit(trt.MemoryPoolType.WORKSPACE, 2 << 30)`（即 2 GiB）；TRT 8.5 前是 `builder.max_workspace_size`（已废弃）。

> 误区澄清：workspace 设大**不等于**总显存一定大——总显存 = 权重 + 激活缓冲 + workspace。经验做法：workspace 给 1~2 GiB 起步，构建日志提示"内存不足导致 tactic 被跳过"再加大。

## 七、源码实现

> 本机为 macOS（无 NVIDIA GPU），以下代码/命令为**标准可运行示例**，需在 Linux + NVIDIA GPU + CUDA 环境运行；注释标明预期行为，实际数值依 GPU 与模型而定。

### 7.1 trtexec 命令行（构建与 benchmark 工具）

位置：`$TRT_ROOT/bin/trtexec`（安装 TensorRT 后通常已在 PATH）。

**① FP32 构建 + 基准测试**

> 需 Linux + NVIDIA GPU + CUDA 环境运行

```bash
# 构建 FP32 engine（默认精度），benchmark 平均 100 次
trtexec --onnx=resnet50.onnx --saveEngine=resnet50_fp32.engine --avgRuns=100
```

**② FP16 构建 + 基准测试**

> 需 Linux + NVIDIA GPU + CUDA 环境运行

```bash
# --fp16 允许层以 FP16 计算（敏感层仍可保持 FP32）
trtexec --onnx=resnet50.onnx --saveEngine=resnet50_fp16.engine --fp16 --avgRuns=100
```

**③ INT8（需要校准数据/校准缓存）**

> 需 Linux + NVIDIA GPU + CUDA 环境运行

```bash
# --int8 启用 INT8；--calib 指定校准缓存文件（首次生成、之后复用）
trtexec --onnx=resnet50.onnx --int8 --calib=resnet50_calib.bin \
        --saveEngine=resnet50_int8.engine --avgRuns=100
```

**④ 动态 shape + timing cache + verbose（生产标准组合）**

> 需 Linux + NVIDIA GPU + CUDA 环境运行

```bash
trtexec --onnx=model.onnx \
        --fp16 \
        --minShapes=input:1x3x224x224 \
        --optShapes=input:8x3x224x224 \
        --maxShapes=input:32x3x224x224 \
        --timingCacheFile=timing.cache \
        --verbose \
        --saveEngine=model_fp16.engine
```

**⑤ 加载已有 engine 做 benchmark**

> 需 Linux + NVIDIA GPU + CUDA 环境运行

```bash
# 对动态 engine 指定 benchmark 形状（只跑不重建，适合对比验证）
trtexec --loadEngine=model_fp16.engine \
        --shapes=input:1x3x224x224 \
        --avgRuns=100
```

参数速查表：

| 参数 | 作用 |
| --- | --- |
| `--onnx=<path>` | 输入 ONNX 模型 |
| `--saveEngine=<path>` | 构建完成后序列化保存 engine |
| `--loadEngine=<path>` | 加载已有 engine（配合 `--shapes` 指定动态 shape） |
| `--buildOnly` | 只构建不执行，适合 CI |
| `--fp16` / `--int8` / `--tf32` | 开启对应精度（可组合） |
| `--calib=<file>` | INT8 校准缓存（存/读） |
| `--minShapes` / `--optShapes` / `--maxShapes` | 动态 shape profile，格式 `输入名:维度`（如 `input:1x3x224x224`） |
| `--avgRuns=<N>` | benchmark 平均次数（默认 10，生产建议 100+） |
| `--warmUp=<ms>` / `--duration=<ms>` | 预热时间 / 测时时长 |
| `--verbose` | 打印每层 tactic 选择与构建细节 |
| `--timingCacheFile=<path>` | kernel 计时缓存，加速二次构建 |
| `--memPoolSize=workspace:<bytes>` | workspace 显存池大小（8.5+，替代旧 `--workspace`） |
| `--shapes=<input:dim>` | 对动态 engine 指定 benchmark 用形状 |

预期行为：成功时构建阶段 `--verbose` 会打印各层的 Tactic 选择与耗时；benchmark 阶段打印 Latency（mean/min/max）与 Throughput 等统计（具体数值依 GPU 型号与模型而定，不在此处伪造）。

### 7.2 Python API 构建（标准写法）

> 需 Linux + NVIDIA GPU + CUDA 环境运行

```python
import tensorrt as trt

logger = trt.Logger(trt.Logger.WARNING)  # 调 ERROR/VERBOSE 可看更多细节

def build_engine(onnx_path: str, save_path: str,
                 fp16: bool = True,
                 min_shape=(1, 3, 224, 224), opt_shape=(8, 3, 224, 224),
                 max_shape=(32, 3, 224, 224)) -> bytes:
    builder = trt.Builder(logger)

    # ① 模型解析：ONNX → TRT Network（EXPLICIT_BATCH 使 batch 成为显式维度，动态 shape 的前提）
    network = builder.create_network(
        1 << int(trt.NetworkDefinitionCreationFlag.EXPLICIT_BATCH))
    parser = trt.OnnxParser(network, logger)
    with open(onnx_path, "rb") as f:
        ok = parser.parse(f.read())
    if not ok:
        for i in range(parser.num_errors):
            print(parser.get_error(i))   # 常见：不支持的 ONNX 算子
        raise RuntimeError("ONNX 解析失败")

    config = builder.create_builder_config()

    # ② 精度设置：允许层使用 FP16（敏感层仍可保持 FP32，由构建权衡）
    if fp16:
        config.set_flag(trt.BuilderFlag.FP16)
    config.set_memory_pool_limit(trt.MemoryPoolType.WORKSPACE, 2 << 30)  # workspace 上限，2 GiB

    # 动态 shape：一个 profile = (min, opt, max) 三元组
    profile = builder.create_optimization_profile()
    profile.set_shape("input", min_shape, opt_shape, max_shape)
    config.add_optimization_profile(profile)

    # ③④ 图优化 + tactic 选 kernel 在 build 内部完成，本步最耗时
    serialized = builder.build_serialized_network(network, config)
    assert serialized is not None, "构建失败（调高 logger 级别排查）"

    with open(save_path, "wb") as f:  # ⑤ 序列化落盘
        f.write(serialized)
    return serialized

if __name__ == "__main__":
    build_engine("resnet50.onnx", "resnet50_fp16.engine")  # 预期：engine 生成、无报错
    print("engine 已保存")
```

> 版本差异：TRT 8.5 前用 `builder.build_engine(network, config)` 拿 engine 再 `engine.serialize()`；新版推荐 `build_serialized_network` 直接返回字节流。INT8 构建需再配一个 calibrator（见 [精度与量化.md](精度与量化.md)）。

### 7.3 反序列化 + 推理（标准写法）

> 需 Linux + NVIDIA GPU + CUDA 环境运行

```python
import time
import numpy as np
import tensorrt as trt
import torch

logger = trt.Logger(trt.Logger.WARNING)

def load_engine(path: str) -> trt.ICudaEngine:
    runtime = trt.Runtime(logger)
    with open(path, "rb") as f:
        engine = runtime.deserialize_cuda_engine(f.read())
    assert engine is not None, "加载失败：engine 与当前 GPU/CUDA/TRT 版本不匹配"
    return engine

class TRTInfer:
    def __init__(self, engine_path: str):
        self.engine = load_engine(engine_path)
        self.context = self.engine.create_execution_context()
        # 枚举 I/O tensor 名与输入输出分组（TRT 8.5+ 的 get_tensor_name 系列 API）
        self.names = [self.engine.get_tensor_name(i)
                      for i in range(self.engine.num_io_tensors)]
        self.inputs = [n for n in self.names
                       if self.engine.get_tensor_mode(n) == trt.TensorIOMode.INPUT]
        self.outputs = [n for n in self.names if n not in self.inputs]

    def __call__(self, feed: dict[str, np.ndarray]) -> dict[str, np.ndarray]:
        for name, arr in feed.items():  # ① 动态 shape：按实际输入设置（须在 min/max 内）
            self.context.set_input_shape(name, arr.shape)

        # ② 按 engine 声明的 dtype/shape 分配 device 端 buffer，③ host → device 拷贝
        t_dtype = {trt.float32: torch.float32, trt.float16: torch.float16,
                   trt.int32: torch.int32,   trt.int8: torch.int8}
        bufs = {}
        for name in self.names:
            shape = tuple(self.context.get_tensor_shape(name))
            dtype = t_dtype[self.engine.get_tensor_dtype(name)]
            bufs[name] = torch.empty(shape, dtype=dtype, device="cuda")
        for name, arr in feed.items():
            bufs[name].copy_(torch.from_numpy(arr.astype(np.float32)))

        # ④ 执行（bindings 按 I/O 顺序传 device 地址）
        stream = torch.cuda.current_stream().cuda_stream
        self.context.execute_async_v2(
            bindings=[bufs[n].data_ptr() for n in self.names],
            stream_handle=stream)

        return {n: bufs[n].cpu().numpy() for n in self.outputs}  # ⑤ device → host（同 stream 同步）

if __name__ == "__main__":
    model = TRTInfer("resnet50_fp16.engine")
    x = np.random.rand(1, 3, 224, 224).astype(np.float32)
    y = model({"input": x})["output"]
    print(y.shape)                       # 预期 (1, 1000)，分类 logits
```

## 八、常见坑

1. **ONNX 算子不支持**：parser 报"不支持的算子"。对策：升级 TRT、用 onnx-graphsurgeon 重写子图、写 Plugin；**根治在训练侧**——训练时避免自定义/动态控制流算子（导出 ONNX 前先审计算子清单）；
2. **动态 shape 对不上**：`set_input_shape` 越界（超出 min/max）直接失败；profile 里的输入名与 ONNX 图不一致（写 `"input"` 却叫 `"images"`）；`optShapes` 没填（动态 shape 必须给全三元组）；
3. **engine 与 GPU 型号绑定**：A100（sm_80）上构建的 engine 放到 RTX 4090（sm_86）/V100（sm_70）上跑不了或性能崩坏。生产按"GPU 型号 × TRT 版本"建构建矩阵，CI 里各自构建归档；
4. **构建时间超长**：大模型 + 动态 shape + 默认优化等级，构建可达小时级。对策：timing cache 复用、`--buildOnly` 在 CI 构建、调低 `builder_optimization_level`、能静态就静态；
5. **精度与版本兼容**：FP16 注意溢出（大激活/小数值）；INT8 校准数据必须贴近线上分布，量化后必须用评测集确认不掉点（详见 [精度与量化.md](精度与量化.md)）；升级 CUDA/cuDNN 后旧 engine 可能加载失败需重构建，timing cache 也要按版本重跑；
6. **动态 shape 显存按 max 预留**：maxShape 设太大显存白占（峰值按它算），设太小高分辨率输入爆显存；容量规划要按"max shape 激活 + workspace + 权重"估算。

## 九、高频面试问答

**Q1：TensorRT 为什么快？按贡献排序？**
四个层面：① 层融合（省 kernel 启动 + 省中间张量显存往返，逐元素/卷积多的模型收益最大）；② tactic 自动选 kernel（每层在目标 GPU 实测挑最快）；③ 低精度（FP16/INT8/TF32/FP8 翻倍吞吐 + 减带宽）；④ 显存池（推理零动态分配）+ 深度算子库。卷积多的模型①贡献最大，GEMM 密集模型②④贡献大。

**Q2：层融合有哪些？原理是什么？**
Conv+Bias+ReLU（逐元素并入卷积 epilogue）；Conv+BN 折叠（$W'=\frac{\gamma}{\sqrt{\sigma^2+\epsilon}}W,\ b'=\frac{\gamma(b-\mu)}{\sqrt{\sigma^2+\epsilon}}+\beta$）；QKV 三 GEMM 拼一（$W_{QKV}=[W_Q,W_K,W_V]$）；softmax 整段融合（scale/mask/softmax/PV 一段，中间矩阵不落显存）；残差/归一化并入 epilogue。本质：**让中间结果不出寄存器/共享内存**。

**Q3：engine 和 ONNX/PyTorch 模型文件有什么区别？**
`.pth`/`.onnx` 是"定义 + 权重"，跨平台可被解释执行，灵活但慢；engine 是把图优化 + kernel 选择全部做完的**可执行编译产物**，快但绑定 GPU 型号、精度与 shape 档位，不能当通用权重分发。类比：源码 vs 编译好的二进制（且只对特定 CPU 优化）。

**Q4：动态 shape 是什么？min/opt/max 怎么选？**
构建时声明每个动态输入的最小/最优/最大形状；推理时允许区间内任意实际形状。min=最小合法输入，opt=最常见形状（**kernel 按它选**，离它越远越慢），max=最大合法输入（显存按它预留）。多模态（可变分辨率 + 可变 batch + 可变序列长）几乎必须动态。

**Q5：FP16 和 INT8 有什么区别？INT8 为什么要校准？**
FP16 直接开，吞吐约 2×FP32，注意溢出与精度验证；INT8 吞吐约 4×FP32，但必须先**校准**：喂代表性数据统计激活分布，算量化 scale 使量化误差最小。不校准的 INT8 scale 靠猜，掉点不可控。校准数据分布必须贴近线上真实输入。

**Q6：workspace 是什么？设大设小有什么影响？**
workspace 是构建/推理的临时显存池。构建期决定 tactic 可选范围（太小→复杂 kernel 因内存不够被跳过，被迫选慢 kernel）；推理期是中间缓冲的 arena（构建期已规划，运行时零分配）。总显存 = 权重 + 激活 + workspace，不是 workspace 一个数。

**Q7：为什么同一个 engine 不能跨 GPU 用？**
tactic 是**在目标 GPU 上实测**选出来的，不同 sm 架构（A100 sm_80 vs 4090 sm_86）的最优 kernel 不同、指令集不同，engine 里的 kernel 二进制不兼容。跨卡型强跑会失败或性能崩坏，正确做法是按 GPU 型号分别构建。

**Q8：构建时间为什么这么长？怎么加速？**
构建要做"每层 × 多套候选 kernel × 多种形状"的**真实计时**，大模型可达小时级。加速：timing cache（复用实测结果，同 GPU 同配置跳过实测）；调低 `builder_optimization_level`；固定形状（动态 shape 构建更慢）；CI 里 buildOnly 一次性构建并归档产物。
